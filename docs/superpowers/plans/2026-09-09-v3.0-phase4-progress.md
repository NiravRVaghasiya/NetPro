## Repository analysis and phase selection

- PR #33 supplied the v3.0 roadmap; PR #34 merged workspace schema/auth.
- The roadmap's **Suggested order of implementation** explicitly puts Phase 4
  after Phase 1, independently of Phases 2–3, as the prerequisite for plugins.
  This PR takes that independent track; it does not claim Phase 2 is complete.
- Existing web credentials were read only from env in outreach, AI skills,
  enrichment, and embeddings. Content token-based adapters remain disabled
  stubs, not functioning integrations that can be enabled by storing a key.
- Existing `WorkspaceScope` and live membership checks are reused. Vault
  queries and writes are explicitly scoped in core, with no HTTP-supplied
  workspace/user ID accepted as authority.

## Implementation

- Migration `0009_key_vault` for SQLite and PostgreSQL, schema definitions,
  journal entries, and current-schema Drizzle snapshots. Prior phases stopped
  snapshot generation at `0002`; the new snapshots also capture those existing
  schema additions, without adding unrelated SQL migrations.
- Partial unique indexes distinguish personal and NULL-user workspace slots,
  with atomic conflict-target upserts (including concurrent first writes).
- AES-256-GCM with random 12-byte IVs, 16-byte authentication tags, and
  principal/slot-bound SHA-256 key derivation. The principal is a JSON tuple
  to avoid delimiter ambiguity. No crypto dependencies beyond Node.
- `ENCRYPTION_MASTER_KEY` requires at least 32 non-padding characters. Missing
  or short master means read-only management and env-only credential use.
  Wrong configured master/tampering produces a generic failure, not fallback.
  Error messages are uniform; no claim of constant *whole-request latency*.
- Core save/list/remove/resolve functions enforce scope, ownership, provider
  slot validation, and member/admin write floors. Metadata explicitly selects
  only safe columns; ciphertext never reaches management responses.
- `/settings/keys` and `/api/settings/keys` supply personal/shared save/remove,
  masked status, usage times, bounded JSON, and no-store responses. Authenticated
  membership is resolved fresh, not trusted from request parameters.
- Outreach, AI skills, enrichment, and hybrid embeddings use personal → shared
  → env resolution. Search capability rendering checks only metadata; it does
  not decrypt credentials or mark them used. Env-only health status stays public
  and never inspects user credentials.
- Web provider error adapters suppress upstream/network error details before
  they can enter core summaries or API responses: errors can echo shared API
  keys or credential-bearing URLs. CLI provider diagnostics remain unchanged.
- Content slots and `plugin.<id>` core slots are reserved for future consumers;
  the built-in settings UI lists content slots honestly as not yet enabled.
- CLI keychain unchanged. Deployment docs cover backup, read-only mode,
  replacement after master changes, role boundaries, and retained credentials
  after membership revocation.

## Deliberate plan adjustments

1. Migration numbers reflect landing order: vault is **0009**, future Phase 2
   authorship becomes **0010**. No placeholder migration and no rewriting old
   journal history. The plan is updated accordingly.
2. The naive nullable three-column UNIQUE constraint is replaced by two partial
   unique indexes; otherwise SQL permits multiple workspace-level keys.
3. Provider slot is part of the derivation principal as well as workspace/user,
   preventing ciphertext relocation between different slots of the same user.
4. Short credentials are rejected (minimum eight characters), so revealing the
   final four can never reveal the whole stored credential.
5. No automatic master-key rotation/re-encryption, functioning content clients,
   plugin runtime, or application-wide tenant/GDPR retrofit is claimed here.

## Security review checklist

- [x] No plaintext persisted in vault rows or management responses.
- [x] Ciphertext bound to workspace, user, and slot; tampering rejected.
- [x] No other user's personal keys in listings; no cross-workspace resolution.
- [x] Request-supplied user/workspace IDs ignored; 401/403 paths tested.
- [x] Shared modifications admin+, personal modifications member+ in core.
- [x] Bounded request bodies/credential lengths; no secret-bearing DB errors logged.
- [x] External error text suppressed before entering web summaries/responses.
- [x] Public health and CLI keychain behavior unchanged.
- [ ] Live PostgreSQL and Docker verification: delegated to PR CI.
