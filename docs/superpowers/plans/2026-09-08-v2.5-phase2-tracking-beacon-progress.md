# v2.5 Phase 2 — Tracking beacon & ingestion pipeline — progress

Implemented against
[docs/superpowers/plans/2026-09-08-v2.5-implementation-plan.md](./2026-09-08-v2.5-implementation-plan.md).

## What shipped

`profile_views` — the producer-less table Phase 1 hardened — now has a
producer. Every view of the public card flows through two public beacon
endpoints and one core ingestion function, with all Phase 1 hardening
applied at the write path.

- **Core `@netpro/core/views` additions** (`packages/core/src/views/`,
  exported from `core.views`):
  - `referrer.ts` — `parseReferrer`: absolute http(s) only, query string
    stripped (it is the main channel for token leakage), capped at 200
    chars, anything else → `null`.
  - `utm.ts` — `parseUtm` / `mergeUtm`: reads `utm_source|medium|campaign`
    from the beacon URL and the referrer, URL params win per field, each
    value capped.
  - `ratelimit.ts` — `createRateLimiter` (fixed-window in-memory counter,
    the plan's "in-memory token bucket, no Redis") + `BEACON_RATE_LIMIT`
    (60/min). Keyed by the salted IP hash, never the raw IP; a
    `reset()` for tests.
  - `beacon.ts` — the rest of the pipeline:
    - `extractViewerIp` — first `X-Forwarded-For` entry or `X-Real-Ip`,
      validated as an IP literal; a non-literal value is treated as absent
      (a spoofer controls the whole header, so no fallthrough to proxy
      hops).
    - `extractViewerGeo` — Vercel (`x-vercel-ip-country|city`) and
      Cloudflare (`cf-ipcountry`) headers only, 64-char cap; NetPro never
      runs a geo lookup.
    - `isDntRequest` — `DNT: 1` / `Sec-GPC: 1` → minimal mode.
    - `VIEWED_PAGES` / `normalizeViewedPage` — allowlist
      (`/card`, `/card/vcard`, `blog`, `portfolio`, `embed`); unknown
      values snap to `/card` rather than erroring — beacons degrade
      silently.
    - `shouldCountView` — pure dedup decision: same fingerprint within 5
      min, or same IP hash + page within 1 h, skips the row with a reason
      (`new` / `dedup-fingerprint` / `dedup-ip-page`). One round trip
      covers both rules: the probe only selects rows inside the longer
      window and the fingerprint rule re-checks its window in JS.
    - `recordView(conn, input)` — applies everything (HMAC hashing, bot
      and owner labeling, minimal mode, dedup, 1-hour duration clamp,
      500-char UA cap) and inserts one row. Dialect-branched Drizzle
      insert (the house pattern); the better-sqlite3 branch needs the
      explicit `.run()` terminal.
    - `createContactViewToken` / `resolveContactFromToken` /
      `findLiveContactId` — signed `?v=` tokens:
      `base64url(contactId|exp|HMAC-SHA256(NEXTAUTH_SECRET, contactId|exp))`,
      30-day cap, timing-safe comparison, and the contact must still
      exist. Every failure mode (empty secret, wrong shape, expiry, cap,
      forged signature, dead contact) resolves to `null`, never an error
      — and there is no path from IP or email to a contact.
- **Web ingestion layer** (`apps/web/lib/beacon.ts`): the only place
  beacon request headers are read. `viewsDisabled` (`NETPRO_DISABLE_VIEWS`),
  `viewBaseSalt` (`NETPRO_VIEW_SALT` → `NEXTAUTH_SECRET` → built-in),
  `beaconRateLimiter`, and `readViewBeaconContext(request, input)` →
  `{ record, rateLimitKey }`.
- **`GET /api/card/pixel.gif`** — always a 42-byte 1×1 GIF with
  `Cache-Control: no-store, no-cache, private`; 200 normally, 429 when the
  per-IP rate limit is exhausted (still the GIF — a 4xx on a cross-origin
  `<img>` would be visible to a curious owner's visitor), and 200 with no
  write when tracking is disabled. Params: `p` (page), `r` (referrer),
  `v` (token).
- **`POST /api/card/view`** — JSON `{ page, referrer, durationMs,
  viewToken }` for browsers that can measure visit duration.
  `OPTIONS` → 204 + CORS `*` (cross-origin embeds). The body is
  stream-capped at 8 KiB; non-JSON → 415, oversize/malformed/bad-shape →
  400. Success: `{ counted, reason }`; disabled: `{ counted: false,
  reason: "disabled" }`.
- **`/card` page** — exactly one beacon per visit: a `<noscript>` pixel
  for non-JS clients, and in JS browsers a `pagehide`
  `navigator.sendBeacon` (with a `fetch` keepalive fallback) carrying
  `durationMs` and the `?v=` token. The token is injected as a
  `JSON.stringify` of a value gated on the base64url charset first
  (`</script>` cannot appear), and the beacon script is a plain string
  constant — never evaluated at server import.
- **Proxy** (`apps/web/proxy.ts`) — both beacon paths added to
  `PUBLIC_ROUTES`, so the edge leaves them alone (no session read) while
  `/api/card` and every other subpath still require a session.
- **Settings surface** (`apps/web/app/(app)/settings/card/`) —
  `tracking-panel.tsx` (dumb presentational component) + the page
  resolves the public origin from `x-forwarded-host`/`host` +
  `x-forwarded-proto` (mirroring `lib/card-request.ts`) and shows a
  copy-paste `<img>` snippet for blog/portfolio embeds, or a disabled
  state when `NETPRO_DISABLE_VIEWS=true`.
- **Card HTML opt-in** (`packages/core/src/card/html.ts` +
  `apps/cli/src/commands/card.ts`) — `netpro card --pixel-url <origin>`
  renders an `<img>` view beacon in HTML cards and extends the card CSP
  with `img-src <origin>`; the URL must be absolute http(s)
  (`RangeError` otherwise) and the vCard command refuses the flag
  (`--pixel-url only applies to HTML cards.`).

## Notes / decisions vs the plan

- **The `/card` page splits by capability instead of firing pixel + JS
  simultaneously.** The plan's letter is "a 1×1 pixel for non-JS, and a
  JS fallback"; but firing both in JS browsers would write two rows for
  one visit (or, with dedup on, drop the *second* beacon — the JS one —
  and lose `durationMs`). One row per visit, with duration when the
  browser can measure it, is the only reading that keeps the dedup
  guarantees the plan also requires.
- **`viewToken` rides in the POST body for the JS beacon.** `sendBeacon`
  to a pixel URL would work, but the POST endpoint is the browser's only
  JSON carrier; keeping the token in the body means the `<img>` noscript
  path is the only place a token appears in a URL — and only for non-JS
  clients, where there is nothing to intercept it.
- **429 still serves the GIF.** A rate-limited beacon must be
  indistinguishable from a successful one to the visitor (and to any
  cache), per the plan's "beacons never break the page".
- **In-memory rate limit is per process.** The plan specifies no Redis;
  multi-instance serverless deploys apply the limit per instance.
  Documented in the deployment reference.
- **No migration, no new runtime dependencies.** `profile_views`
  (migration `0006`, Phase 1) is the consumer as designed; the pipeline is
  `node:crypto`, `fetch`, and `sendBeacon` on top of Drizzle.
