# v2.0 Phase 5 — Skills gap analyzer — progress & verification

Implements Phase 5 of the [v2.0 plan](2026-09-07-v2.0-implementation-plan.md).
The phase had a head start — PR #22 landed migration `0005`, the schema
columns and a first sketch of the core/CLI/web surfaces — but the sketch had
no evidence, no persistence path, no AI option, no tests worth the name and a
`skills` command that was never registered. This pass replaces the sketch
with the full feature under the plan's rules, keeping the migration exactly
as shipped.

The governing idea throughout: **a skill is a claim, and every claim has to
point at the words that justify it.** The analyzer never guesses, never
infers from a company name, and shows its evidence on every surface.

## What shipped

### Migration `0005_skills` (both dialects, additive — unchanged from PR #22)

`ALTER TABLE contacts ADD COLUMN skills text` (nullable, no default). SQLite
models it as a Drizzle `json`-mode column, Postgres as plain `text`; both
hold the same JSON array of canonical taxonomy names, so the shared reader is
one `JSON.parse`. Nothing else in the schema moved: the evidence goes into
the existing `enrichments` table, exactly as the plan's "both" recommendation
asked.

### Core: `packages/core/src/skills/`

- **`taxonomy.ts`** — 101 skills in 12 categories (`languages`, `frontend`,
  `backend`, `mobile`, `cloud`, `data`, `ai`, `security`, `product`,
  `design`, `business`, `leadership`), each with aliases (`k8s` →
  `kubernetes`, `data engineer` → `data engineering`, `pyspark` → `spark`,
  `cofounder`/`co-founder` → `founder`). `normalizeMatchText` lower-cases and
  turns separators into spaces while keeping `+ # . &` inside a token, so
  `c++`, `c#`, `node.js`, `.net` and `fp&a` survive whole; aliases are
  normalised with the same function, which is why `ci/cd` and `ci cd` need no
  second spelling. Seven bare names are flagged `ambiguousName` (`go`,
  `excel`, `spark`, `swift`, `growth`, `operations`, `strategy`): they only
  match in prose through an unambiguous alias (`golang`, `microsoft excel`,
  `apache spark`, `swiftui`, `growth marketing`…) but count as an explicit
  tag, custom-field value or `--skills` entry — "Go-to-market" in a headline
  is not a Go programmer, a `go` tag is. The whole table is data; an integrity
  test asserts unique names and that no alias maps to two skills (it caught a
  duplicate `kafka` during this pass).
- **`extract.ts`** — `extractSkills(contact)`: whole-token, longest-match
  n-gram scan over headline, role, department, industry, tags, custom fields
  and notes (in that order; a token that begins no alias costs one Map
  lookup). Every hit records `{ field, matched, snippet }`; confidence is 1
  for explicit and structured fields, 0.9 for notes-only, 0.8 for a
  previously stored verdict (`source: 'stored'` — the owner's claim, never
  outranking fresh evidence and never hiding that the text no longer
  supports it) and 0.6 for an AI pick. "react native" never also yields
  "react". Text is capped at 20k chars per field. `extractSkillsWithAi`
  builds a taxonomy-only prompt (temperature 0, 300 tokens, ≤ 25 picks),
  parses a JSON array *or* a comma list, drops anything outside the taxonomy,
  and on any provider failure returns the heuristic result with `aiError` set.
- **`gap.ts`** — `parseTarget({ role, description, skills })` scans role and
  description as prose *and* value-by-value on comma/newline/bullet-separated
  text (people paste requirement lists), matches explicit `skills`
  permissively and reports `unrecognized` names. `gapAnalysis(target,
  candidateSkills)` → `{ required, present, partial, partialVia, missing,
  matchScore }` with `matchScore = (present + ½·partial) / required` at 2 dp;
  partial coverage is a small, legible rule table (`kubernetes` via `docker`,
  `sql` via `postgresql`/`mysql`/`snowflake`/`dbt`/`spark`, `typescript` ⇄
  `javascript`, `full-stack` via frontend + backend…) and the rule that fired
  is always returned. `analyzeNetworkGaps(target, contacts)` runs extraction
  once per contact and returns per-skill coverage (holders strongest-tie
  first, capped `perSkill`), `gaps` (skills nobody covers even partially),
  `coveredCount` and ranked `candidates` (match score, then relationship,
  then name; zero-score contacts dropped). `networkSkillCounts` is the
  network skill map with a `limit` and a `distinct` total.
- **`repository.ts`** — raw ANSI SQL reads through the search indexer's
  `rawAll` (one query text for both dialects; building a Drizzle select map
  over the `SqliteConn | PgConn` union does not typecheck), Drizzle writes
  inside dialect branches. `writeExtractedSkills` stores the verdict on the
  contact and the full extraction in `enrichments` (`provider =
  skills_heuristic | skills_ai`, `data_type = skills`, one row per contact
  per extractor, replaced on re-run), and bumps `updated_at` + writes a
  `skills.extracted` activity-log row **only when the verdict changes**.
  `getSkillsProfile` (stored, current, `unsupported`, evidence rows) is what
  both the CLI and the contact page render. `extractSkillsBatch` is the one
  producer (`{ scanned, updated, unchanged, withSkills, mode, aiErrors,
  dryRun, changes, indexed? }`); after a real run it refreshes the keyword
  search index for changed contacts — best-effort, keyword-only, never an
  embedding call, same posture as import. `skillsStatus` is the counts line.
  Loads cap at 10,000 contacts.

### Search (optional Phase 4 tie-in, done)

`contacts.skills` is part of the indexed search document (after tags, before
notes), so `netpro search kubernetes --mode keyword` finds a contact whose only
Kubernetes signal is the derived verdict. A new `skills` filter
(`SearchContactsOptions.skills`, `netpro search --skills python,k8s`,
`GET /api/search?skills=`) requires every listed skill; it is a
quoted-substring test on the JSON text (`LIKE '%"kubernetes"%'`), which is
exact because canonical names never contain quotes and portable because it
uses no JSON operators. A name outside the taxonomy compiles to `1 = 0` — a
typo narrows to zero rather than silently widening. The stale "contacts carry
no skills column" note in `search/types.ts` is gone.

### CLI (16th command)

`netpro skills <contact>` (stored + current skills with field/snippet
evidence, "stored but not supported" flagged, last extraction), `netpro skills
gap --role --description --skills [--contact] [--limit] [--json]`, `netpro
skills extract [--mode heuristic|ai] [--contact] [--limit] [--dry-run]
[--provider] [--json]`, `netpro skills status`. Contact selectors go through
`resolveContactRef`. `--mode ai` reuses the outreach credentials (keychain
then env) and fails **before** opening a transaction when no key is
configured. `netpro search --skills` as above.

### Web

- `/skills` — GET-form page (role / description / explicit skills). With a
  target: required skills (+ ignored names), the coverage table (category,
  count, partial count, holders linking to `/contacts/[id]`), the gaps, and
  ranked matches with has/partial/missing and a **Find a warm intro** link
  into `/graph`. Without one: the network skill map (top 40, each a filter
  link). A client `ExtractPanel` posts to the extract API with a "Preview
  changes" dry-run and an explicit **also run the AI pass** checkbox.
  Hand-typed pathological URLs render an alert, never a 500.
- `/contacts/[id]` — skill tags (union of stored and current), each titled
  with its category and evidence and linking to `/skills?skills=`; a stored
  skill the current text no longer supports is drawn dashed with a `?`; a
  "Why these skills?" disclosure lists every match with field and snippet.
- **Skills** nav link; `/skills` added to the proxy's `PROTECTED_ROUTES`.
- `GET /api/skills/gap?role=&description=&skills=&contact=&limit=&perSkill=`
  — owner-only; `contact` resolves through the shared resolver (unknown →
  404, ambiguous → 400); targets bounded at 10k chars (400 beyond).
- `GET|POST /api/skills/extract` — status counts / `{ mode?, contact?,
  dryRun?, limit?, provider? }`; JSON body bounded and content-type checked
  via `readCrmJson`; AI keys come from the server environment only and a
  missing key answers `500 ai_not_configured` before any write.

## Decisions & notes

- **AI extraction is default-off — plan open question #3 answered.** The
  heuristic pass is the product: offline, deterministic, and every skill
  carries the words that produced it. `--mode ai` / `{ mode: 'ai' }` is
  opt-in per run, the model may only choose from the taxonomy, and a failed
  call degrades to the heuristic result with the failure reported rather than
  hidden. There is no `SKILLS_AI=…` env switch on purpose: turning the model
  on should be a decision made at the moment of the run, by the person
  paying for it.
- **Verdict on the contact, evidence in `enrichments`** — the plan's "both".
  The verdict is what search filters and the gap maths read (cheap, one
  column); the evidence row is what the contact page and `netpro skills
  <contact>` explain from. One row per contact per extractor keeps the table
  from growing with re-runs.
- **A stored skill is a claim, not evidence.** `getSkillsProfile` reports
  `unsupported` (stored but not derivable from the current text); the contact
  page marks it, the gap analysis still counts it (the owner may know
  something the text does not), and the next `extract` drops it — with the
  change listed in the summary so nothing disappears silently.
- **`updated_at` only moves when the verdict changes.** Extraction is a
  derived write; it must not make every contact look freshly edited, and it
  must not spam the activity log on a nightly re-run.
- **Bounded taxonomy, not a free vocabulary.** ~100 skills is small enough to
  read in one sitting and large enough for a professional network; adding a
  skill is a one-line data change plus the integrity test. Ambiguity is
  handled as data too (`ambiguousName`) rather than as special cases in the
  scanner.
- **Unknown skill names narrow, never widen.** In `--skills`, `?skills=` and
  the target parser an unrecognised name is reported (`unrecognized`) or
  compiles to a no-match condition. A typo that quietly returned "everyone"
  would be the worst possible failure for a filter.
- **`SKILL_CONTACT_LIMIT = 10,000`, `MAX_EXTRACT_CHARS = 20,000`,
  `MAX_TARGET_CHARS = 10,000`, `AI_MAX_SKILLS = 25`** are the guard rails; all
  are exported constants with tests.
- Deferred, per the plan and untouched here: a skill graph / adjacent-skill
  recommendations beyond the small `PARTIAL_COVERAGE` table, skill
  verification by the contact, a public by-request skills endpoint, and
  manual editing of a contact's skills in the UI (the verdict is derived; an
  owner override belongs with the contact-edit surface when that exists).
