# v2.5 Phase 4 — Content tracker data model & provider interface — progress

Implemented against
[docs/superpowers/plans/2026-09-08-v2.5-implementation-plan.md](./2026-09-08-v2.5-implementation-plan.md).

## What shipped

The blueprint's second v2.5 feature now has its foundation: tables,
identity, import, snapshots, and the provider seam. No CLI/web surface —
`netpro content`, `/content` and `/api/content` arrive in Phase 5 on top of
these exact functions.

- **Migration `0007` (SQLite + Postgres, additive):** `content_items`
  (`url` as given, `url_norm` UNIQUE, `title`, `platform`, nullable `type` /
  `published_at` / `author` / `tags` / `summary`, `source` default
  `manual`), `content_metrics` (FK `content_id` cascade, `fetched_at`,
  `source`, nullable views/likes/comments/shares/bookmarks, nullable
  `raw_payload`), and `content_mentions` (`content_id`, `contact_id`,
  `context`, composite PK, both FKs cascade). Journals updated on both
  dialects (idx 7).
- **Six indexes:** `idx_content_items_platform`,
  `idx_content_items_published` (`published_at DESC`),
  `idx_content_metrics_item_time` (`(content_id, fetched_at DESC)`),
  `idx_content_metrics_time` (`fetched_at DESC`),
  `idx_content_mentions_contact`, `idx_content_mentions_content`.
- **Core `@netpro/core/content` module** (`packages/core/src/content/`,
  exported as `core.content`):
  - `types.ts` — `CONTENT_PLATFORMS` (the plan's nine, `x` and `twitter`
    distinct), `CONTENT_TYPES`, `CONTENT_SOURCES`, `METRIC_SOURCES`,
    `CONTENT_LIMITS`, `ContentError` (house codes plus `not_configured`
    for disabled providers), and the `ContentItem` / `ContentMetric` /
    `ContentMention` / `ContentItemSummary` / `ContentOverview` shapes.
  - `urls.ts` — the one canonicalizer. Absolute http(s) only;
    lower-cased host; default ports, fragments and trailing slashes
    dropped; `utm_*` + ad-click params stripped with survivors sorted
    (scheme stays identity — http and https are different deployments).
    Plus host-suffix `detectPlatform` and strict `parsePlatform`.
  - `parse.ts` — `parseContentCsv` (papaparse, alias-tolerant headers,
    per-row errors/warnings, 1,000-row cap), `parseFeedXml` (RSS 2.0 +
    Atom with no new dependency: CDATA, entities incl. numeric, alternate
    links, categories→tags, HTML-stripped summaries, RFC 2822 dates),
    `parseContentDate` (strict ISO via the event reader, then RFC 2822),
    and `fetchFeedText` — the module's only network call, with injectable
    fetch, a timeout, and pre/post-read byte caps.
  - `providers.ts` — `ContentProvider` (`id`, `name`, `enabled`,
    `canFetch`, optional `fetchMetrics`/`parse`): `manual` + `rss` built
    in, `devto`/`twitter`/`github` as disabled stubs whose
    `fetchMetrics` throws `not_configured` naming the enabling key.
    `resolveContentProviders` routes most-specific-first with `manual`
    as the eternal fallback; `canFetchMetrics` /
    `resolveMetricsProvider` answer whether numbers are fetchable _now_.
  - `repository.ts` — strict `addContentItem` vs idempotent
    `upsertContentItem` (the UNIQUE constraint is the backstop for a
    concurrent double-insert); filtered/paginated `listContentItems`;
    id-or-URL `resolveContentRef`; `getContentItem` detail payload;
    explicit-children-first `deleteContentItem`; append-only
    `recordMetrics`; oldest-first `getContentMetricsSeries`; three-query
    `getContentOverview` (totals, top 5, platform breakdown — no per-item
    round-trips); `importContent` (CSV/feed/pre-parsed rows, overrides,
    dry-run); idempotent mentions; `contentStatus`. Reads are portable
    raw SQL; writes go through Drizzle with JSON stringified on Postgres
    only (the `contacts.tags` trade-off).
- **Schema mirrors** in `schema.sqlite.ts` / `schema.pg.ts`, and
  `core/src/index.test.ts` asserts the module boundary.
- **CI:** the postgres job now runs
  `src/content/postgres.integration.test.ts`, next to the search/events
  suites.

## Notes / decisions vs the plan

- **`url_norm` is an extra column.** The plan lists `url (unique)`; the
  implementation keeps `url` as given (display + working link) and keys
  dedupe, idempotency and the UNIQUE constraint on `url_norm`. A
  re-import with different tracking junk still dedupes, and the original
  link still renders.
- **Undated items and windows.** `days` filters exclude undated items
  (they cannot be placed), and `getContentOverview` states the skip as
  `excludedUndated` rather than silently shrinking the total.
- **Strict platform, lenient type/date.** An unknown platform is a row
  error (it drives breakdowns); an unknown type or unparseable date is a
  warning + null (advisory, and feeds are full of both). Events reject
  bad dates because the date defines the event; a post is still a post.
- **A snapshot needs ≥1 metric.** An all-null row measures nothing, so
  `recordMetrics` rejects it — while any single reported field (even
  alongside nulls) is a valid snapshot. `null` stays "unreported" in
  every sum.
- **Provider `parse` is sync and returns rows + warnings**, not the
  plan's `Promise<ContentItem[]>`: parsing cannot mint DB rows (no ids,
  no timestamps), and feed parsing is pure text work.
- **Re-imports never overwrite.** `upsertContentItem` returns the
  existing row unchanged — the title the owner edited since the import
  wins over the file.
- **Migration-test hardening (incidental).** The 0005/0006 upgrade
  fixtures asserted journal-relative lengths, so adding 0007 broke them
  — and the 0006 tag-prefix filter leaked 0007 into its own pre-upgrade
  fixture. All three fixtures now filter by idx and assert explicit idx
  arrays, so the next migration cannot break them again.
- No new runtime dependencies (`papaparse` was already present; the feed
  reader is hand-rolled, the fetch is plain `fetch`).
