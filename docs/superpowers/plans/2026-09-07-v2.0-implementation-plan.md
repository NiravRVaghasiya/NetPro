# NetPro v2.0 Implementation Plan — "The Strategist"

> Product milestone per the [project
> blueprint](../../../NetPro%20%E2%80%94%20Blueprint.md): **v2.0 · Month 4–6 ·
> Warm intro pathfinder, Event matcher, Skills gap analyzer · 2–3 devs,
> 8 weeks.** This plan turns the blueprint's graph-native v2 features into
> implementable, testable phases that build on the v1.5 foundations (CRM,
> campaigns, scoring, owner-only auth, dual-dialect Drizzle, CI with live
> Postgres).
>
> Every phase follows the house pattern: shared business logic in
> `packages/core` (pure, testable, dual-dialect), thin CLI + web surfaces,
> additive Drizzle migrations for both dialects, adversarial tests on the
> migrated fixture, CI gates green (lint, typecheck, 592+ tests, build, live
> Postgres, Docker), and verification recorded in the phase plan.

## What already exists (v1.5 foundation)

- `edges` table exists in both dialects (`packages/db/src/schema.{pg,sqlite}.ts`)
  — **but has no producer, no indexes, and no data**. The analytics module
  clusters by _attribute_ (normalized company), not graph structure.
- Search is the portable v1 engine: case-insensitive substring + facets in
  ANSI SQL, identical on SQLite/Postgres. Hybrid engine is deferred.
- CRM logging (`logInteraction`) and campaign sends already write real
  interactions; relationship scoring is recomputed per write.
- `profile_views` and `search_index` tables exist, both **unused/producer-less**.
- Auth is single-owner (Phase 5 boundary); no scheduler (no cron/queue infra).

## The four v2.0 features (blueprint scope)

1. **Graph analytics + warm-intro pathfinder** — Louvain community detection,
   centrality scoring, shortest warm-intro paths over the `edges` table.
2. **Hybrid search** — SQLite FTS5 + pgvector embeddings, RRF re-ranking.
3. **Skills gap analyzer** — compare target role/description against a
   contact's extracted skills; list gaps.
4. **Event matcher** — conference/event discovery with attendee matching
   against your network.

## Phase 1 — Edge provenance: graph data model users can trust

**Problem.** The `edges` table has existed since the scaffold but nothing
populates it; analytics documented in the blueprint (communities, centrality,
warm intros) has no input. v2.0 cannot build graph features on an empty table.

**Goal.** Make `edges` trustworthy: auditable provenance, deduped and
undoable, with explicit user confirmation — NetPro never silently infers that
two of _your_ contacts know each other.

### Data model (additive migrations, both dialects)

- Keep `edges(id, source_id, target_id, relation, strength, context,
bidirectional, discovered_at, updated_at)`.
- `relation` gains **whitelisted provenance vocabulary** — reuse house style:
  `mutual_network` (deduced from shared LinkedIn connection data),
  `colleague`, `met_at_event`, `mutual_intro`, `manual`. (Extend rather than
  replace; old rows default to `manual`.)
- Add `source` (text, not null) — `linkedin_csv` | `manual` | `event_import`
  | `skype_migrate`.
- Add `confidence` (real 0–1, default 1) — inferred edges carry < 1 so
  analytics can weight them.
- Add **`edges` indexes (migration `0003`)**:
  - `edges(source_id)`, `edges(target_id)` — neighborhood lookups for BFS.
  - `edges(relation)`, `edges(confidence)` — filtering/weighting in analytics.
- Add `events` + `event_attendees` tables (Phase 6 needs them; ship schema here
  so Phase 6 is logic-only):
  - `events(id, name, location, starts_at, ends_at, source, created_at)`.
  - `event_attendees(event_id, contact_id, role, attended, discovered_at)`.
- Revise `profile_views` to record viewer info (name/headline/organization)
  for the v2.5 profile-viewer analytics; not v2.0 scope, keep as is.

### Producers (so the table is actually usable)

- **CSV import (`netpro import`)** — when a file includes a
  "Mutual connections / Shared connections" section (LinkedIn export), also
  emit candidate edges `mutual_network` with `confidence` derived from
  reported mutuals; surface them for confirmation rather than auto-inserting.
- **`netpro edge` CLI (new command)** — `add <from> <to> [--relation] [--at]`,
  `list [--contact] [--relation]`, `rm <edgeId>`, `import` (from a two-column
  CSV), `merge` (dedupe symmetric pairs). Selectors reuse `resolveContactRef`.
- **`/api/edges` + `/edges` page** — owner-only list/search of graph links,
  add/remove a manual link, confirm or reject inferred ones.
- **Event attendance** — a contact form on the contacts detail page
  ("also met at…") that creates an `event_attendees` row + `met_at_event` edge.

### Out of scope / deferred

- Automatic edge inference from email headers or LinkedIn scraping (privacy;
  the blueprint's "cross-reference GitHub, company data" stays enrichment
  only). Auto-discovery = opt-in confirmation flow only.
- Multi-user / shared graphs (Phase 3's RLS).

### Verification

- Migration test: fresh SQLite + live Postgres apply `0003` idempotently
  (advisory lock path).
- Core tests: edge CRUD + dedupe (symmetric pair collapses), provenance
  whitelist, confidence weighting, adversarial (self-edge, duplicate,
  soft-deleted contact, unknown relation rejected).
- CLI tests: `edge` command parse/exec.
- Web tests: `/api/edges` 401/400/404 mapping + render tests.
- Capture **before/after** edge counts on the demo fixture.

## Phase 2 — Graph analytics engine (communities, centrality, paths)

**Problem.** `packages/core/analytics` clusters by company attribute; the
blueprint wants graph-native community detection, centrality, and shortest
paths over `edges`.

**Goal.** `packages/core/graph` + wiring into `analytics` — algorithmically
honest at single-owner scale (hundreds–thousands of nodes, no heavyweight
graph DB).

### Core module (`packages/core/src/graph`)

- **Adjacency build** — single indexed pass over `edges` → in-memory adjacency
  map (portable: same code for both dialects since analytics already reads
  whole tables at v1 scale).
- **Louvain community detection** — implement in pure TS (no new dependency
  just for one algorithm), or vendor `graphology-communities-louvain` as a
  small, testable dep. Decision documented: pure JS keeps the "no network / no
  heavyweight deps" posture; a vendored algorithm must be pinned and
  measured. `getCommunities()` → `{ communityId, members[], modularity }`.
- **Centrality** — degree + betweenness (Brandes, unweighted for v2; weighted
  by `strength × confidence` later). `getCentrality()` → per-contact score.
- **Warm-intro pathfinder** — BFS on the adjacency map honoring
  `maxDepth` (default 4, blueprint's reference) and
  `relation`/`confidence` filters; returns the shortest path array of contact
  ids + intermediaries with their scores/relation labels. Bidirectional edges
  traversed both ways; `bidirectional=false` edges one-way.
- **`getNetworkGraph()`** — merged view for `/dashboard`: community list with
  members, top-centrality contacts, avg path length, connected-components
  count, the warm-intro candidate pairs (high-target contact, no direct edge,
  exists path).
  > Note: this supersedes the "attribute-based" note in README — clustering
  > becomes graph-native once edges have producers.

### Integration

- `analytics/index.ts` gains `graph` entry points; `netpro analyze --graph`
  summarizes communities/centrality/paths.
- `GET /api/analytics` extends with the graph payload behind the owner
  boundary; `/dashboard` adds a "Network graph" strip (communities by size)
  when edges exist, empty-state otherwise.

### Testing strategy

- Small hand-built graphs with **known answers**: butterfly/star/ring,
  modularity computed by hand; betweenness on the vintage 4-node examples.
- Path tests: direct, 2-hop, no-path, max-depth cutoff, relation-filtered,
  one-way edge, self-edge ignored.
- Performance budget test: 3,000 nodes / 8,000 edges under the analytics
  budget (< 500 ms dashboard load; measure and record).

### Out of scope

- Persistent graph DB (Neo4j), streaming/online updates, temporal
  (edge-added-at) analytics, visualization beyond a simple static server-render
  (no v2 scope for a full graph canvas; a list/table of communities +
  paths is the v2 deliverable).

## Phase 3 — Warm-intro pathfinder surface (CLI + web + API)

**Goal.** Make the pathfinder usable end-to-end.

- CLI: `netpro path <target> [--from <contact>] [--max-depth n]
[--relation r] [--json]` → prints the intermediary chain with each hop's
  relationship score/recency and a suggested ask for the next hop
  (reusing `packages/core/ai` compose, **draft-only** — the blueprint says
  "AI-composed outreach", not auto-send).
- Web: `/graph` page — pick a target (search select), see the warm-intro path
  chain, one-click "draft intro request" pre-fills the outreach composer.
  `/graph/<contactId>` shows centrality + communities for that person.
- API: `GET /api/graph/paths?target=&from=&depth=`, `GET /api/graph/overview`.
- README + getting-started updates; analytics scope note rewritten (graph
  native now).

**Verification.** API tests (owner boundary, depth cap 1–6, unknown target 404);
page render tests; CLI exec tests.

**Deferred within v2.** Auto-suggesting _which_ intermediary to use (score the
chain by relationship strength) — ship the k-shortest candidate list, rank by
score in a UI, let the human choose.

## Phase 4 — Hybrid search (FTS5 + pgvector with RRF re-ranking)

**Problem.** Current search is substring-only; the blueprint specifies an FTS +
vector hybrid with RRF.

**Goal.** One `searchContacts` entry point, dialected internally: SQLite FTS5 +
Postgres pgvector, keyword and semantic arms merged via Reciprocal Rank
Fusion; degrade gracefully with no embeddings configured.

### Architecture

- **Keyword arm** — SQLite `FTS5` virtual table (`contacts_fts`) + Postgres
  `tsvector` generated/expression index; same indexed fields as v1 search
  (name, headline, company, role, location, industry, notes, tags). Migration
  `0004` creates them + `search_index` gets a real producer (the v1 portable
  search keeps working; this is additive).
- **Semantic arm** — embeddings produced **only when configured**: existing
  OpenAI-compatible `packages/core/ai` provider surface is reused (the
  `compose` module already speaks fetch-only HTTP to OpenAI-compatible
  endpoints). New env: `EMBEDDINGS_PROVIDER=openai` (or `disabled`),
  `EMBEDDINGS_API_KEY`, `EMBEDDINGS_MODEL`, optional `EMBEDDINGS_BASE_URL`.
  Postgres: `vector` column on `search_index` (pgvector extension, optional
  `CREATE EXTENSION IF NOT EXISTS` gated by config). SQLite: **no vector
  support** (no extension in the app's runtime story) — semantic arm skipped
  on SQLite, keyword-only remains.

### RRF + correctness

- `reciprocalRankFusion(rankedLists, k=60)` — pure function, unit-tested
  against hand-computed merges to keep dialect parity.
- Contact-level dedupe after merge (both arms keyed by contact id).
- **Deterministic tests**: seeded fake embedding function (never calls
  network), injected feature flag; filter/sort/pagination parity with v1
  behaviour tested side-by-side on the same fixture.
- **No config = no behavior change**: default `EMBEDDINGS_PROVIDER=disabled`
  → existing portable search is untouched; hybrid only opt-in on Postgres.

### Surface

- CLI `netpro search` gains `--semantic` (opt-in) behind the same flags.
- Web `/search` gets a semantic toggle (hidden when not configured) and a
  "results powered by FTS+vector" badge; API `GET /api/search?mode=hybrid`.

### Verification

- Migrations route test on both dialects (FTS5 syntax differs from pgvector →
  keep both SQL files as separate additive migrations).
- Core: RRF math, arm merge, empty-arm fallback, filter parity, embedding
  provider mocked (no HTTP), failure fallback (embeddings API down → keyword
  results, no error).
- Perf: index + upsert path on a 1k-contact import, `searchContacts` under
  budget.

### Deferred

- Local embeddings (ONNX/Transformers.js), quantized vector search, BM25
  tuning, multi-language tokenizers, typo tolerance beyond trigram FTS.

## Phase 5 — Skills gap analyzer

**Goal.** Given a target role/description, list the skills your network (or a
selected contact) has vs. what the target needs, with actionable gaps.

### Data

- New `skills` provider in the enrichment pipeline — **pure extraction** from
  existing `headline`/`notes`/`customFields` + optional LLM extraction
  (reuses `packages/core/ai`, BYO-key, offline-safe: no key → heuristic
  extraction only).
- Store derived skills in `contacts` via a new `skills` JSON column
  (migration `0005`, both dialects) or `enrichments` typed rows
  (`provider='skills_heuristic'|'skills_ai'`, `data_type='skills'`); decision
  documented: denormalized `contacts.skills` for cheap search/filter, raw
  payload in `enrichments` for provenance. **Recommendation: both** — keep the
  verdict on the contact, the evidence in enrichments.

### Core `packages/core/skills`

- `extractSkills(contact, {mode})` — heuristics (title/headline/notes
  keyword lists) + optional AI pass.
- `gapAnalysis(target: {role, skills?, description?}, candidateSkills) →
{present, missing, partial, matchScore}` — bounded vocabulary from an
  embedded skill taxonomy (no new dep / no network) + AI fallback when
  configured.
- `analyzeNetworkGaps(target)` — aggregate across contacts: most common
  missing skills, who fills each gap, contact count per skill.

### Surface

- CLI `netpro skills <contact>` / `netpro skills gap --role "Staff Engineer"
--description "…"` (analyzes your network) / `--contact` for one person.
- Web `/skills` — target-role form + gap table (missing skill → contacts that
  have it), per-contact skill tags on the contact detail page.
- API `GET /api/skills/gap?role=&description=` (owner-only).

### Verification

- Extraction unit tests (whitelist + heuristic, LLM mocked), gap-algorithm
  vectors, network-aggregate tests, route/page tests, migration tests.

### Deferred

- Skill graph / adjacent-skill recommendations, skill verification by the
  contact (v2.5 profile-analytics territory), public by-request skills
  endpoint.

## Phase 6 — Event matcher

**Goal.** Conference/event discovery with attendee matching against your
network: "who in my network is going / attended X, and who do I know that I
could go with / be introduced to."

### Data + ingestion

- `events` + `event_attendees` (schema shipped in Phase 1).
- **Import path**: `netpro events import <csv>` (name, location, dates,
  optional attendee emails) — parses and matches attendee emails against
  contacts (dedupe by normalized email; ambiguous → list), creates
  `met_at_event` edges for matched attendees where confirmed.
- **Optional discovery API** (deferred within v2 unless cheap): a stub
  `EventMatcherProvider` interface with `disabled` default — callers can add
  Luma/Eventbrite later without touching the core.

### Core `packages/core/events`

- `importEvents`, `matchAttendees(event, contacts)` (email/name fuzzy,
  confidence), `listEvents`, `getEvent(id)` (attendees + network overlap),
  `recommendEvents` (by location + industry + company of your contacts:
  "events where 5 of your industry peers are attending/attended").
- Conflict rules: attendee already linked → no duplicate edge; unmatched
  attendee email → `unmatched` bucket for manual linking.

### Surface

- CLI `netpro events list|import|show <id>|match <id>`.
- Web `/events` — list, import (CSV upload), detail with attendee
  intersection ("5 in your network"), and per-contact "also at" linking.
- API `GET/POST /api/events`, `GET /api/events/[id]`, `POST
/api/events/[id]/match`.

### Verification

- Core: import parsing (CSV variants), matching dedupe/confidence,
  recommend logic, edge creation side effects; route/page/CLI tests; migration
  tests.

### Deferred

- Calendar sync, RSVP tracking, live discovery providers, event-specific
  analytics.

## Cross-cutting notes

### House rules every phase must follow

- **Dual dialect**: every migration ships `postgres/` + `sqlite/` additive
  SQL + snapshot + `_journal` update; no dialect-only features without
  documented degradation (see hybrid search).
- **No new runtime deps unless justified** — the repo's posture is "pure TS +
  fetch, offline tests". If an algorithm needs a library, the phase plan must
  justify, pin, and measure it (test client-side, never in prod surface).
- **Selectors shared** — `resolveContactRef` stays the one resolver.
- **Owner-only everywhere** — new routes inherit the proxy boundary; public
  surfaces (card) never read contact data.
- **Adversarial tests** — validation caps, unknown enums, backdated/future
  timestamps, soft-deleted contacts, ambiguous selectors, idempotency.
- **No secrets in web client** — AI/embeddings keys stay server-env only;
  BYO-key only in the CLI keychain (Phase 4 decision, unchanged).

### Risks

| Risk                                        | Mitigation                                                                                                                                                                                          |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `edges` stays empty (users don't add edges) | CSV mutuals + `met_at_event` producers make graph data a side effect of import + CRM, with confirmation UI; graph features show an onboarding empty-state with a 2-step "add your first edges" path |
| pgvector not available on a host            | Feature-gate: `EMBEDDINGS_PROVIDER`; health endpoint reports `search.mode: portable                                                                                                                 | hybrid`; no hard dependency |
| FTS5 vs pgvector SQL drift                  | Migration + route tests on both dialects; RRF is dialect-agnostic pure JS                                                                                                                           |
| Louvain/betweenness perf on big networks    | Budget test + static server-render only; documented cap (data < 50k edges), otherwise degrade to attribute clusters with a notice                                                                   |
| AI skills extraction cost / BYO key absent  | Heuristic fallback; extraction runs offline by default, AI only on explicit `--mode ai` / settings toggle                                                                                           |
| Event matching over-links people            | Confidence + confirmation flow; edges removable; nothing auto-published                                                                                                                             |
| Release slip                                | Phases 1, 4, 6 are independently shippable; prioritize 1 → 2 → 3 (graph) and 4 (search) if schedule tight                                                                                           |

### Suggested branch / PR pattern

Same as v1.0–v1.5: one branch per phase (`arena/<commit>-v2.0-phaseN-…`),
each phase its own PR referencing the phase plan, merge to `master` with CI
green; cut `v2.0.0` only after Phase 7's full gate.

## Suggested order of implementation (quick start)

1. **Phase 1** (edge provenance) — unblocks everything graph-shaped.
2. **Phase 4** (hybrid search) — independent, high value, can run parallel.
3. **Phase 2** (analytics engine) once edges have data.
4. **Phase 3** (pathfinder surface) on top of Phase 2.
5. **Phases 5–6** (skills, events) — independent, on Phase 1's schema.
6. **Phase 7** (release).
