# v2.5 Phase 1 — Profile views data model & privacy hardening — progress

Implemented against
[docs/superpowers/plans/2026-09-08-v2.5-implementation-plan.md](./2026-09-08-v2.5-implementation-plan.md).

## What shipped

- **Migration `0006` (SQLite + Postgres, additive):** `profile_views` gains
  `viewer_fingerprint`, `is_bot` / `is_owner_view` (NOT NULL, default false —
  so analytics filters can rely on the flags without a null dance),
  `session_id`, `duration_ms`, `utm_source` / `utm_medium` / `utm_campaign`,
  and `viewed_card_id`. Journals updated on both dialects (idx 6).
- **Five indexes:** `idx_profile_views_time` (`viewed_at DESC`),
  `idx_profile_views_resolved` (partial, `WHERE resolved_contact IS NOT
  NULL`), `idx_profile_views_page`, `idx_profile_views_fingerprint_time`
  (`(viewer_fingerprint, viewed_at)`), and `idx_profile_views_is_bot`
  (partial over `viewed_at WHERE is_bot = false` — the plan named the
  predicate but not the column; the analytics fast path is time-bounded
  non-bot scans, so `viewed_at` is the indexed column).
- **Legacy raw IPs are blanked by the migration itself** (`UPDATE
  profile_views SET viewer_ip = NULL`). The table had no producer before
  0006, but an in-place upgrade can never hash a stored IP without the
  operator's salt — so the migration enforces the privacy promise instead of
  trusting that nothing was ever written. Tested on an upgrade fixture.
- **Core `@netpro/core/views` module** (`packages/core/src/views/`), exported
  as `core.views`:
  - `privacy.ts` — daily-salted HMAC-SHA256 hashing. `hashViewerIp` stores
    `HMAC-SHA256(dailySalt, ip + UA)` truncated to 16 hex chars;
    `hashViewerFingerprint` mixes in accept-language so the 24h dedup value
    is a different digest than the IP hash. Salt rotates per UTC day
    (`dailyViewSalt`), so no stored hash is correlatable across days.
  - `bots.ts` — vendored deny-list (~45 markers in 8 documented groups:
    search engines, social preview fetchers, AI crawlers, SEO crawlers,
    archivers, monitors) plus a token backstop that catches glue-named
    crawlers (`FooBot/1.0`, `MJ12bot/1.0`) without flagging browsers or
    plain English. Generic HTTP clients (`curl`, `python-requests`) are
    deliberately not "bots".
  - `owner.ts` — owner-view labeling. `shouldMarkOwnerView` returns true on
    an authenticated owner session, or when the daily-salted IP hash matches
    a view already confirmed `is_owner_view` within a 24h lookback
    (`recentOwnerViewIpHashes`). Labeling only — never blocks, never
    deletes; salt rotation makes the heuristic same-day by construction.
  - `retention.ts` — `purgeExpiredProfileViews` deletes rows older than 90
    days (default; configurable, validated), idempotent, returning the
    deleted count for the single per-run `activity_log` row the Phase 6
    purge job will write.
- **Schema mirrors** in `schema.sqlite.ts` / `schema.pg.ts`, and db tests for
  both dialects; `core/src/index.test.ts` asserts the module boundary.

## Notes / decisions vs the plan

- The time index is `viewed_at DESC` in the migration SQL; the Drizzle schema
  declarations keep the plain column form (the SQLite index builder cannot
  express `DESC`), which only matters if someone regenerates migrations from
  the schema — the applied SQL is the source of truth.
- Plan Phase 1 lists "owner view detection via signed token or same-IP
  heuristic"; the **same-IP heuristic** was chosen for this phase (signed
  `?v=` tokens are contact *resolution* and belong to Phase 2). Session-based
  owner detection is a web-beacon concern (Phases 2–3); this module provides
  the tested core half plus the pure decision function.
- The retention *query* ships now (Phase 1 verification demands it); the
  daily job scheduling, env knob, per-run `activity_log` entry, and
  deployment-doc retention notes are Phase 6 scope, as planned.
- No new runtime dependencies; hashing uses `node:crypto`.
