# v2.0 Phase 6 — Event matcher — progress & verification

Implements Phase 6 of the [v2.0 plan](2026-09-07-v2.0-implementation-plan.md):
conference/event discovery with attendee matching against your network —
_"who in my network is going / went to X, and who could I go with or be
introduced to."_

The schema (`events`, `event_attendees`) and the manual "also met at…"
producer shipped in Phase 1's migration `0003`, so **this phase is
logic-only: no migrations, no new columns, no new runtime dependencies.**

The governing idea: **an attendee list is a claim about attendance, not a
claim about a meeting.** Every design decision below follows from it.

## What shipped

### Core: `packages/core/src/events/`

| File | What it does |
| --- | --- |
| `types.ts` | Vocabulary (`EVENT_SOURCES`, `ATTENDANCE_VIAS`), limits, `EventError`, and the record types shared by every surface. |
| `parse.ts` | The CSV reader: alias headers, date normalization, attendee splitting. Pure. |
| `match.ts` | The pure matcher: three tiers, confidence, ambiguity. |
| `repository.ts` | Reads (raw ANSI SQL) and writes (Drizzle) for events, attendance, matching and ranking. |
| `providers.ts` | The deferred discovery seam — an interface and a disabled default. |

**Parsing (`parse.ts`).** Exports from Luma/Eventbrite/conference tools
disagree about everything, so headers resolve through an alias table
(`Event Name`, `starts_at`, `Attendee Emails`, `names`, `ticket`…) with a
documented regex fallback, resolved longest-alias-first so `attendee names`
wins over `attendees`. Attendee cells split on `,` `;` `|` and newline; a
token with `@` is an email, anything else is a name. Dates accept
`YYYY-MM-DD`, `YYYY/MM/DD`, optional `HH:MM[:SS][.sss]` and optional
`Z` / `±HH:MM`; **everything else is rejected** — `14/03/2026` is March 14th
or April 3rd depending on who exported it, and silently shifting an event by
a month is worse than not importing it. `2026-02-31` is rejected rather than
rolled into March.

**Matching (`match.ts`).** Three tiers, most trusted first:

| Tier | Confidence | Behaviour |
| --- | --- | --- |
| exact email | 1.0 | auto-linked (normalized: lower-cased, `mailto:` and `<…>` unwrapped) |
| exact name | 0.9 | auto-linked (accent-, case- and punctuation-insensitive) |
| last name + first initial | 0.6 | **`review`** — reported, never linked unless you ask |

Anything with more than one plausible contact is `ambiguous` and comes back
with its candidates; two people are never resolved by guessing. A line whose
email and name point at *different* people is ambiguous too — contradictory
evidence is a decision for the owner, not a coin flip. `actionableMatches()`
is the only way a caller gets rows to write, so no surface can accidentally
link a `review` tier.

**Persistence (`repository.ts`).** Reads are raw ANSI SQL through the same
`rawAll` helper the search indexer and the skills module use (one query text,
both dialects); writes go through Drizzle inside dialect branches.

- `importEvents` — idempotent. Events dedupe on normalized name, attendance
  on `(event, contact)`; re-importing the same file writes nothing and says
  so. `--dry-run` / `{ dryRun: true }` previews.
- **Imported `met_at_event` edges are `pending`.** A conference roster says
  who was in the building. It does not say two of your contacts met, so those
  edges wait for confirmation on `/edges` — exactly like LinkedIn's "Mutual
  connections". Manual links (`netpro events link`, the web form) are
  `confirmed`, because that is you speaking, not an export file.
- **Bounded pairwise linking.** Co-attendee edges are O(n²) — a 500-person
  event would be 124,750 edges. Each event, each run, spends one cap of 250
  (`EVENT_LIMITS.edgesPerEvent`); when it is exhausted the run stops and says
  `edgeCapReached` rather than quietly writing a fraction.
- **The unmatched bucket.** Attendee lines that matched nothing (or too much)
  are parked per event in `activity_log` (`action = 'events.unmatched'`,
  replaced each run) instead of a new table, since Phase 6 ships no
  migration. `getEvent` reads the newest one back, so the UI can offer manual
  linking and `matchEventAttendees` can re-check them later — this is how a
  contact you imported *after* the conference gets linked with no re-import.
- `linkAttendee` marks attendance **planned** (`attended: false`) for an event
  that has not started yet, rather than claiming it already happened.
- `recommendEvents` — ranked, and every score is explained:
  `0.6 × peers` (how many of your contacts went; 5 saturates it, the
  blueprint's number) `+ 0.2 × industry` (share of your network in the
  attendees' industries) `+ 0.2 × timing` (upcoming 1.0 → recent 0.5 → old
  0.15 → undated 0.3). Empty *past* events are dropped; empty upcoming ones
  are kept (they are still a suggestion). Timing is computed at UTC-day
  granularity so a page can never print "in 7d" and "starts in 6 days" for
  the same event.

**`providers.ts`** — the plan's "optional discovery API" ships as an
interface plus a disabled default. Scraping Luma/Eventbrite means rate
limits, terms of service and a moving target, to suggest conferences you can
already find; `DISABLED_EVENT_PROVIDER` keeps the seam without the network
call, and `resolveEventProvider` / `canDiscover` are the only things a future
phase has to satisfy.

### CLI (17th command): `netpro events`

```bash
netpro events list [--query] [--upcoming] [--limit] [--json]
netpro events show <event>                    # id or exact name
netpro events add "React Conf" --location Berlin --starts 2026-09-14
netpro events import events.csv [--dry-run] [--review] [--no-edges]
netpro events match <event> [--apply] [--review]
netpro events link <event> <contact> [--role speaker]
netpro events unlink <event> <contact>
netpro events recommend [--limit]
netpro events rm <event>
```

Selectors reuse `resolveContactRef`; `show`/`match`/`link` take an event id
or an exact name and refuse to guess between same-named events. `import`
prints the matched / review / ambiguous / unmatched split, names the
candidates for every ambiguous line, and says plainly that the edges it
wrote are pending.

### Web

- **`/events`** — the list (name, when, where, how many of your contacts
  went), a GET filter form, **Where to go next** (the ranked recommendations
  with their reasons and the people going), an add form, and a CSV import
  panel that previews before it writes and names ambiguous rows.
- **`/events/[id]`** — the overlap: attendees strongest-tie first with
  company, role and tie strength; industries and companies; the **unmatched
  bucket** with a per-row link box; a re-match panel (preview then apply); an
  add-attendee box; and delete.
- **`/contacts/[id]`** gained an **Events** section — where you crossed paths
  with this person, linked to the event.
- **APIs** (all owner-only through the proxy boundary):
  `GET/POST /api/events`, `GET/DELETE /api/events/[id]`,
  `POST /api/events/[id]/match`,
  `POST/DELETE /api/events/[id]/attendees`.
- **Events** in the navigation and in `proxy.ts`'s protected routes.
- `EventError` now maps to HTTP like `CrmError` and `GraphError` do
  (`invalid_input` 400, `not_found` 404, `conflict` 409 — ambiguity is 400
  on every surface, matching the contact resolver).

## Decisions worth recording

1. **Attendance ≠ meeting.** Imported co-attendee edges are `pending`;
   manual ones are `confirmed`. This is the single most important rule in the
   phase and it is printed on the CLI, the import summary and the web panel.
2. **Ambiguity is data, not an error.** No code path picks between two
   people. The candidates come back to the owner every time.
3. **The unmatched bucket lives in `activity_log`.** Phase 6 ships no
   migration, and an unresolved attendee line is an event in the audit trail
   anyway. Replaced (not appended) on each run, so the table does not grow.
4. **Merging an existing pair upgrades it.** `addEdge(..., { merge: true })`
   — the house write path — updates an existing pair in place, so a manual
   link between two people who already had a *pending* imported edge
   confirms it. Documented, and consistent with Phase 1's producer.
5. **Discovery stays disabled.** See `providers.ts` above.
6. **The health payload was left alone.** `/api/health` reports `search`
   because search capability is a deployment-variable thing (migration +
   index + key). Event counts are inventory, not readiness, so they were not
   added to a probe that is deliberately terse for anonymous callers.

## Verification

- `npm run lint`, `npm run typecheck`, `npm run build` — clean (zero
  warnings).
- `npm test` — **1190 passing, 33 skipped** (was 1051 / 25; +139 tests, of
  which the 8 new skips are the live-PostgreSQL suite). Core events 72
  (parse 20, match 13, repository 39), CLI events 22, web routes 31
  (list/create 13, detail 6, match 4, attendees 8), web pages 11, proxy 2,
  plus the registration test that gained the seventeenth command and the
  shared CRM error-mapping test that gained `EventError`.
- New **live PostgreSQL** suite
  `packages/core/src/events/postgres.integration.test.ts` (8 tests, skipped
  without `NETPRO_TEST_DATABASE_URL`), wired into CI's postgres job. It
  exists because the module's "ANSI" SQL — `LIKE … ESCAPE '\'`,
  `ORDER BY (col IS NULL)`, correlated `COUNT(*)` subqueries,
  `COUNT(DISTINCT …)` — and the JSON/text `activity_log` bucket are exactly
  the kind of claim only a second dialect can contradict. (The sandbox for
  this work had no Postgres server, so it is verified by construction and by
  CI, not locally.)
- Adversarial coverage: unparseable and ambiguous dates, rows ending before
  they start, LIKE wildcards as literals, header-alias collisions, quoted
  and multi-separator attendee cells, malformed emails, duplicate attendees,
  ambiguous names, soft-deleted contacts (never matched, never counted),
  unknown/ambiguous event and contact selectors, re-import idempotency, the
  per-event edge cap, and pagination limits.

## Deferred

- Live event discovery (`providers.ts` is the seam), calendar sync, RSVP
  tracking, per-event analytics, and automatic attendee scraping — the
  plan's own deferred list. SMTP delivery for campaigns remains optional
  follow-up work (NetPro drafts; a human sends).
