# v2.0 Phase 7 — Release readiness & the `v2.0.0` cut

**Date:** 2026-09-08
**Branch:** `arena/01a07d3d-netpro`
**Plan:** [2026-09-07-v2.0-implementation-plan.md](2026-09-07-v2.0-implementation-plan.md)

Phase 7 has no product surface. It is the work that decides whether the six
phases before it are *shippable*: versions that agree with each other, a
CHANGELOG that says what was not shipped as loudly as what was, deployment docs
for the surfaces an operator has to run, a release gate that measures the thing
the plan asked to measure, and the cut itself.

## Decisions

### The version question the plan left open

The plan's open question #4 was: *keep workspace npm versions at `X.Y.0`
milestones (the v1.5 precedent: `1.5.0`), or stay on `0.x` until a public
npm publish?*

**Answer: bump to `2.0.0`.** Three reasons, in order of weight:

1. **Precedent.** v1.5 set versions to `1.5.0` at its cut, and the CHANGELOG
   records it under `### Changed` as the way a milestone is marked. The repo
   has already decided that the npm version tracks the product milestone, not
   the publish status.
2. **They are private packages.** Every workspace package is
   `"private": true`. The version is a label, not a contract with a registry,
   so the usual reason to sit at `0.x` — signalling an unstable public API —
   does not apply.
3. **The CLI was already there.** `apps/cli/src/cli.ts` has shipped
   `.version('2.0.0')` since Phase 5, and its test asserts it. Leaving the
   packages at `1.5.0` meant `netpro --version` and every `package.json`
   disagreed — exactly the drift a release cut exists to remove.

Documented in the CHANGELOG's `### Changed` so the choice is visible, not just
the bump.

### The pgvector item was obsolete

The plan asked for a **pgvector service in the Postgres job (health check for
the extension)**. That item was written against a risk that no longer exists:
v2.0's semantic arm stores embeddings as **portable JSON text**
(`search_index.embedding`), not as a `vector` column. The schema comments name
a native pgvector column as "a documented later optimization", and the plan's
own risk table already promised "no hard dependency" with `search.mode:
portable | hybrid` as the feature gate.

So the honest version of that item is not *add pgvector to CI*, it is **prove
the no-dependency claim in CI**, because "we don't need the extension" is
exactly the kind of promise that silently rots the day someone adds a
`vector` migration. `packages/db/src/postgres.integration.test.ts` now asserts
it directly: the server's extension list contains `plpgsql` and does **not**
contain `vector`, while the embedding round-trip above it still works. It runs
on the stock `postgres:16-alpine` service — which is what a managed provider
gives you.

### Where the performance pass lives

A one-off measurement in a scratch script would have answered the plan's
question once. The repo already had the better pattern: `graph/perf.test.ts`
measures the in-memory pipeline, asserts a CI-safe multiple of the budget, and
prints the real number for the record. So the pass is a test —
`packages/core/src/postgres.perf.test.ts` — that skips without
`NETPRO_TEST_DATABASE_URL`, runs in CI's Postgres job, and prints what it
measured. It asserts loose budgets (a 20× regression fails; jitter does not).

## Performance pass: 5k contacts / 20k edges

Measured on the sandbox for this work: **PostgreSQL 18.4** (npm
`@embedded-postgres` binaries), local, untuned, 4-connection pool, fixture
seeded with a deterministic LCG so the same graph is measured on every machine.
Timings are **medians of 3 runs** (search: 6 runs; pathfinder: 10), and they
time the **core entry point behind each route** — not HTTP, Next rendering or
auth, which add their own constant cost.

| What | Endpoint | Median | Min |
| --- | --- | --- | --- |
| Dashboard overview, graph section included | `GET /api/analytics` | **350 ms** | 266 ms |
| Dashboard overview, `graph=0` | `GET /api/analytics?graph=0` | **50 ms** | 42 ms |
| Graph overview (communities, centrality, components, warm intros) | `GET /api/graph/overview` | **264 ms** | 214 ms |
| Keyword search (`tsvector` + GIN) | `GET /api/search?mode=keyword` | **28 ms** | 26 ms |
| Hybrid search (no embedder configured → keyword + RRF merge) | `GET /api/search?mode=hybrid` | **28 ms** | 26 ms |
| Pathfinder plan, one request | `GET /api/graph/paths` | **~10 ms** | 9 ms |
| Fixture setup (not on the request path) | — | 2.1 s seed + 2.5 s index | — |

Numbers under 100 ms are stable run to run; the two graph-heavy rows moved
about 20 % between consecutive runs on the same idle machine (a second run
gave 327 ms / 47 ms / 209 ms / 32 ms / 31 ms / 106 ms). Treat them as an order
of magnitude rather than a benchmark — which is why the test asserts loose
budgets and this doc quotes both runs instead of the flattering one.

Three readings that matter:

1. **The graph is the cost, and it is not the expensive part.** The full
   dashboard is 350 ms; the same overview with the graph section switched off
   is 50 ms. Roughly 85 % of the dashboard's time is Louvain + centrality +
   components over 20k edges, in pure TypeScript, in the web process. That is
   the number to watch as a network grows — it is linear-ish in edges, and the
   ~50k-edge documented cap is where it stops being comfortable.
   (`docs/deployment.md` quotes 330 ms / 210 ms — rounded, because a number
   that precise would be a promise.)
2. **Search is not a Postgres problem at this size.** 28 ms for a tsvector
   query with `ts_rank` over 5k documents. The hybrid number here is the same
   work plus an RRF merge, because no embedder was configured — the vector
   call would be the operator's latency and bill, not this repo's.
3. **The pathfinder reloads the graph per request and still costs ~10 ms**, so
   there is no caching work needed at this scale. That is the trade the docs
   now state explicitly: no cache, no incremental recompute, ~50k edges.

Because these are entry-point timings, the doc records them as such rather
than implying a 327 ms page load.

## Verification

- `npm run lint`, `npm run typecheck`, `npm run build` — clean (only the
  pre-existing turbo "no output files" warnings for packages that emit none).
- **The cut broke CI before it passed it.** Bumping the package versions
  without updating `package-lock.json` — and, less obviously, without bumping
  the internal `"@netpro/*": "^1.5.0"` dependency ranges — makes `npm ci`
  fail, because it no longer matches the lockfile and npm then tries to
  resolve the workspace packages from the registry (404). Three jobs,
  including the Docker build, failed inside 30 seconds. Fixed by bumping the
  four internal ranges to `^2.0.0` and regenerating the lockfile; verified by
  running `npm ci` locally afterwards, which is the step that was skipped the
  first time. Worth remembering: in this repo a version bump is a
  three-part edit — `package.json` versions, the internal ranges, the lockfile.
- `npm test` — **1191 passing, 38 skipped** (was 1191 / 33 before this phase;
  +4 performance tests and +1 db Postgres test, all skipped without
  `NETPRO_TEST_DATABASE_URL`).
- Live Postgres: `@netpro/db` (15 tests), core search (11), core events (8) and
  the performance pass (4) all executed against a real server. The events suite
  is the one that failed on its first CI run this week and was fixed here —
  see the [Phase 6 progress doc](2026-09-07-v2.0-phase6-event-matcher-progress.md).
- CI: Lint/Typecheck/Test/Build on Node 20 and 22, PostgreSQL integration
  (db + search + events + performance pass), Docker image build with the
  migrate → health → auth-boundary smoke.
