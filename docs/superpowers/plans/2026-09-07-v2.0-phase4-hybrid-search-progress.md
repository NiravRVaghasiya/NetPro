# v2.0 Phase 4 — Hybrid search — progress & verification

Implements Phase 4 of the [v2.0 plan](2026-09-07-v2.0-implementation-plan.md).
Unlike Phases 1–3 this one touches the schema again (migration `0004`) and it
is the first phase to add an *optional paid dependency* to a read path, so the
governing constraint throughout was the plan's own rule: **no configuration =
no behaviour change.**

## What shipped

### Migration `0004_hybrid_search` (both dialects, additive)

`search_index` existed since v1 as an empty table with no producer. It now has
one, plus the dialect-native index behind it:

- **Both**: `search_text`, `content_hash`, `embedding`, `embedding_model`,
  `embedding_dims` columns on `search_index` + `idx_search_index_updated_at`.
- **SQLite**: `contacts_fts` — `fts5(contact_id UNINDEXED, search_text,
  tokenize='unicode61 remove_diacritics 2')` — with `contacts_fts_ai/_ad/_au`
  triggers on `search_index` so the virtual table can never drift, and a
  backfill for existing rows.
- **Postgres**: `search_vector tsvector GENERATED ALWAYS AS
  (to_tsvector('english', coalesce(search_text,''))) STORED` + a GIN index.
  Generated means there is no trigger to forget and no way to desync.

Neither `contacts_fts` nor `search_vector` is modelled in Drizzle (Drizzle has
no vocabulary for either); they are raw SQL in the migration and raw SQL in the
arm queries. There is deliberately **no snapshot JSON for 0004** — the columns
are in the schema files, the rest is not expressible.

### Core: `searchContacts` becomes a dispatcher

One entry point, unchanged signature apart from an optional third argument:

```ts
searchContacts(conn, options, deps?: { embedder?, signal? })
```

- `packages/core/src/search/rrf.ts` — `reciprocalRankFusion(lists, k = 60)`,
  pure, weighted, stable. Tested against merges computed by hand.
- `embeddings.ts` — fetch-only OpenAI-compatible client mirroring
  `ai/providers/openai.ts` (**no new runtime dependency**), plus
  `resolveEmbeddingsConfig`, `encodeEmbedding`/`decodeEmbedding`,
  `cosineSimilarity`.
- `indexer.ts` — `reindexSearchIndex()` and `searchIndexStatus()`.
  `buildSearchDocument` joins the fields the plan named — name, email,
  headline, company, role, seniority, department, industry, location, country,
  tags, notes — lowercased, capped at 4,000 chars. A content hash guards the
  write, so a re-run costs one SELECT per contact and nothing else.
- `arms.ts` — the keyword arm per dialect (`bm25(contacts_fts) ASC` /
  `ts_rank(...) DESC`, prefix-matching query builders that strip syntax
  characters so a user typing `"` or `*` can't inject FTS operators) and the
  semantic arm (filters to the current model, scans ≤ 5,000 vectors by
  relationship score, cosine, skips dimension mismatches).
- `hybrid.ts` — compiles the filters **once, without the free-text term**, and
  applies that identical WHERE to every arm. This is what makes filter parity
  with v1 structural rather than something tests have to keep re-proving.
  Fused ids then drive `total`, the page slice, and the facet scope.

### Producer, surfaces

- **Import** (`import/pipeline.ts`) writes index rows for touched contacts,
  best-effort behind a dynamic import: a failed index write reports
  `indexed: undefined` and **never fails the import**. Import never calls an
  embedder, so no CSV can run up an API bill.
- **CLI**: `netpro reindex [--embeddings] [--force] [--status] [--limit]`
  (15th command) and `netpro search --mode portable|keyword|hybrid` /
  `--semantic`, with an `Engine:` line that names each arm, its hit count and
  its skip reason. Keys resolve keychain-then-env exactly like
  `netpro outreach` (`embeddings.provider|key|model|baseUrl`).
- **Web**: an engine `<select>` on `/search` (the semantic option is not
  rendered at all when the server has no key), an `EngineBadge` with
  actionable hints, `GET /api/search?mode=`, and an owner-only `search` block
  in `GET /api/health?verbose` reporting `{ mode, indexed, contacts, embedded }`.

Against the plan's verification list, item by item:

- **Migration tests, both dialects** — SQLite asserts the columns, the virtual
  table, trigger sync on insert/update/delete, and idempotent re-run. The
  Postgres equivalents live in the gated integration suites.
- **RRF math** — hand-computed merges, including the weighting and the
  tie-break.
- **Arm merge + empty-arm fallback** — a keyword arm returning zero hits
  triggers a `count(*)` probe that distinguishes `index_empty` ("run
  `netpro reindex`") from a genuine no-match; a missing table reports
  `index_missing` ("run `netpro migrate`").
- **Filter parity with v1 on the same fixture** — same filters asserted
  against both `mode: 'portable'` and `mode: 'hybrid'`.
- **Embedding provider mocked, no HTTP** — every embedding test injects a
  provider or a typed `fetch` mock; the suite makes no network calls.
- **Embeddings API down → keyword results, no error** — asserted at three
  layers: core (`provider_error` in the engine report), CLI (`Engine:` line
  says "provider error", exit 0), web (route still 200s).
- **Perf on a 1k-contact import** — `search/perf.test.ts`, deterministic LCG
  fixture, budgets asserted at a CI-safe multiple. This machine reported:

  | Operation (1,000 contacts) | Measured |
  | --- | --- |
  | Cold reindex (all rows) | **85 ms** |
  | Warm reindex (all skipped by content hash) | **10 ms** |
  | `searchContacts` portable | **12 ms** |
  | `searchContacts` keyword | **14 ms** |
  | `searchContacts` hybrid (256-dim vectors) | **33 ms** |

- **Live CLI smoke** (`/tmp/netpro-p4`, built CLI, fresh SQLite): migrate → 5
  migrations, import 4 contacts → `reindex --status` reports 4/4 indexed,
  `reindex` warm = "0 indexed, 4 unchanged", `--force` = "4 indexed".
  `search stri --mode keyword` matched Stripe on the prefix. The money shot:

  ```
  $ netpro search senior              → No contacts match. (0 total matches)
  $ netpro search senior --mode keyword
    Jane Doe …
    Engine: keyword — full-text 1, substring 0
  ```

  `seniority` isn't a portable column, so v1 search could never find that row.
  `--semantic` with no key printed `semantic off (no embeddings key)` and
  exited **0**; `--mode fuzzy` exited 1 with the valid-mode list.
- **Gates**: `npm run lint` / `typecheck` / `test` / `build` all green
  repo-wide.

**Postgres could not be run locally** — this sandbox has no `postgres`,
`initdb`, `docker` or `podman`, and no installable package. Both pg suites are
skip-gated on `TEST_DATABASE_URL` and a `@netpro/core` integration step was
added to `.github/workflows/ci.yml` alongside the existing `@netpro/db` one, so
they execute against real Postgres in CI. Locally the pg paths are covered by
typecheck and review only, and this is the phase's main residual risk.

## Decisions & notes

- **`EMBEDDINGS_PROVIDER=disabled` by default** — this resolves the plan's
  open question #2 ("should embeddings be owner-gated?"). Off by default means
  there is nothing to gate: the surface that would cost money doesn't exist
  until someone sets a key.
- **Bad config degrades on the web, throws in the CLI.** `EMBEDDINGS_PROVIDER=openia`
  makes `netpro reindex` fail loudly (a human is watching, and a typo that
  silently disables semantic search would waste their afternoon), but the web
  app treats it as `disabled` — a misspelled env var must never 500 `/search`.
  Both behaviours are tested.
- **An unknown `?mode=` is a 400 on the API and ignored on the page.** An API
  client asking for something we don't support deserves an error rather than a
  silent downgrade it will never notice; a person following a stale bookmark
  deserves their results.
- **SQLite gets no semantic arm at all** rather than a slow in-process scan
  pretending to be one. `--semantic` there reports the skip and returns
  keyword results.
- **Weights (keyword 1 / semantic 0.9 / portable 0.5)** are a starting point,
  not a tuned result — tuning needs a real corpus and real relevance
  judgements. They live in one exported constant so changing them is a
  one-line diff plus a test update. BM25 tuning stays deferred per the plan.
- **Substring search still runs in every mode.** It is the only arm that can
  match a freshly-imported contact whose index row hasn't been written yet, so
  it stays in the fusion as a low-weight safety net rather than being replaced.
- **`SEMANTIC_SCAN_LIMIT = 5000`, `HYBRID_POOL_LIMIT = 500`** are asserted in
  the perf test so raising them has to be deliberate; the pool cap surfaces to
  users as `engine.truncated` → "Showing the top candidates only".
- Deferred, per the plan and untouched here: local/ONNX embeddings, quantized
  vector search, BM25 tuning, multi-language tokenizers, typo tolerance beyond
  prefix matching. `pgvector` specifically is **not** required — the semantic
  arm reads vectors out of a text column and ranks in JS, which keeps the
  migration portable and managed-Postgres-friendly; swapping in a real vector
  index is a Phase 7-or-later optimisation with a measurement to justify it.
