## What already exists (v2.5 foundation) relevant to v3.0

- **Auth is hard single-owner.** `NETPRO_OWNER_GITHUB_ID` is the only
  authorized account (`apps/web/lib/owner.ts` says it outright: "contacts are
  not partitioned by user, so open registration is unsafe"). The Auth.js
  `user` / `account` / `session` tables exist since `0000` but hold one user.
  **No `owner_id` / `workspace_id` column exists on any data table** — every
  core function implicitly means "all rows, one owner's data". Team mode is
  therefore the largest schema and query-contract change in NetPro's history,
  and it gets two dedicated phases (1–2) plus a compatibility guarantee:
  a single-member workspace must behave exactly like today.
- **Four provider seams already ship, each with the shape a plugin needs:**
  - `EnrichmentProvider` (`packages/core/src/enrichment/types.ts`) —
    `hunter`, `pdl`, `clearbit`; BYO key, injectable `fetch`, offline tests.
  - `AiProvider` (`packages/core/src/ai/types.ts`) — `openai` (any
    OpenAI-compatible base URL), `anthropic`; plain `fetch`, no SDKs.
  - `ContentProvider` (`packages/core/src/content/providers.ts`) — `manual` +
    `rss` enabled; `devto` / `twitter` / `github` as disabled, self-explaining
    stubs naming the env key that would enable them.
  - `EventDiscoveryProvider` (`packages/core/src/events/providers.ts`) — the
    disabled interface shipped in v2.0 precisely so v3.0 could grow producers.
  The plugin runtime (Phase 5) unifies registration behind these interfaces
  instead of inventing a fifth one — a plugin is a bundle of implementations
  for seams that already exist.
- **Patterns to reuse, all with tests:** the in-process scheduled job
  (retention purge, ≤ once per 24 h, audit-logged — the exact shape webhook
  delivery needs); the in-memory token-bucket rate limiter; HMAC-signed,
  expiring tokens (`?v=` view tokens — the same construction for invite
  tokens and webhook signatures); `activity_log` as the audit trail;
  `resolveContactRef` / `resolveContentRef` as the shared selector pattern.
- **`viewed_card_id` exists on `profile_views`** (v2.5 Phase 1, still
  nullable and unused) — future-proofing for more than one card, which a
  team workspace might eventually want.
- **The Security doc already designs the key vault.** §2.3 specifies
  per-user AES-256-GCM API-key encryption (master secret ≥ 32 chars,
  per-user derived keys, `base64(iv + ciphertext + authTag)`). It was
  deferred from v1.0 through v2.5; teams and plugins both need it, so it
  ships here as Phase 4.
- **Deferred from v2.0/v2.5 that v3.0 picks up or keeps deferring:**
  - *Picked up:* per-user encrypted web key storage (Phase 4 — prerequisite
    for plugin credentials and per-member provider keys).
  - *Picked up (as a plugin, not built-in):* live event discovery — the
    `EventDiscoveryProvider` seam becomes a plugin capability, and the
    reference example plugin can implement one.
  - *Still deferred:* native `pgvector` + ANN index; SMTP delivery
    (draft-only outreach is a product stance, not a gap); `$EDITOR`
    draft-review loop; graph caching.
- **`docs/deployment.md`** already carries the operator-knob convention
  (`NETPRO_*` env vars documented in tables) that the new phases extend.

## The four v3.0 features (blueprint scope)

1. **Plugin architecture** — custom data sources, custom AI providers: a
   versioned `definePlugin()` contract over the existing provider seams,
   with a permission manifest, an in-process loader, and CLI + web lifecycle
   management. The blueprint sketches `sources`, `enrichers`, and `commands`;
   NetPro's shipped seams also make content metrics providers, event
   discovery, and AI providers first-class plugin capabilities.
2. **Team/org mode** — shared CRM, collaborative outreach: workspaces with
   members and roles, invite-based join (GitHub OAuth stays the only IdP),
   every query explicitly scoped, follow-ups assignable, campaign steps
   ownable, an audit viewer, and per-user GDPR export.
3. **Self-hosted marketplace** — a static, self-hostable plugin index format
   plus `netpro plugin install` with checksum verification and a
   pre-install permissions review. No central hosting, no accounts, no
   telemetry — the default index is a file in this repo, overridable.
4. **Webhook integrations** (Zapier, n8n, Make) — outbound webhooks with
   HMAC-SHA256 signatures, a versioned event catalog, retry with backoff and
   dead-lettering, delivery logs, and receiver recipes for the three named
   platforms. Outbound only in v3.0; inbound "webhook → NetPro action" stays
   deferred (the API already covers programmatic writes).

## Phase 1 — Workspaces data model & multi-user auth

**Problem.** Every table implicitly belongs to the one owner. There is no
membership, no role, no invite path, and open registration is unsafe by
design. Team mode needs row ownership without breaking a single existing
install.

**Goal.** Introduce workspaces, members, roles, and invites; put every data
row in exactly one workspace; let more than one GitHub account sign in —
but only through an invite.

### Data model (additive migration `0008`, both dialects)

- `workspaces`: `id`, `name`, `slug` (unique), `created_at`. The bootstrap
  workspace is created by the migration **from existing data** (name
  "Personal" or the owner's login if resolvable; no network in migrations —
  default to `"default"` and let the UI rename).
- `workspace_members`: `id`, `workspace_id` (FK cascade), `user_id` (FK to
  the existing Auth.js `user` table), `role` (`owner` | `admin` | `member` |
  `viewer`, default `member`), `created_at`; UNIQUE `(workspace_id, user_id)`.
  The `NETPRO_OWNER_GITHUB_ID` account is migrated to the first `owner` row.
- `workspace_invites`: `id`, `workspace_id`, `token` (HMAC-signed, expiring —
  same construction as the `?v=` view tokens), `role`, `expires_at`,
  `created_by`, `accepted_at`, `revoked_at`. Membership is *only* created by
  an invite being accepted or by an admin adding a known user.
- `workspace_id` (text, nullable in the column, backfilled and thereafter
  always written) added to **every** data table: `contacts`,
  `interactions`, `follow_ups`, `campaigns`, `campaign_recipients`, `edges`,
  `events`, `event_attendees`, `content_items`, `content_metrics`,
  `content_mentions`, `enrichments`, `search_index`, `cards` (draft +
  published), `profile_views`, `activity_log`. The migration backfills all
  rows with the bootstrap workspace id. House rules apply: additive SQL,
  no destructive change, idempotent re-run.
- **Indexes:** composite `(workspace_id, …)` leading variants where queries
  filter — at minimum `contacts (workspace_id, updated_at)`,
  `interactions (workspace_id, contact_id)`, `follow_ups (workspace_id, status, due_at)`,
  `profile_views (workspace_id, viewed_at)`, `activity_log (workspace_id, created_at)`.
  Existing single-column indexes stay (they remain the fast path for the
  one-workspace case).
- **FTS is the one structural change:** the SQLite FTS5 virtual table and
  the Postgres `tsvector` column from `0004` must learn `workspace_id`. The
  migration adds the column to `search_index` and triggers a one-time
  reindex marker (the existing `netpro reindex` rebuilds both arms; the
  migration notes it, the upgrade guide states it, and search falls back to
  the portable arm — which is workspace-filtered — until reindexed).

### Auth changes

- Sign-in stays GitHub OAuth. The post-sign-in authorization changes from
  "is this `NETPRO_OWNER_GITHUB_ID`" to "does this user have a live
  membership in any workspace" (for v3.0: in *the* workspace — one workspace
  per install remains the supported shape; the schema is multi-workspace so
  v3.x can grow).
- `NETPRO_OWNER_GITHUB_ID` remains the bootstrap owner and the emergency
  break-glass account: always a member with role `owner`, cannot be removed,
  and a fresh install with no members table rows auto-provisions exactly as
  today (single-owner compatibility path).
- Invites: an admin generates a link (`/invite/<token>`), the invitee signs
  in with GitHub, the token binds their GitHub id → `user` row → membership,
  then expires. Tokens are HMAC-signed with `NEXTAUTH_SECRET`, expiring
  (7-day default), single-use, revocable.
- `proxy.ts`: every `(app)` route resolves session → user → active
  membership; role floors are enforced per route class in Phase 3 (`viewer`
  can read, `member` can write CRM, `admin` manages workspace, `owner`
  controls billing-adjacent things — for v3.0: deletion, member roles,
  plugins, webhooks).
- The public card and beacons resolve **card → workspace** (a card belongs
  to a workspace; `?v=` tokens sign the workspace's card). Public surfaces
  gain no new information.

### Out of scope

- Multiple workspaces per install as a *supported UI* (schema-ready only).
- SSO/SAML, email invites (token links only — no mail is sent, the admin
  hands the link over), per-contact visibility flags (see Open questions).
- Any change to the CLI's default behavior (Phase 2 adds `--workspace`, and
  a single-workspace install never needs it).

### Verification

- Migration tests: fresh SQLite + live Postgres apply `0008` idempotently;
  backfill assigns every pre-existing row to the bootstrap workspace
  (count-asserted); journals updated on both dialects.
- Auth tests: invited user can sign in and see the workspace; uninvited
  GitHub account is refused exactly like today; revoked member's next
  request 401s; expired/used/replayed invite tokens rejected; break-glass
  owner always passes.
- Scoping smoke (the real teeth arrive in Phase 2, but the guard starts
  here): two workspaces seeded, the API layer cannot return workspace B rows
  to a workspace A session.
- Single-owner regression: the full v2.5 test suite passes **unchanged** on
  a migrated one-member database — no snapshots edited en masse; where a
  payload gains a `workspace` field it must be additive (JSON keys added,
  none renamed or removed).

## Phase 2 — Workspace-scoped engine & surfaces

**Problem.** Every function in `packages/core` reads "all rows". With more
than one member — or eventually more than one workspace — that is a
cross-tenant leak waiting for the first multi-member install.

**Goal.** Every core query is explicitly workspace-scoped, and every surface
passes the scope from the authenticated principal.

### Core contract

- New `WorkspaceScope` type in `packages/core` (`{ workspaceId: string; role: Role; userId: string }`),
  threaded through every exported function that touches data — the same
  seam for CLI and web. Functions keep their signatures compatible by
  accepting an optional scope that defaults to the bootstrap workspace
  (single-owner installs call them exactly as before).
- Every SQL statement in `packages/core` gains an explicit
  `workspace_id = ?` predicate — including the raw-SQL modules (analytics
  overview, hybrid search's three arms, events matcher, views analytics,
  content repository, graph engine's edge loads, CRM, campaigns).
  **Scoping is enforced in the core, not trusted to callers** — the same
  rule that made bot/owner exclusion trustworthy in v2.5's views analytics.
- A `scope-guard` test helper: on a two-workspace fixture, every exported
  query is called with workspace A's scope and asserted to return zero rows
  from workspace B. This becomes the template the live-Postgres job runs per
  dialect.
- Writes stamp `workspace_id` (and where authorship matters — interactions,
  follow-up completions, campaign step confirmations — a `created_by_user`
  text column lands in this phase's additive `0009_authorship.sql`,
  backfilled to the bootstrap owner).

### Surfaces

- **Web:** session → active membership → scope for every server component
  and route handler; the analytics, views, content, graph, events, skills,
  CRM, campaign, import, and export surfaces all pass through one
  `requireScope()` helper. No page changes beyond what membership requires.
- **CLI:** `netpro config` gains the workspace binding (default: the
  bootstrap workspace, so existing setups are untouched);
  `--workspace <id|slug>` on commands that operate on data. CLI remains
  operator-grade: it talks to the database directly and can address any
  workspace (documented — the CLI is the admin tool).
- **Retention job, reindex, beacons:** scoped (purge per workspace;
  reindex per workspace; beacon resolves the card's workspace before
  writing or counting).
- **GDPR:** the export flow becomes per-user (their interactions, drafts,
  key-vault entries) vs per-workspace (contacts, shared data) with the
  deletion flows matching; documented in `docs/deployment.md`.

### Verification

- The scope-guard suite over every core module, on SQLite and live Postgres
  (dialect-divergent SQL — `COALESCE` uniques, FTS predicates, tsvector —
  is exactly what live-PG CI exists for).
- Adversarial: crafted `workspace_id` params in API requests are ignored
  (scope comes from the session, never the request); CLI `--workspace` with
  an unknown slug errors cleanly; import into workspace A never touches B's
  dedupe keys (unique indexes gain the workspace column where dedupe is
  per-workspace — e.g. contact email dedupe stays per-workspace).
- Performance: the v2.5 budgets re-run on a two-workspace fixture at the
  same sizes; dashboard/search/graph latencies within 10% of the recorded
  v2.5 numbers for the single-workspace case.

## Phase 3 — Team collaboration surface

**Problem.** Members can exist after Phases 1–2, but the product is still a
solo cockpit: nothing is assigned, authorship is invisible, and admins have
no audit view.

**Goal.** Make the shared CRM actually collaborative, with roles that mean
something and an audit trail you can read.

### Features

- **Team admin (owner/admin):** `/settings/team` — member list with roles,
  role changes (never below your own), removal (membership revoked; their
  authored interactions and completions stay, attributed), invite
  generation/revocation. Owner role transfers require the break-glass owner.
- **Role floors (enforced server-side, mirrored in the proxy):**
  `viewer` — read-only (pages render, write APIs 403);
  `member` — CRM writes (interactions, follow-ups, campaign step outcomes,
  imports); `admin` — everything except owner-level acts (workspace
  deletion, owner transfer); `owner` — everything.
- **Assignment:** follow-ups gain `assigned_to` (nullable user id; null =
  anyone); `/contacts` and the dashboard surface "assigned to me" and
  "unassigned" filters; interactions already carry author stamps from
  Phase 2 and render them.
- **Collaborative outreach (draft-only stance unchanged):** campaigns are
  workspace objects; step confirmations record who confirmed the send;
  per-day send limits stay per-workspace (documented — the human mailboxes
  doing the sending are the real limit).
- **Audit viewer:** `/settings/activity` — paginated `activity_log` reader
  (admin+), filterable by action prefix, member, and date. No new logging —
  v3.0's new actions (`workspace.*`, `plugin.*`, `webhook.*`) flow into the
  same table.
- **CLI:** `netpro team list/invite/revoke/role/rm` (admin tool, operates
  on the configured workspace).

### Verification

- Role-matrix tests: every write API crossed with every role (403 vs 200),
  including the viewer floor on brand-new routes.
- Assignment lifecycle tests; reassignment on member removal (assigned
  follow-ups fall back to unassigned, with an `activity_log` entry).
- Audit viewer pagination/filters; invite flow end-to-end in route tests.
- Adversarial: self-role-escalation attempts, removing the break-glass
  owner, invite replay, role floor bypass via API with a viewer session.

## Phase 4 — Encrypted key vault (web)

**Problem.** Provider keys in the web app are server-env only. That was
correct for one operator, but a team has members who should not share one
key, and plugins (Phase 5) need per-plugin credentials the operator should
set in the UI, not in `docker-compose.yml`.

**Goal.** The Security doc §2.3 design, shipped: encrypted at rest with a
master secret, per-principal derivation, and an env fallback that keeps
today's deployments working.

### Data model (additive migration `0010_key_vault.sql`, both dialects)

- `key_vault`: `id`, `workspace_id`, `user_id` (nullable — null =
  workspace-level), `key_name` (e.g. `outreach.openai`, `plugin.github`),
  `ciphertext` (AES-256-GCM, `base64(iv + tag + ct)`), `last_four`,
  `created_at`, `updated_at`, `last_used_at`; UNIQUE
  `(workspace_id, user_id, key_name)`. Never the plaintext, never the
  full key length, never in `activity_log` payloads.

### Core & surfaces

- `packages/core/crypto/key-vault.ts` per the Security doc: master secret
  from `ENCRYPTION_MASTER_KEY` (≥ 32 chars, refuse to boot the write path
  without it — read-only fallback documented), per-principal key derivation
  (`sha256(master:principal:netpro-key-vault-v1)`), encrypt/decrypt
  round-trip, constant-time failure modes (no plaintext in errors).
- Resolution order for every provider flow (AI outreach, enrichment,
  embeddings, content fetch): **personal vault → workspace vault → server
  env** (unchanged behavior when only env exists — the compatibility
  guarantee again).
- `/settings/keys`: add/save/remove keys per provider slot, "personal" vs
  "workspace" (admin) toggle, masked display (`sk-…abcd`), last-used
  stamps. Keys are POSTed once, never rendered again; the page shows
  integration status exactly like today's `/settings`.
- CLI keychain is unchanged (already encrypted at rest in `~/.netpro`); the
  two stores are documented as the CLI-is-you / web-is-shared split.

### Verification

- Crypto: round-trip, tampered ciphertext rejected (GCM tag), wrong master
  key yields auth-failure not garbage, per-principal isolation (user A
  cannot derive user B's key).
- Adversarial: no plaintext or full key material in DB, logs, or API
  responses (grep-level assertions in tests); 401/403 floors on the new
  routes; env fallback precedence tests (personal overrides workspace
  overrides env).
- Migration test on both dialects; `ENCRYPTION_MASTER_KEY` absence behaves
  as documented (read-only, no writes to the vault).

## Phase 5 — Plugin runtime & manifest

**Problem.** The four provider seams are compile-time built-ins. Adding a
source, enricher, AI provider, or content provider means forking NetPro.

**Goal.** A versioned, permission-declaring plugin contract over the
existing seams, loadable at runtime, honest about its trust model.

### The contract (`packages/core/src/plugins/`)

```typescript
export interface PluginManifest {
  name: string;                 // npm-style unique id
  version: string;              // semver
  engine: string;               // netpro version range, e.g. "^3.0.0"
  permissions: {
    network?: string[];         // host allowlist, e.g. ["api.github.com"]
    capabilities: Array<
      "source" | "enricher" | "ai-provider" |
      "content-provider" | "event-discovery" | "command"
    >;
  };
  settings?: SettingSpec[];     // typed fields the UI renders
}

export function definePlugin(manifest: PluginManifest, register: (api: PluginApi) => void): Plugin;
```

- `PluginApi` is **injection, not ambient**: a `fetch` wrapper that enforces
  the declared host allowlist (undeclared host → blocked + audited), a
  workspace-scoped data API (typed read/search/write helpers over the same
  core functions — never a raw `Conn`), a settings reader (secrets resolved
  from the vault with `plugin.<name>.<key>` slots), a logger (structured,
  rate-capped, into `activity_log` on lifecycle events only), and capability
  registrars that take the *existing* interfaces (`EnrichmentProvider`,
  `AiProvider`, `ContentProvider`, `EventDiscoveryProvider`) plus a CLI
  command registrar (commander subcommand).
- Built-ins are not rewritten as plugins (they stay in-process, zero-cost),
  but they register through the same capability registry so surfaces list
  them uniformly and a plugin can *override by id* only where the built-in
  is disabled-by-default (e.g. the event-discovery seam).

### Data model (additive migration `0011_plugins.sql`, both dialects)

- `plugins`: `id`, `workspace_id`, `name`, `version`, `manifest` (JSON),
  `enabled` (default false), `installed_from` (path | index | url),
  `installed_by_user`, `created_at`, `updated_at`; UNIQUE
  `(workspace_id, name)`.
- Plugin settings: non-secret fields in a `plugin_settings` JSON column;
  secrets live in the Phase 4 vault, never here.

### Loader & lifecycle

- Discovery: `NETPRO_PLUGIN_DIR` (default `./plugins`), each subdirectory a
  manifest + entry (ESM `import()`, no `require` of arbitrary URLs —
  installation is a Phase 6 CLI/web action that copies files locally first).
- Registration is explicit and audited: `plugin.installed` / `enabled` /
  `disabled` / `removed` in `activity_log` with the actor.
- Enable/disable is runtime and reversible; a failing plugin disables
  itself with a logged reason and **never takes the app down** (loader
  wraps registration in a boundary; surfaces show the notice).
- Engine range check refuses plugins declaring incompatible versions with
  a self-explaining error (not a stack trace).
- **Trust model, documented plainly:** plugins run in-process with the
  Node process's privileges. The permission manifest enforces the *network*
  boundary and scopes the *data* boundary, but a malicious plugin is
  defended against only by the operator's review — which is why the
  marketplace (Phase 6) puts permissions in front of every install, and
  why nothing is ever auto-installed. This is stated in the README,
  `docs/deployment.md`, and the settings UI.

### Surfaces

- CLI: `netpro plugin list|info|enable|disable|rm` (+ `install/update` in
  Phase 6); `netpro plugin paths` shows the load roots.
- Web: `/settings/plugins` — installed plugins, capabilities, permissions,
  settings forms rendered from `SettingSpec`, enable/disable, secrets to the
  vault. Admin+ role floor.
- First-party reference plugin: `plugins/example-event-discovery/` — a
  minimal, offline-testable event-discovery plugin that exercises every
  capability of the contract (manifest, one network host, settings, a
  command) and doubles as the marketplace's index entry #1. The disabled
  built-in seam stays disabled; the plugin is how you turn it on.

### Verification

- Manifest validation: malformed manifests, bad semver, engine mismatch,
  unknown capabilities, oversized settings specs.
- Permission enforcement: plugin `fetch` to an undeclared host is blocked
  and audited; declared host passes; allowlist is exact-host with explicit
  wildcard syntax (no accidental subdomain matching).
- Data boundary: the injected API cannot reach another workspace even with
  a crafted id (scope-guard suite extended to the plugin API).
- Lifecycle: enable → capabilities registered; disable → unregistered;
  crashing plugin → isolated; adversarial loader tests (entry that throws,
  registers twice, never resolves).

## Phase 6 — Self-hosted marketplace

**Problem.** Plugins need a distribution story that does not create a
central service to run, police, or pay for.

**Goal.** A static index format anyone can host, an installer that
verifies what it installs, and a permissions review in front of every
enable.

### Index format (shipped in this repo)

`marketplace/index.json` — the reference index:

```json
{
  "schema": 1,
  "updated_at": "2026-…",
  "plugins": [{
    "name": "example-event-discovery",
    "version": "1.0.0",
    "description": "…",
    "homepage": "https://github.com/…",
    "source": { "type": "tarball", "url": "https://…/plugin.tgz", "sha256": "…" },
    "manifest": { "permissions": { "network": ["…"], "capabilities": ["event-discovery"] } }
  }]
}
```

- `MARKETPLACE_INDEX_URL` (default: this repo's raw file; overridable to any
  static host — GitHub Pages, S3, a file on the intranet). Fetching the
  index is a plain GET with a user agent; nothing about the operator is
  sent (no install telemetry, ever — the fetch cache is local and
  documented).
- `source.type`: `tarball` (sha256 **required**; extraction via a vendored
  minimal USTAR reader — Node's built-in `zlib` gunzip + ~200 lines of tar
  parsing, no new dependency, consistent with the house rule) or `git`
  (clone + checkout, pinned to a commit sha256 of the tree hash).

### Install flow (CLI + web)

1. Fetch/cache index → `netpro plugin search <term>` / marketplace list in
   `/settings/plugins`.
2. `netpro plugin install <name>` → download → **sha256 verify** (mismatch
   = hard refusal, audited) → copy into `NETPRO_PLUGIN_DIR` → register
   disabled with the manifest recorded.
3. **Permissions review gate:** the install output (and the web dialog)
   shows hosts and capabilities and requires an explicit
   `--i-have-reviewed-permissions` (CLI) or confirm step (web) *before the
   first enable*. The enable action is what writes `plugin.enabled = true`
   and the audit entry.
4. `update` = install-over with version monotonicity (downgrades refused
   unless forced, with a warning); `rm` unregisters and deletes the files.

### Verification

- Offline install tests against a fixture index and fixture tarball
  (file:// or a local server — no network in tests, house rule).
- Checksum mismatch, truncated tarball, path traversal in tar entries
  (`../../` entries refused — the USTAR reader validates every path),
  index schema drift, oversized index, downgrade attempts.
- Web install route tests (403 for member role, permissions dialog flow).
- The reference plugin installs from the shipped index end-to-end in CI.

## Phase 7 — Webhooks (outbound)

**Problem.** NetPro's data lives behind its own UI and CLI; the automation
platforms the blueprint names (Zapier, n8n, Make) need a push interface.

**Goal.** Signed, retried, observable outbound webhooks over a small,
versioned event catalog.

### Data model (additive migration `0012_webhooks.sql`, both dialects)

- `webhooks`: `id`, `workspace_id`, `url`, `secret` (generated, shown once,
  stored hashed — HMAC verification uses the plaintext only in memory
  around delivery), `events` (JSON allowlist), `enabled`, `description`,
  `created_by_user`, `created_at`, `updated_at`.
- `webhook_deliveries`: `id`, `webhook_id`, `event`, `payload` (JSON),
  `status` (`pending` | `delivered` | `failed`), `attempts`, `next_attempt_at`,
  `response_status`, `error`, `created_at`. Retention: deliveries pruned
  after 30 days by the existing scheduled job (new knob
  `NETPRO_WEBHOOK_DELIVERY_RETENTION_DAYS`).

### Event catalog (schema-versioned, additive)

v3.0 ships: `contact.created`, `contact.updated`, `interaction.logged`,
`followup.completed`, `campaign.activated`, `campaign.step.confirmed`,
`campaign.recipient.replied`, `content.added`, `plugin.enabled`,
`workspace.member.added`. Payloads carry `schema: 1`, the workspace id, the
actor, and the entity — deliberately **excluding** high-volume events
(card views) and raw third-party payloads, for the same reason the
observer's privacy budget exists: volume and PII discipline. Webhook
payloads are the operator's own data going to the operator's own endpoint;
the docs say so plainly, and the event allowlist is per-webhook.

### Delivery engine

- In-process scheduler reusing the retention-job pattern (interval, ≤ once
  per tick, audit summary — plus an immediate enqueue on event emission).
- Signature: `X-NetPro-Signature: t=<unix>,v1=<hmac-sha256(secret, t + "." + body)>`
  — timestamped (replay window documented for receivers), constant-time
  comparison recipe documented for receivers.
- Retries: exponential backoff (1 m → 32 m), max 8 attempts, then
  dead-letter (`failed`, redeliverable by hand). Per-webhook rate limit
  (in-memory token bucket, same class as the beacon limiter). Response
  timeouts (10 s), 2xx = delivered, everything else retries.
- **SSRF posture, documented:** URLs are operator-configured (admin role),
  so private-network targets are *allowed but flagged* in the UI
  (`http://localhost` shows a warning); this is a self-hosted tool whose
  admins may legitimately target internal n8n. Not silent, not blocked.

### Surfaces

- CLI: `netpro webhook list|add|rm|enable|disable|test|deliveries|redeliver`.
- Web: `/settings/webhooks` (admin+) — list, add with event-picker,
  rotate secret, enable/disable, delivery log with response codes,
  one-click redeliver, and a copy-paste **receiver recipes** section:
  Zapier (Webhooks by Zapier), n8n (Webhook node + signature check snippet),
  Make (Custom webhook), and a plain Node/`crypto` verification example.
- `docs/deployment.md`: operating notes, retention, the event catalog
  table, and the signature recipe.

### Verification

- Signature correctness and receiver-side verification recipe (the Node
  example in docs is itself exercised as a test).
- Retry/backoff with fake timers; dead-letter after 8 attempts; redeliver
  resets and retries; disable stops pending deliveries.
- Event allowlist: a webhook subscribed to nothing gets nothing; unknown
  event names rejected at configuration time.
- Adversarial: non-2xx and hanging endpoints (timeout), oversized payloads
  (capped; truncated with a notice, never a failed emit), invalid URLs at
  config time, delivery-log injection attempts, secret rotation
  invalidating old signatures (documented).

## Cross-cutting notes

### House rules every phase must follow

- **Dual dialect**: every migration ships `postgres/` + `sqlite/` additive
  SQL + snapshot + `_journal` update; no dialect-only features without
  documented degradation.
- **No new runtime deps unless justified** — the marketplace's tarball
  reader is vendored minimal USTAR over Node's `zlib`; the plugin loader is
  ESM `import()`; webhooks are plain `fetch` + `node:crypto`. Anything else
  gets justified, pinned, and measured in the phase plan.
- **The compatibility guarantee**: single-workspace, single-member installs
  keep v2.5 behavior, payloads, and performance — enforced by running the
  v2.5 suite unchanged against migrated fixtures.
- **Scoping in the core, not the callers** — the rule that made v2.5's
  privacy exclusions trustworthy now guards tenancy.
- **Owner/admin boundaries everywhere**: new admin surfaces (team, plugins,
  marketplace installs, webhooks) inherit the proxy boundary with role
  floors; public surfaces (`/card`, beacons) gain no new information.
- **Adversarial tests**: cross-tenant reads, role escalation, invite
  replay, checksum mismatch, tar path traversal, permission bypass,
  secret leakage into logs, oversized everything.
- **No secrets in web client or client payloads**: vault plaintext is
  write-only from the UI; webhook secrets shown once; plugin secrets live
  in the vault.
- **Draft-only AI and outreach stays** — even "collaborative outreach"
  means humans send; SMTP remains deferred on purpose.
- **No telemetry**: the marketplace index fetch sends nothing but the URL;
  there is no phone-home anywhere in v3.0.

### Risks

| Risk | Mitigation |
|---|---|
| Multi-tenant migration breaks existing installs | Additive `0008` + backfill, idempotency tests, the unchanged v2.5 suite against migrated fixtures, live-PG migration job, and the compatibility guarantee as a standing release gate |
| Cross-tenant leakage in raw-SQL modules | `WorkspaceScope` threaded through core; scope-guard suite per module per dialect; scoping enforced in core, never trusted to surfaces |
| FTS reindex needed after `0008` | Migration records the marker; search falls back to the portable (already scoped) arm until `netpro reindex` runs; upgrade guide states the step |
| Malicious plugin | Honest trust model: enforced host allowlist + injected data API + no auto-install + permissions review gate + audit trail; documented as operator-trust, never marketed as a sandbox |
| Marketplace supply chain | sha256-pinned index entries, tarball path validation, no script execution at install time, index fully self-hostable, no install telemetry |
| Webhook abuse / SSRF | Admin-only config, per-webhook rate limit, event allowlist, 30-day delivery retention, private-target warning, HMAC + timestamp recipe |
| Perf regression from `workspace_id` predicates | Composite indexes in `0008`; two-workspace perf fixture recorded in Phase 8; single-workspace budgets must stay within 10% |
| Scope creep (12 weeks, 3 devs) | Phases independently shippable; explicit Deferred list below; parallel tracks (1–3, 4–6, 7) with Phase 2 as the merge point |

### Deliberately deferred from v3.0

- Real plugin sandboxing (worker-thread/VM isolation, capability-based OS
  security) — the manifest is honesty about trust, not a security boundary;
  a sandbox proposal belongs in v3.x with its own threat model.
- A centrally hosted, curated marketplace with accounts, search, and
  ratings — the index format is designed so one *could* be built, but
  NetPro ships none.
- Inbound webhooks ("Zapier triggers NetPro actions") — the authenticated
  API already covers programmatic writes; a token-scoped inbound contract
  is a v3.x candidate.
- Per-contact visibility (private vs shared) beyond the shipped column —
  shared-by-default is the blueprint's "shared CRM" intent; making rows
  private is a product decision that deserves its own round.
- Multiple public cards per workspace (the `viewed_card_id` column keeps
  the door open).
- SSO/SAML, email-delivered invites, workspace-level billing.
- Carried over: native `pgvector` + ANN, SMTP delivery, `$EDITOR`
  draft-review loop, graph caching, AI skills extraction by default.

### Suggested branch / PR pattern

Same as v1.0–v2.5: one branch per phase (`arena/<commit>-v3.0-phaseN-…`),
each phase its own PR referencing this plan, merge to `master` with CI
green; cut `v3.0.0` only after Phase 8's full gate.

## Open questions for the owner (decide before Phase 1/5)

1. **One workspace or many per install?** Proposal: schema and core support
   many (the cost is one column), but v3.0 ships a one-workspace UI — the
   bootstrap workspace is the product, and multi-workspace switching lands
   in v3.x only if someone asks. Keeps Phase 3 small.
2. **Per-contact visibility in v3.0?** Proposal: `0008` ships the
   `visibility` column (`shared` default) but no surface uses it yet —
   shared-by-default is the "shared CRM" the blueprint asked for, and
   private rows change search, analytics, and graph semantics everywhere.
3. **Plugin signing beyond sha256?** Proposal: checksum-pinned index only;
   a minisign/sigstore layer is v3.x once there are plugins worth signing.
4. **Default marketplace index location?** Proposal: raw file URL of this
   repo's `marketplace/index.json`, overridable via `MARKETPLACE_INDEX_URL`;
   no central service, ever.
5. **Card ownership in teams?** Proposal: one card per workspace (the
   workspace's public identity); per-member cards deferred — `viewed_card_id`
   already exists for that future.
6. **Keep workspace versions at `X.Y.0`?** — `3.0.0`, per the v1.5/v2.0/
   v2.5 precedent. Yes.
