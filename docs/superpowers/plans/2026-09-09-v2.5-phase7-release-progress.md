## Decisions

### Where views live-PG coverage lives

The plan's "new test totals for views + content" reads, at face value, like
"add two integration suites to the postgres job." Content already had one
(Phase 4, `src/content/postgres.integration.test.ts` — url_norm UNIQUE
backstop, JSON-mode round-trips, LOWER() tag matching). Views did not, and
the honest question was whether to add a symmetric
`src/views/postgres.integration.test.ts`.

It would have duplicated the beacon unit tests: the ingestion path's only
dialect-sensitive surface is a handful of portable SQL predicates, already
covered on SQLite across `views/*.test.ts`. What *wasn't* covered anywhere on
a real server was the analytics read path at scale — `substr` day-bucketing,
the `COUNT(DISTINCT COALESCE(...))` uniqueness expression, the
partial-index filters, the zero-filled series — over 10k rows with a real
query planner. So the coverage went into the release pass instead:
`getViewsOverview` now runs against live Postgres with a fixture whose exact
expected totals are computed at seed time with the same predicates the core
applies (non-bot, non-owner, in-window), and the test asserts the planner
agrees to the row. Speed *and* correctness, one fixture, in the job that
already exists. A separate suite would have re-tested the writer twice and
the reader never.

One real bug-shaped near-miss found while writing it: the stats metric is
`COUNT(DISTINCT resolved_contact)` — *distinct contacts*, not resolved rows.
The first fixture expectation counted rows and failed by 838. The test was
wrong, the code was right — which is exactly the kind of misunderstanding a
seed-time expectation is supposed to surface.

### The Docker smoke got the new boundary, not just the old one

Every release since v2.0 Phase 6 has proven the auth boundary in a
production build because that is where the UntrustedHost class of bug lives.
v2.5 added public routes for the first time since the card, so the smoke now
checks both sides of that line in the image: the new owner-only surfaces
must 401, and the beacons must stay *public and inert* — 200, `no-store`,
`nosniff`, no `Set-Cookie`, CORS preflight 204. A pixel that starts setting
cookies or a views API that starts answering 200 anonymously is a privacy
regression, and those are checked where the app actually ships.

### The cut itself

The plan's last item — tag `v2.5.0`, GitHub Release, milestone — needs the
merge commit to exist. This phase's PR ships everything the cut requires and
documents the remaining mechanical steps for the maintainer at merge time:

1. Merge the release PR to `master` with CI green.
2. `git tag v2.5.0` on the merge commit; push the tag.
3. Create the GitHub Release for `v2.5.0` with the CHANGELOG
   `[2.5.0]` section as the notes (the v2.0.0 precedent).
4. Close the `v2.5` milestone (or create it first if it does not exist) and
   confirm the README roadmap reads complete.

## Performance pass: 5k contacts / 20k edges / 10k views / 1k content / 5k metrics

Measured on the sandbox for this work: **PostgreSQL 18.4** (npm
`@embedded-postgres` binaries), local, untuned, 4-connection pool, the same
deterministic LCG fixture the v2.0 pass uses — so the same graph is measured
on every machine, now with the Observer tables beside it. Timings are
**medians of 3 runs**, taken at the core entry points behind each route
(`getNetworkOverview`, `getViewsOverview`, `listContentSummaries`,
`getContentOverview`, `getNetworkGraph`, `searchContacts`,
`planIntroPaths`) — not HTTP, Next rendering or auth.

| What | Endpoint | Run 1 | Run 2 (recorded) |
| --- | --- | --- | --- |
| Dashboard, full payload (graph + views + content) | `GET /api/analytics` | 439 ms | **485 ms** |
| Dashboard without graph/views/content | `GET /api/analytics?graph=0&views=0&content=0` | 69 ms | **67 ms** |
| Views overview (stats + timeline + matches) | `GET /api/card/views` | 21 ms | **16 ms** |
| Content list (50 rows, engagement attached) | `GET /api/content` | 5 ms | **5 ms** |
| Content "At a glance" overview | (dashboard strip / `/content`) | 42 ms | **41 ms** |
| Graph overview | `GET /api/graph/overview` | 330 ms | **346 ms** |
| Search keyword / hybrid | `GET /api/search` | 36 / 45 ms | **37 / 35 ms** |
| Pathfinder (10 plans) | `GET /api/graph/paths` | 148 ms | **161 ms** |

Fixtures: 5k contacts / 20k edges / 10k profile views (~5% bots, ~2% owner
views, ~10% DNT-minimal rows, ~30% resolved) / 1k content items / 5k metric
snapshots; seed ~4.1 s + keyword index ~2.8 s, off the request path.

Three readings:

1. **The Observer is cheap on a real planner.** The views overview costs
   ~16 ms at 10k views on Postgres — the plan budgeted 100 ms — and the
   content surfaces are single-digit milliseconds. The dashboard's full
   payload (~485 ms, budget 500 ms) is still ~85% graph (Louvain +
   betweenness over 20k edges), not views or content: turning those two
   blocks off moves the number to ~67 ms. Nothing in v2.5 moved the
   dashboard's cost profile.
2. **Both budgets hold on both dialects.** The Phase 6 hermetic SQLite
   budget test (10k views / 1k content, budgets 500/100/100 ms) passes in
   every `npm test`; this pass confirms the same entry points inside budget
   on PostgreSQL 18.4 with a real planner, real round-trips and real
   partial indexes.
3. **Jitter is real; the smoke-alarm style holds.** Run-to-run spread on the
   graph-heavy rows was ~10–20% (439 → 485 ms), which is why the pass
   asserts loose multiples and this doc records both runs instead of the
   flattering one — same discipline as the v2.0 cut.

## What is still open after the cut

Nothing in v2.5 is unfinished. The carry-over list is deliberate scope,
written down in the CHANGELOG's `### Deferred — v2.5 deliberately does not
ship` and mirrored in the README: no cross-day viewer tracking, no
deanonymization of strangers, no platform metric integrations beyond the
disabled stubs, and no cookies/third-party scripts in the observer features
— plus the items carried over from v2.0. The only mechanical remainder is
the tag + GitHub Release + milestone at merge time, enumerated above.
