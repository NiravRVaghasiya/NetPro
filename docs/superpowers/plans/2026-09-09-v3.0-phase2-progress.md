## Repository analysis and phase selection

- The v3.0 roadmap's **Suggested order of implementation** puts Phase 2 after
  Phase 1 as the tenancy milestone that makes anything multi-user safe: "the
  teeth; nothing multi-user is safe before it." Phase 1 (workspaces schema &
  auth) and Phase 4 (key vault) are already merged. Phase 2 is therefore the
  next critical-path work.
- Phase 1 already stamps `workspace_id` on writes (many hard-coded to
  `'default'`) but **queries are still unscoped** — every exported core
  function reads "all rows". This PR starts the core-wide scoping on the
  shared CRM (contacts / interactions / follow-ups / timeline / activity /
  contact resolution), which is the center of team mode and the highest
  cross-tenant risk, and wires the web CRM routes to pass the principal's
  scope. It does **not** claim Phase 2 is complete: analytics, search, views,
  content, graph, events, campaigns, retention/reindex/beacons, the CLI
  `--workspace` selection, and per-user GDPR remain to be scoped.

## Implementation

### Scope helpers (`packages/core/src/workspaces/scope.ts`)

- `BOOTSTRAP_WORKSPACE_ID` (`default`), `SYSTEM_USER_ID`, `bootstrapScope()`,
  `resolveScope()`, and `workspacePredicate()` — a single seam for every core
  query. An un-scoped call resolves to the bootstrap workspace so single-owner
  installs behave exactly as before (the compatibility guarantee). Export a
  `WorkspaceScope` re-export so consumers can import one type.
- Scoping is enforced *in the core*, never trusted to a caller: a surface may
  only supply a scope it already derived from an authenticated principal; there
  is no request-supplied `workspace_id` that could widen a query.

### Scoped core module (CRM)

Every exported data-touching function gains an optional `scope?: WorkspaceScope`
(appended, so existing callers are source-compatible) and adds an explicit
`workspace_id = ?` predicate on both dialect branches:

- `ai/resolve-contact.ts` — `resolveContactRef`, `getContactById`,
  `findCandidates`.
- `crm/interactions.ts` — `logInteraction` (stamps `workspace_id` + the
  new `created_by_user` from the scope), `recomputeContactStats`,
  `getContactStats`, `listInteractions`, `countInteractions`,
  `campaignExists`, `loadScoredInteractions`.
- `crm/follow-ups.ts` — `createFollowUp` (stamps workspace + author),
  `listFollowUps`, all bucket/count selectors, `completeFollowUp`,
  `snoozeFollowUp`, `cancelFollowUp`, `getFollowUp`, `resolveFollowUpId`,
  `countFollowUps`.
- `crm/contacts.ts` — `listCrmContacts` (including the workspace-filtered
  correlated follow-up subquery).
- `crm/timeline.ts` — `getContactTimeline` threads the scope through.
- `crm/activity.ts` — `writeActivityLog` stamps the scoped `workspace_id`.

### Authorship migration `0010_authorship.sql` (both dialects)

- Adds `created_by_user` (text) to `interactions` and `follow_ups`, plus
  `idx_interactions_author` / `idx_followups_author`. Column added to both
  Drizzle schemas and the migration journals. Historical rows are left `NULL`
  (an author cannot be inferred in pure SQL; documented — the plan's
  "backfill to the bootstrap owner" is not deterministically expressible and is
  intentionally not fabricated).
- New CRM writes stamp `created_by_user = scope.userId` (or `null` on the
  system/bootstrap path).

### Scope-guard test helper + suite

- `workspaces/scope-guard.ts` — `createTwoWorkspaceFixture()` seeds the
  bootstrap workspace plus a second `acme` workspace, one owner member each.
- `workspaces/scope-guard.test.ts` — 7 tests asserting cross-tenant isolation
  for the CRM module: list, get-by-id, resolve, log/recompute, timeline,
  follow-ups, and the un-scoped-bootstrap compatibility path. This is the
  hermetic SQLite pass; the live-Postgres job mirrors it per dialect.

### Web wiring

- `apps/web/lib/authz.ts` — new `requireScope(minRole?)` returns the
  authenticated principal as a `WorkspaceScope` (reuses `requireMembership`).
- CRM API routes now derive scope from the session and pass it into the core:
  `api/interactions`, `api/follow-ups`, `api/follow-ups/[id]`,
  `api/contacts`, `api/contacts/[id]`. Route tests mock `@/lib/authz` to grant
  a bootstrap scope (unit tests don't run the proxy/NexthAuth boundary).

## Deliberate plan adjustments

1. **Scope of this PR is the CRM engine, not all of Phase 2.** Analytics,
   search, views, content, graph, events, campaigns, retention/reindex/beacons,
   CLI `--workspace`, and per-user GDPR retain their documented dependencies and
   are the next milestones. The phase-progress doc is explicit so a reader does
   not mistake this for certified tenant safety across every surface.
2. **CLI workspace selection is not shipped here.** The CLI calls these scoped
   functions without a scope, which resolves to the bootstrap workspace — the
   compatibility guarantee. A `--workspace` flag (and `netpro config` binding)
   should land with the remaining module scoping so it is actually meaningful.
3. **Authorship backfill is left `NULL`, not fabricated** (see migration note).
4. **Optional appended `scope` parameter (not a required one)** keeps the entire
   v2.5 CLI/web/test surface source-compatible — the house rule.
