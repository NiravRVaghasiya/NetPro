# v2.0 Phase 2 — Graph analytics engine — progress & verification

Implements Phase 2 of the [v2.0 plan](2026-09-07-v2.0-implementation-plan.md),
building directly on [Phase 1's edge provenance](2026-09-07-v2.0-phase1-edge-provenance-progress.md).

## What shipped

Core engine (`packages/core/src/graph/`):

- **`analysis.ts`** — one filtered read pass over `edges` + a live-contact
  projection, joined in pure JS into `LoadedGraph` (undirected simple
  adjacency for clustering/centrality; a directed out-list for the pathfinder).
  Filters: `status` (default `confirmed`; `all` = confirmed+pending;
  `rejected` is never selectable), `relation` (whitelist), `minConfidence`.
  Edges touching missing/soft-deleted contacts are dropped and counted as
  `dangling`.
- **`louvain.ts`** — Louvain modularity optimization in **pure TS** (two
  phases: local moves with the classical ΔQ gain rule, then contraction with
  internal weight folded into super-node self-loops; up to 3 levels).
  Deterministic by construction: nodes swept in sorted-id order, equal gains
  resolve to the lowest community index.
- **`centrality.ts`** — degree centrality + Brandes betweenness (unweighted,
  undirected posture: a `bidirectional=false` row still proves a two-way
  *connection*; direction gates traversal only). Normalized
  betweenness = raw / ((n−1)(n−2)/2).
- **`communities.ts`** — `getCommunities()` → `{ communityId, members,
  modularity }`, communities labeled by dominant normalized company, else
  `Community N`.
- **`paths.ts`** — `shortestPaths()` (bounded-k layered BFS honoring
  `maxDepth`, default 4 per the blueprint) and `findIntroPaths()` (validated,
  structured errors, hop annotations: relations, min confidence/strength,
  `oneWay`).
- **`network.ts`** — `getNetworkGraph()`: stats + coverage, Louvain
  communities, centrality, union-find components, exact average path length,
  and warm-intro candidates.

Integration:

- `analytics/overview.ts` appends `getNetworkOverview`'s new `graph` section to
  the shared `Promise.all` (opt out with `includeGraph: false`);
  `analytics/index.ts` re-exports the graph entry points per the plan.
- CLI: `netpro analyze --graph` section (now one of four mutually exclusive
  section flags); `--json` carries the whole payload.
- Web: `GET /api/analytics` returns the graph payload (`?graph=0` opts out);
  `/dashboard` gained a **Network graph** strip — communities by size, most
  connected, components/avg-path line, warm-intro candidates, pending-edge
  nudge, onboarding empty state, degraded-cap notice — server-rendered, no
  client JS.

## Decisions taken (plan's open questions)

1. **Pure-TS Louvain, not vendored graphology** (plan open question #1).
   Measured against the plan's own budget — 3,000 nodes / 8,000 edges full
   pipeline (load + Louvain + degree + components + intros) in **106.8 ms**,
   vs a 500 ms dashboard budget — vendoring buys nothing the policy of "no
   new runtime deps unless justified" can't live without. Pinned in the perf
   test so a regression shows up as a failing gate, not folklore.
2. **Betweenness / APL budgets, honest skips**: Brandes (O(V·E)) is skipped
   above 1,500 nodes with `skippedReason` reported; exact average path length
   above 600 nodes reports `value: null` + note. The 3,000-node perf case
   confirms the skip fires and that nothing accidentally costs O(V·E) on the
   request path. Above the 50k-edge cap (plan's documented limit) the whole
   analysis degrades to a notice — the dashboard keeps working.
3. **Warm-intro candidates definition** (plan: "high-target contact, no direct
   edge, exists path"): for the top-`limit` hubs by degree, BFS finds contacts
   at 2..maxDepth hops with **no direct edge** to the hub; the reported `via`
   is the strongest-tie node on the chain (ties: closer to the hub). Ranking
   is deterministic (hub degree, hops, via score, ids). Phase 3 layers the
   ranked k-shortest ask UX on top; Phase 2 ships the list only.
4. **No migration needed**: Phase 1's `0003` shipped every column and index
   this phase reads. Migrations stay byte-identical; CI's live-Postgres job
   exercises both dialects.

## One bug caught by writing the tests honestly

The pathfinder's reverse traversal for bidirectional rows initially
self-pointed (the shared row kept its original `targetId`), so `b → a` never
walked back a confirmed `a ↔ b` edge. Fixed by storing the
traversal-oriented copy per direction, with a dedicated regression test
(`traverses bidirectional rows in BOTH directions (regression: out-list
copies)`). The pre-fix one-way assertion "passed" only by accident — that's
the value of asserting the *symmetric* case explicitly.

## Deferred / out of scope (per plan)

- No persistent graph DB, no streaming updates, no temporal analytics, no
  graph-canvas visualization (the v2 deliverable is the list/table form).
- `strength × confidence` weighting for Louvain/Brandes (the code keeps a
  weight hook in `toWeightedAdjacency` so the later change is small).
- Ranked "who exactly should I ask" k-shortest UX → Phase 3 (`/graph`,
  `netpro path`, draft-the-intro via `packages/core/ai`).
