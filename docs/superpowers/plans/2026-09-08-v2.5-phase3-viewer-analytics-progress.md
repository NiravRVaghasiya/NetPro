# v2.5 Phase 3 — Viewer analytics surface (CLI + web + API) — progress

Implemented against
[docs/superpowers/plans/2026-09-08-v2.5-implementation-plan.md](./2026-09-08-v2.5-implementation-plan.md).

## What shipped

`profile_views` — hardened in Phase 1, producing rows since Phase 2 — is now
queryable. Every surface the owner touches reads one core composition, so the
CLI, the API, and the pages can never disagree about a count.

- **Core `@netpro/core/views` additions** (`packages/core/src/views/`,
  exported from `core.views`):
  - `analytics.ts` — the query side:
    - `getViewStats(conn, { days, limit, includeBots, includeOwnerViews,
      now })` — windowed totals (views, unique viewers, resolved
      contacts, avg read duration), a zero-filled daily series, and
      referrer / country / page breakdowns. Uniqueness is
      `COUNT(DISTINCT COALESCE(viewer_fingerprint, viewer_ip,
      session_id))`, so DNT minimal rows (fingerprint-less by design) and
      IP-less views still count sanely.
    - `getRecentViews` — the newest-first timeline with resolved *live*
      contacts (`LEFT JOIN … AND deleted_at IS NULL`: a view attributed
      to a since-deleted contact renders unattributed) and limit/offset
      pagination.
    - `getTopReferrers` — the cheap single-query ranking the dashboard
      strip uses without paying for the full payload.
    - `getViewerContactMatches` — views attributed to known contacts via
      a signed `?v=` link, newest first; bots and owner views stay
      excluded even here.
    - `getViewsOverview` — the `{ stats, recent, matches }` composition
      all three surfaces share.
    - `ViewsError` (`invalid_input` / `not_found` / `conflict`, the house
      vocabulary) + `VIEWS_MAX_DAYS = 90`, `VIEWS_DEFAULT_DAYS = 30`.
  - Privacy rules enforced in the core, not trusted to callers: bots and
    owner views excluded unless opted in (excluded counts ride along in
    every payload); `days` capped at the 90-day retention window (wider is
    a validation error — it would silently under-report purged history);
    future-stamped rows fall outside every `[since, now]` window.
  - Portable SQL on both dialects: `viewed_at` is ISO text everywhere, so
    day bucketing is `substr(viewed_at, 1, 10)` and booleans compare with
    `= true/false` (the Phase 1 `owner.ts` pattern). Referrers fold to
    hosts in JS (`foldReferrerHosts`) because SQL cannot parse hosts
    portably; unparseable legacy values keep their own bucket.
  - `COUNT(*)` / `AVG()` arrive as strings on Postgres — every numeric is
    normalized with `Number()` at the read site (verified by reading the
    pg driver path; the live-PG suite covers the dialect in CI).
- **Analytics overview** (`packages/core/src/analytics/`):
  `NetworkOverview` gains the `views` block (`includeViews: false` opts
  out, `views: { days, limit }` forwards the window — the `includeGraph` /
  `graph` precedent), defaulting to the dashboard's compact 30-day /
  5-row shape.
- **CLI:**
  - `netpro card --views [--days 30] [--limit 10] [--include-bots]
    [--include-owner-views] [--json]` — summary + per-day bars +
    referrers + recent + known visitors. `--input` moved from a Commander
    `requiredOption` to code validation so generation (offline,
    file-driven) and views (database-driven) can have different
    requirements; generation flags are refused in views mode and vice
    versa, `--generate` is ignored in views mode, and generation still
    never touches the database (existing offline test untouched).
  - `netpro analyze --views` — the fifth mutually exclusive section flag;
    `--days` doubles as the views window here (default 30, core validates
    the 90-day cap). `--days` lost its Commander `"90"` default for the
    same reason (the value now defaults in `toAnalyzeOptions`, which
    already handled `undefined`). The full report and `--json` carry the
    views block too — both text renderers share one `renderViewsSection`,
    so `card --views` and `analyze --views` print identically.
- **Web:**
  - `GET /api/card/views?days=&limit=&offset=&includeBots=&includeOwnerViews=`
    (`apps/web/app/api/card/views/`) — owner-only, `private, no-store`,
    lenient params in the house style (garbage falls back, out-of-range
    clamps, effective window echoed in `stats.window`), errors via the
    shared `crmErrorResponse` (now mapping `ViewsError`).
  - `GET /api/analytics` gains the `views` block with a `?views=0`
    opt-out (mirrors `?graph=0`).
  - `/dashboard` gains the “Profile views” strip: totals, a
    server-rendered SVG sparkline, top referrers, recent views with
    contact links, and an onboarding empty state.
  - `/settings/card` gains the analytics section (`analytics-panel.tsx`,
    dumb/presentational): 7/30/90-day links, a show/hide-bots toggle, stat
    cards, the per-day table, referrer/country tables, the recent timeline
    with contact links, and known visitors. Tables, no chart library, no
    client JS.
  - Proxy: no rule change needed (`/api/*` defaults to 401), with a
    regression test pinning that `/api/card/views` does NOT prefix-match
    the public `/api/card/view`.

    for dormancy (no views-window leak into the full report), `--json`

    generation still offline.
  - Web: API 200 shapes, window widening, timeline pagination, bot opt-in,
    clamp/fallback + window echo, empty-DB zeroes; proxy 401s for
    `/api/card/views` (anon) / 200 (owner) with beacons still public;
    `?views=0` omission; dashboard strip + empty state; settings section
    incl. `?days=`/`?bots=` forwarding, clamping, and auth-before-fetch.
- Adversarial coverage: referrer `https://blog.example/post/42?token=SECRET`
  folds to `blog.example` without the query; `days=365` clamps (web) or
  400s via core validation (CLI); `limit=500` clamps to 50; garbage params
  fall back; a bot following a signed link never appears in matches; a
  signed link to a deleted contact renders anonymous; future rows are
  invisible to every query.

## Notes / decisions vs the plan

- **One composition, three surfaces.** The plan lists four core functions;
  they ship plus `getViewsOverview`, which the CLI, `GET /api/card/views`
  and `getNetworkOverview` all call — the cheapest way to guarantee the
  surfaces never disagree.
- **Sections, not tabs, on `/settings/card`.** The plan's “Analytics tab”
  ships as a stacked analytics section above the tracking panel: tabs would
  need client JS, and the house pattern is server-rendered. Same content
  (series, referrers, countries, timeline, contact links), plus 7/30/90-day
  GET links and a show-bots toggle instead of a JS tab switch.
- **No new disable toggle.** “Toggle to disable tracking” is already the
  `NETPRO_DISABLE_VIEWS` env knob with its Disabled state in the tracking
  panel; a second, DB-backed toggle would be two sources of truth.
- **`netpro card --views` reuses `--days`/`--limit`, not `--views-days`.**
  Separate flags were considered for `analyze` too, but overloading keeps
  one vocabulary (`--days` = “window”, `--limit` = “rows”) and the full
  report is careful to never leak its dormancy `--days` into the views
  block (pinned by test).
- **The full `analyze` report and `--json` include views.** The plan only
  requires the `--views` section, but “omit all for the full report” should
  mean everything, and the dashboard already shows the strip — a CLI that
  hid it would be the inconsistent one.
- **Web params are lenient (house style), CLI/core strict.** Garbage
  `?days=` falls back and `?days=365` clamps on the web (the response
  echoes the effective window); the CLI surfaces the core's `ViewsError`
  instead. Same split as search/analytics elsewhere in the tree.
- **No migration, no new runtime dependencies, no new indexes.** Phase 1's
  five `profile_views` indexes cover the analytics queries (23 ms at 10k
  proves it); the purge job stays Phase 6 scope.
