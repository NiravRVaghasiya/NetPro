## What shipped

The Phase 4 content model finally has its three surfaces, all reading the
same core functions so a number recorded in one place shows up everywhere:

- **`netpro content` — 18th top-level command**
  (`apps/cli/src/commands/content.ts`, registered in `cli.ts` after
  `events`; `apps/cli/src/cli.test.ts` grows the exact command list to
  18). Seven subcommands, all with `--json`:
  - `list [--platform --tag --days --query --limit]` — newest-published
    first, undated last, engagement attached per row via the batched
    summaries (latest-known views, or likes when a platform reports no
    views), `N tracked · M with metrics · K snapshot(s) · J mention(s)`
    footer.
  - `add <url> [--title --platform --type --published-at --author
    --tags --summary]` — idempotent on the normalized URL: a re-add
    reports the existing row instead of erroring.
  - `show <id|url> [--metrics]` — one piece, latest snapshot, mention
    list; `--metrics` prints the series.
  - `import --file <csv|xml> [--dry-run]` (plus `--platform` / `--source`
    overrides) — idempotent, per-row errors/warnings printed, dry run
    previews without writing.
  - `fetch <id|url> --manual --views …` — manual snapshots; the auto path
    resolves providers and explains `not_configured` naming the key, with
    `--manual` deliberately bypassing provider resolution entirely.
  - `rm <id|url>` — explicit children-first delete.
  - `analyze [--days]` — windowed overview (top 5 + platform breakdown);
    distinguishes the all-time-onboarding empty state from a windowed
    empty summary (`N undated items sit outside the window`), and renders
    a snapshot's age once (`(YYYY-MM-DD, Nd ago)`).
- **Owner-only `/api/content` API** (proxy boundary; `private, no-store`):
  - `GET /api/content` — list + engagement via `listContentSummaries`
    (bounded list params; no implicit window — the caller opts in with
    `days`, clamped 1–365; limits 50 default / 100 max; unknown platform
    → 400 naming the whitelist; over-long query → 400).
  - `POST /api/content` — add one piece (`url`, `title`, `platform`,
    `type`, `author`, `tags`, `publishedAt`; duplicate URL → 201
    `created: false` with the existing row untouched), or import
    (`{ csv }` | `{ feedXml }`, `?dryRun=1` / `{ dryRun: true }`
    previews), or a `multipart/form-data` upload (`file` field, CSV or
    feed XML by content sniff, capped at 1 MiB → 413). 415 for
    non-JSON, 413/400 discipline from the shared `crm-request` helpers.
  - `GET/DELETE /api/content/[id]` — id-or-exact-URL selectors (tracking
    junk tolerated — the same canonicalizer that keys dedupe); detail
    returns latest snapshot + counts + mentions.
  - `GET/POST /api/content/[id]/metrics` — series oldest-first (365
    snapshots default, `days` clamp) / append a manual snapshot (≥1
    metric, never an update; fractional/negative → 400; `0` is a
    reported zero and is allowed).
  - `POST/DELETE /api/content/[id]/mentions` — link/unlink by contact id,
    email, or exact name (`contactId | contact`, `context?`); ambiguous
    names → 400 listing candidates, never a guess; unknown content or
    contact → 404.
- **`/content` (list page)** — GET-form filters (platform select,
  7/30/90 window, exact tag, title/URL/author query), status line, rows
  linking to detail pages with engagement, and the "At a glance" overview
  (top performers by latest-known views + per-platform breakdown with
  links into the filtered list). Panels: `AddContentForm` and
  `ImportContentPanel` (dry-run-first CSV/feed import; per-row problems
  rendered).
- **`/content/[id]` (detail page)** — the piece itself (URL, tags,
  summary, published), its latest snapshot and full history in
  server-rendered tables, its contacts with contexts and unlink actions,
  `RecordMetricsForm` (manual snapshot), `AddMentionForm`,
  `RemoveMentionButton`, and `RemoveContentButton` (confirm + navigate
  back to `/content`). Missing metrics render "—": unreported never
  looks like zero.
- **Nav, edge, dashboard, contacts:**
  - "Content" link in the app nav (`(app)/layout.tsx`);
  - `/content` under the `/login` 307 redirect and `/api/content*`
    401/200 rows in `proxy.ts` + `proxy.test.ts`;
  - `/contacts/[id]` "Content" section (empty-state guidance + list of
    the person's content with platform and date);
  - `/dashboard` "Content" strip — items · measured · latest-known views
    · platform mix · top 3, hidden until the first item exists.
- **Core follow-up:** the three-query enrichment behind
  `getContentOverview` was factored into `enrichSummaries` and exposed as
  `listContentSummaries` — list surfaces (CLI list, API list, `/content`
  table) read engagement with three batched `IN` queries, never per-item
  round-trips.

## Notes / decisions vs the plan

- **The JSON `rows` import path did not ship in the web API.** Import
  JSON bodies accept `csv` or `feedXml` (plus the multipart upload); the
  core's `rows` option stays available to internal callers. A "send
  pre-parsed rows" endpoint would only ever be called by this codebase
  itself.
- **List pages opt into windows.** A bare `GET /api/content` is the whole
  library, newest first — no surprise 30-day default — while the page
  offers explicit 7/30/90 windows and `analyze` / the dashboard read the
  same `getContentOverview`.
- **One row formatter for CLI + API.** The list row prints engagement
  when the latest snapshot has views (or likes when a platform reports no
  views); rows without snapshots are unchanged, so plain-library output
  stays terse.
- **Dashboard/contact sections are additive and empty-state-gated** —
  they render nothing until content items exist, keeping the earlier
  dashboard tests stable (their teardown now also clears the content
  tables).
- **Page render tests stub `panels.tsx` client components** (house
  pattern, same as events) and seed dates relative to the wall clock,
  since server pages render "today" / "Nd ago" against the real clock;
  route tests use a fixed clock through the shared test sqlite
  connection.
- No new runtime dependencies.
