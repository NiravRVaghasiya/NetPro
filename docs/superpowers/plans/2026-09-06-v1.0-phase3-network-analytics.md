# NetPro v1.0 Phase 3 Implementation Plan — Network Analytics

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the analytics engine (network metrics, composite score, growth, diversity, clusters, dormant ties) in `packages/core`, wire it into `netpro analyze` (CLI) and `/dashboard` + `GET /api/analytics` (web), and make LinkedIn import persist the "Connected On" date so growth and dormancy are truthful.

**Architecture:** One new module `packages/core/src/analytics/` (`types`, `metrics`, `growth`, `clusters`, `dormant`, `overview`). All functions take the existing `SqliteConn | PgConn` union and an injectable `now?: Date`; aggregation is a single portable projection query + pure JS, so there is no dialect branching anywhere in the module. CLI and web are thin formatters over `getNetworkOverview`.

**Tech Stack:** TypeScript (strict), Drizzle `sql` templates (ANSI only), Vitest with an in-memory SQLite harness identical to the Phase 2 tests, server-rendered inline SVG for the dashboard chart. **No new dependencies.**

## Global Constraints

- All Phase 1 plan constraints carry over: pins on `typescript@^5`, `commander@^14`, `better-sqlite3@^12` stay untouched; no new HTTP clients; `crypto.randomUUID()` for IDs; expect `SqliteConn | PgConn` union quirks (though this module should need zero branching by design).
- **No new npm dependencies** — no chart libraries, no graphology, no date libraries. Date parsing/bucketing is hand-rolled (LinkedIn dates are a fixed small format set).
- All `now`-relative math goes through an injected `now` parameter — no frozen timers in tests.
- SQL stays ANSI (no `strftime`, no `date_trunc`) so SQLite and Postgres behave identically; bucketing happens in JS.
- Every task ends with `git add` + `git commit` for exactly the files that task created or modified.
