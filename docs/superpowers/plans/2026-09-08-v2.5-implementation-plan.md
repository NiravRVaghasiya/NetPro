## What already exists (v2.0 foundation) relevant to v2.5

- `profile_views` table exists since scaffold (`0000`) — columns `viewer_ip`,
  `viewer_agent`, `referrer`, `resolved_contact`, `viewed_page`, `viewed_at`,
  `country`, `city`. **No producer, no indexes, no privacy hardening, no
  retention.** Public `/card` page does not write to it. Spec
  `2026-09-06-v1.0-phase5-profile-card-design.md` explicitly says
  “No `profile_views` writes… Viewer analytics belongs to v2.5.”
- `activity_log` already logs `skills.extracted`, `events.unmatched`, etc.
  but not profile views (intentionally — views are high volume, not audit).
- No content tracking tables. No content provider interface.
- `/card` is public, owner-only editor at `/settings/card`, published snapshot
  separate from draft. Metadata sets `robots: noindex, nofollow` and
  `referrer: no-referrer` — privacy-first baseline already.
- Analytics module `getNetworkOverview` returns health, clusters, graph,
  dormant, growth, follow-ups — but no views or content.
- Search is three-arm hybrid; no content indexing yet.

## The two v2.5 features (blueprint scope)

1. **Profile viewer analytics** — “Who viewed your profile” (last 90 days)
   equivalent, self-hosted, privacy-preserving. A 1x1 tracking pixel / beacon
   on the public card + portfolio/blog embed, hashed IP, bot filtering,
   geo from headers, referrer, optional contact resolution via signed link,
   owner-only dashboard.
2. **Content cross-posting tracker** — Track engagement on cross-posted content
   (blog, Twitter/X, dev.to). Manual + RSS import, provider interface for
   metrics, time-series storage, correlation with profile views and network
   growth.

Deferred from v2.0 that may be opportunistic in v2.5 (not required but noted):

- Per-user encrypted web key storage (Security doc §2.3) — would let web UI
  store BYO keys instead of only server env.
- Native pgvector column + ANN index — optimization for hybrid search.
- Live event discovery providers — `EventDiscoveryProvider` already ships
  disabled; similar pattern for content.

## Phase 1 — Profile views data model & privacy hardening

**Problem.** `profile_views` has existed since `0000` but is producer-less,
has no indexes, stores raw IP (privacy risk), no bot filtering, no retention,
and no way to distinguish owner views.

**Goal.** Make `profile_views` trustworthy, privacy-preserving, and queryable.

### Data model (additive migration `0006`, both dialects)

- Keep existing columns, but **harden**:
  - `viewer_ip` → store **hashed** IP, not raw. Hash = `HMAC-SHA256(daily_salt + ip + UA)`,
    truncated to 16 hex chars. Salt rotated daily via `NETPRO_VIEW_SALT` or
    generated server-side and stored in env. Never store raw IP.
  - Add `viewer_fingerprint` (text, nullable) — hash of IP + UA + accept-language
    for dedup within 24h, not for tracking.
  - Add `is_bot` (boolean, default false) — filtered from analytics.
  - Add `is_owner_view` (boolean, default false) — excluded from counts.
  - Add `session_id` (text, nullable) — ephemeral, random per view, for
    de-duping rapid reloads (same session within 5 min = 1 view).
  - Add `duration_ms` (integer, nullable) — optional, from beacon.
  - Add `utm_source`, `utm_medium`, `utm_campaign` (text, nullable) — parsed
    from query, for campaign attribution.
  - Add `viewed_card_id` (text, nullable) — future-proof for multiple cards,
    defaults to single owner card.

- **Indexes (migration `0006`):**
  - `idx_profile_views_time` on `viewed_at DESC` — timeline queries.
  - `idx_profile_views_resolved` on `resolved_contact WHERE resolved_contact IS NOT NULL`.
  - `idx_profile_views_page` on `viewed_page` — filter by card vs embed.
  - `idx_profile_views_fingerprint_time` on `(viewer_fingerprint, viewed_at)` — dedup.
  - `idx_profile_views_is_bot` partial index `WHERE is_bot = false` — analytics fast path.

- **Retention:** document 90-day default retention for raw views, aggregated
  stats kept longer. Add `activity_log` entry for purge runs, not per view.

### Out of scope

- Cookies, localStorage, fingerprinting for cross-session tracking.
- Storing raw IP, email, or any PII without explicit contact resolution.
- Real-time WebSocket push for views (poll is enough for v2.5).

### Verification

- Migration test: fresh SQLite + live Postgres apply `0006` idempotently.
- Core tests: hash function deterministic with same salt, different with
  different salt; bot detection on known UA list; owner view detection via
  signed token or same IP as recent owner session (heuristic, never auto-block);
  retention query deletes >90d.
- No raw IP ever persisted — test asserts column contains only hex hash.

## Phase 2 — Tracking beacon & ingestion pipeline

**Problem.** No producer writes to `profile_views`. Public `/card` needs a
privacy-preserving beacon that works without JS, without cookies, and without
leaking to third parties.

**Goal.** A public, rate-limited, bot-filtered ingestion path that writes to
`profile_views`.

### Core module `packages/core/views`

- `hashViewerIp(ip, ua, salt)` — HMAC-SHA256, truncated, daily salt.
- `isBot(ua)` — small, vendored bot list (no new dep) + `bot` keyword heuristic.
- `parseReferrer(referrer)` — allowlist, strip query, only store domain + path,
  never full URL with tokens.
- `parseUtm(url)` — extract utm_* params, validate length caps.
- `shouldCountView({ fingerprint, viewedAt, existing })` — dedup: same
  fingerprint within 5 min = skip, same IP hash + same page within 1h with
  identical UA = skip (configurable).
- `recordView(conn, input)` — insert with all hardening, returns `{ counted: boolean, reason }`.
- `resolveContactFromToken(token)` — optional: owner can share card link with
  `?v=base64url(contactId|exp|hmac)` — HMAC with `NEXTAUTH_SECRET`, exp 30d,
  resolves to `resolved_contact` if valid. No auto-resolution from IP/email.

### Ingestion surfaces

- **Web beacon:**
  - `GET /api/card/pixel.gif` — public, no auth, returns 1x1 transparent GIF
    (`Content-Type: image/gif`, `Cache-Control: no-store, no-cache, private`).
    Query params: `p=/card`, `r=referrer`, `u=utm_source`, etc. — all optional.
    Headers: `User-Agent`, `X-Forwarded-For` / `X-Real-Ip` (first IP only),
    `Referer`, `X-Vercel-Ip-Country/City` or Cloudflare `CF-IPCountry` if present.
  - `POST /api/card/view` — JSON alternative for JS beacon (`{ page, referrer, durationMs }`),
    same hardening, CORS `*` for embed use, rate-limited.
  - Both endpoints:
    - Rate limit: 60 req/min per IP hash (in-memory token bucket, no Redis).
    - Bot filter: if `isBot` true, still record but `is_bot=true` and excluded from analytics.
    - Owner view filter: if request has valid owner session cookie, mark `is_owner_view=true`.
    - DNT: if `DNT: 1` or `Sec-GPC: 1`, still count but with minimal fields (no geo, no UA beyond bot check) — document.
    - No cookies set, no `Set-Cookie` header.

- **Public card auto-beacon:**
  - `/card` page includes `<img src="/api/card/pixel.gif?p=/card" width="1" height="1" alt="" />`
    plus optional JS `navigator.sendBeacon('/api/card/view', ...)` for duration.
  - Embed snippet for user's blog/portfolio: documented in `/settings/card` —
    `<img src="https://your-netpro.com/api/card/pixel.gif?p=blog" />`.

- **CLI:** no direct tracking, but `netpro card --generate` includes optional
  pixel URL in generated HTML if `--pixel-url` passed.

### Privacy & compliance

- Document in `docs/deployment.md` and `/settings/card`:
  - What is stored (hashed IP, UA, referrer domain, country/city from headers only),
  - What is NOT stored (raw IP, cookies, fingerprint across days),
  - Retention 90d, aggregation kept,
  - DNT/GPC respected, owner can disable tracking entirely via `NETPRO_DISABLE_VIEWS=true`.
- Add `profile_views` to GDPR export (hashed, not raw) and deletion flows
  (already covered by retention).

### Verification

- Core: hash determinism, bot list, referrer sanitization (strip query, cap 200 chars),
  utm parsing caps, dedup logic (5 min window).
- Route tests: `GET /api/card/pixel.gif` returns GIF, 200, no-store, writes row
  (or skips with reason), 429 when rate limited, 200 even when DNT (minimal row).
  `POST /api/card/view` 400 on oversized body, 415 wrong content-type, 200 on valid.
- Adversarial: `referrer` with JS injection → sanitized; `viewed_page` with `../../etc/passwd` → capped to allowlist (`/card`, `/card/vcard`, `blog`, `portfolio`, `embed`); IP spoof via `X-Forwarded-For` with multiple IPs → first taken, validated as IP.
- No secrets in logs, no raw IP in DB — verified by migration test.

## Phase 3 — Viewer analytics surface (CLI + web + API)

**Goal.** Make views queryable and actionable for the owner.

### Core `packages/core/views` analytics

- `getViewStats(conn, { days, groupBy })` — total views, unique viewers (by fingerprint),
  views by day (time series), by referrer domain, by country, by page, bot vs human,
  owner vs visitor. All queries filter `is_bot=false AND is_owner_view=false` unless
  explicitly opted in.
- `getRecentViews(conn, { limit, offset })` — recent timeline, newest first,
  includes resolved contact if present (join to contacts).
- `getTopReferrers(conn, { days, limit })` — top referrer domains with counts.
- `getViewerContactMatches(conn)` — views where `resolved_contact` not null,
  ranked by recency.

### Surfaces

- **CLI (extend `netpro card` or new `netpro views` / `netpro analyze --views`):**
  - `netpro card --views [--days 30] [--json]` — summary + recent.
  - `netpro analyze --views` — new mutually exclusive section flag (alongside
    existing `--graph`, `--clusters`, etc.) — prints view stats, top referrers,
    timeline.
  - `netpro card --generate` already exists; add `--pixel-url` to embed tracking.

- **Web:**
  - `/dashboard` — add “Profile views” strip: last 30d total, unique, sparkline,
    top referrers, recent views (5 rows) — only when views exist, empty-state otherwise.
  - `/settings/card` — new “Analytics” tab: time series chart (server-rendered table
    for v2.5, no heavy chart lib), referrer breakdown, country breakdown, recent
    timeline with resolved contact links, toggle to disable tracking, embed snippet.
  - `/api/analytics` — extend with `views` block (opt-out via `?views=0`), owner-only.
  - `/api/card/views` — owner-only `GET /api/card/views?days=&limit=` returns stats + recent.

- **API contracts (owner-only unless noted):**
  - `GET /api/card/views` — stats + recent, query `days` (default 30, max 90), `limit`.
  - `GET /api/card/pixel.gif` — public (Phase 2).
  - `POST /api/card/view` — public (Phase 2).

### Verification

- Core: stats aggregation on hand-built fixture (known counts), unique counting
  by fingerprint, referrer grouping, bot/owner exclusion.
- CLI tests: `card --views` parse/exec, `--json` shape.
- Web tests: `/api/card/views` 401 when signed out, 200 with fixture, page render
  tests for dashboard strip and settings tab.
- Performance: 10k views, `getViewStats` under 100ms on SQLite (measured).

## Phase 4 — Content tracker data model & provider interface

**Problem.** No content tracking. Users cross-post blog, Twitter, dev.to but have
no unified view of what performs.

**Goal.** Tables and provider interface for content items and time-series metrics,
privacy-first, offline-capable.

### Data model (additive migration `0007`, both dialects)

- `content_items`:
  - `id` (text PK), `url` (text not null, unique), `title` (text not null),
    `platform` (text not null — whitelist: `blog`, `twitter`, `x`, `devto`,
    `linkedin`, `youtube`, `github`, `manual`, `rss`),
  - `type` (text — `article`, `post`, `video`, `thread`, `repo`),
  - `published_at` (text, nullable), `author` (text, nullable),
  - `tags` (text, JSON), `summary` (text, nullable),
  - `source` (text, default `manual`), `created_at`, `updated_at`.

- `content_metrics`:
  - `id` (text PK), `content_id` (FK to `content_items.id` cascade),
  - `fetched_at` (text not null), `source` (text — `manual`, `rss`, `twitter_api`, etc.),
  - `views` (integer, nullable), `likes` (integer), `comments` (integer),
    `shares` (integer), `bookmarks` (integer),
  - `raw_payload` (text, JSON, nullable) — raw API response for debugging,
  - `created_at`.

- `content_mentions` (optional, for linking content to contacts):
  - `content_id`, `contact_id`, `context` (text, e.g., “co-authored”, “mentioned”),
    PK composite.

- **Indexes:**
  - `content_items(url)` unique, `platform`, `published_at DESC`, `tags` (if supported).
  - `content_metrics(content_id, fetched_at DESC)`, `fetched_at DESC`.
  - `content_mentions(contact_id)`, `content_id`.

### Provider interface `packages/core/content/providers.ts`

```typescript
interface ContentProvider {
  id: string; // 'rss' | 'devto' | 'twitter' | 'manual'
  name: string;
  canFetch(url: string): boolean;
  fetchMetrics?(url: string): Promise<Partial<ContentMetrics>>; // optional, BYO key
  parse?(input: string): Promise<ContentItem[]>; // for import
}
```

- Ship `manual` (always) and `rss` (parse RSS/Atom feed, no network in tests,
  fetch in prod via plain fetch, no new dep) as built-ins.
- `devto`, `twitter`/`x`, `github` as **disabled** stubs implementing the interface,
  requiring BYO key, never auto-called. Document as future providers.
- No scraping: only public APIs, RSS, or manual entry.

### Core `packages/core/content`

- `importContent(input, { source })` — parse CSV/JSON/RSS, dedupe on normalized URL,
  idempotent, supports `--dry-run`.
- `addContentItem(data)`, `listContentItems({ platform, tag, days })`,
  `getContentItem(id)`, `deleteContentItem(id)`.
- `recordMetrics(contentId, metrics)` — append time-series row.
- `getContentOverview(conn, { days })` — total items, total views, top performing,
  growth, platform breakdown.
- `getContentMetricsSeries(contentId, { days })` — time series for chart.

### Verification

- Migration test: fresh DB applies `0007`.
- Core: URL normalization (strip utm, lower host, trailing slash), dedupe,
  platform whitelist, CSV/RSS parsing (alias-tolerant headers), metrics append
  and series query.
- Provider: `rss` parse on fixture, no network; disabled providers throw
  explicit “not configured” rather than 500.

## Cross-cutting notes

### House rules every phase must follow

- **Dual dialect**: every migration ships `postgres/` + `sqlite/` additive SQL
  + snapshot + `_journal` update; no dialect-only features without documented
  degradation.
- **No new runtime deps unless justified** — posture is “pure TS + fetch,
  offline tests”. If an algorithm needs a library, phase plan must justify,
  pin, and measure it.
- **Selectors shared** — `resolveContactRef` stays the one resolver; add
  `resolveContentRef` for content.
- **Owner-only everywhere** — new analytics routes inherit proxy boundary;
  public surfaces (`/card`, `/api/card/pixel.gif`, `/api/card/view`) never read
  contact data, never set cookies, never leak owner existence.
- **Adversarial tests** — validation caps, unknown enums, backdated/future
  timestamps, soft-deleted contacts, ambiguous selectors, idempotency,
  oversized bodies, injection in referrer/utm.
- **No secrets in web client** — AI/embeddings/content provider keys stay
  server-env only; BYO-key only in CLI keychain.
- **Privacy-first** — hashed IP, no cookies, no cross-day fingerprint, DNT/GPC
  respected, bot filtering, owner views excluded, retention documented, opt-out
  via env.

### Risks

| Risk | Mitigation |
|---|---|
| Profile views table grows fast (high traffic) | 90d retention + daily purge, indexes, dedup 5 min window, rate limit 60/min/IP, no per-view activity_log |
| Bot traffic inflates counts | Vendored bot list + `is_bot` flag, filtered from analytics, visible toggle “include bots” for debugging |
| IP hashing collisions or privacy complaints | HMAC-SHA256 with daily salt, truncated but documented, raw IP never stored, DNT minimal mode, opt-out env |
| Content provider APIs cost / rate limits | Disabled by default, BYO key, manual provider always works, fetch is explicit not auto, no background cron |
| RSS parsing drift | Alias-tolerant, no network in tests, fixture-based, graceful degradation |
| Owner views counted | Session cookie check marks `is_owner_view`, excluded from stats, toggle to include for testing |
| Large content metrics time series | Keep only latest per content + last 365d, aggregation query, not per-row log |
| Release slip | Phases 1–3 (views) and 4–5 (content) independently shippable; prioritize views if schedule tight |

Same as v1.0–v2.0: one branch per phase (`arena/<commit>-v2.5-phaseN-…`),
each phase its own PR referencing this plan, merge to `master` with CI green;
