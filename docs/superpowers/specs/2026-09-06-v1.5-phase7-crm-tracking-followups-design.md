# NetPro v1.5 Phase 7 — CRM Tracking & Follow-ups — Design

> Status: Implemented
> Builds on: Phase 1 (Import), Phase 2 (Search), Phase 3 (Analytics),
> Phase 4 (AI Outreach — contact resolution), Phase 6 (Deployment)
> Source blueprints: `NetPro — Blueprint.md` (roadmap v1.5, CLI reference
> `netpro track`, `/contacts` + `/contacts/[id]` page detail),
> `NetPro — DB & Pipeline Deep Dive.md` (§ interactions/follow_ups schema,
> §2.6 `computeRelationshipScore`, index plan)

## Purpose

v1.0 could import, find, analyze, and draft for your network — but nothing
ever *wrote back*. The `interactions` and `follow_ups` tables existed since the
scaffold with no producer, `contacts.lastInteraction/interactionCount/
relationshipScore` were frozen at import values, and three surfaces were
stubs: the core `crm` module (one line), the CLI `track` command ("not yet
implemented"), and the web `/contacts/[id]` page ("Coming soon").

Phase 7 is the first half of v1.5 (CRM tracking + follow-up reminders). It
makes NetPro a working CRM: log every touchpoint, let the relationship score
finally mean something, and never lose track of who you promised to follow up
with. Phase 8 (batch campaigns) builds directly on this — campaign sends are
logged as interactions through the same entry points.

## Scope

**In scope:**

- **Core `crm` module** (`packages/core/src/crm`) — the single write path for
  relationship history, shared by CLI and web exactly like `search`/
  `analytics`:
  - `logInteraction` — validate (whitelisted type/direction/channel, length
    caps), insert the `interactions` row, then recompute the contact's
    denormalized stats: `lastInteraction` (max `occurredAt`),
    `interactionCount`, and `relationshipScore`.
  - `computeRelationshipScore` — the Deep Dive §2.6 formula (recency 40%,
    frequency 25%, depth 20%, richness 15%), computed over the contact's full
    interaction history at write time.
  - `listInteractions` / `getContactTimeline` — per-contact history and the
    detail-page aggregate (contact + recent interactions + pending follow-ups).
  - Follow-ups: `createFollowUp`, `listFollowUps` (overdue / due-today /
    upcoming / completed views), `completeFollowUp`, `snoozeFollowUp`,
    `cancelFollowUp`. Optional recurrence (`every: "30d"`) re-arms the next
    occurrence on completion instead of closing the loop.
  - Every mutation appends an `activity_log` row (`interaction.logged`,
    `followup.created`, …) — the audit trail the schema always promised.
- **CLI `netpro track`** (replaces the stub), matching the blueprint's
  reference:
  - `track log <contact> --note "…" [--type meeting] [--channel] [--direction]
    [--subject] [--at <iso>]`
  - `track add <contact> --met-at "React Conf" [--follow-up 7d] [--at <iso>]`
    — logs a `meeting` interaction and schedules the follow-up in one step.
  - `track list [--due-today | --overdue | --upcoming | --recent | --all]
    [--contact <sel>] [--limit n] [--json]`
  - `track done <followUpId>` and `track snooze <followUpId> --for 3d`.
  - `<contact>` selectors (email / id / unique full name, ambiguity errors
    listing candidates) reuse Phase 4's `resolveContactRef` — one resolver,
    one behavior, everywhere.
- **Web CRM** (replaces the stubs):
  - `GET /api/contacts` (paginated CRM rows incl. next pending follow-up),
    `GET /api/contacts/[id]` (timeline), `POST /api/interactions`,
    follow-up routes `GET/POST /api/follow-ups` and
    `PATCH /api/follow-ups/[id]` (complete / snooze / cancel). All behind the
    existing owner-only proxy boundary; strict body validation with the same
    limits as the core module.
  - `/contacts` — real CRM view: last touch, interaction count, relationship
    score, next follow-up, due-today/overdue summary, pagination; rows link to
    the detail page.
  - `/contacts/[id]` — profile summary, interaction timeline, pending
    follow-ups with complete/snooze actions, and a client panel to log an
    interaction or schedule a follow-up (then `router.refresh()`).
- **Indexes migration (both dialects)** — the Deep Dive's index plan was never
  generated: `interactions(contact_id, occurred_at)`, `interactions(campaign_id)`,
  `follow_ups(due_at)`, `follow_ups(contact_id)`, `contacts(last_interaction)`,
  `contacts(relationship_score)` (Phase 8 adds the campaign_recipients ones).
  Additive `CREATE INDEX` only — safe on existing databases, applied through
  the normal migration runner and its advisory lock.

**Explicitly deferred** (documented, not forgotten):

- **Automatic interaction capture** — IMAP/webhook email ingestion, LinkedIn
  sync, calendar hooks. NetPro v1.5 records what *you* tell it (plus campaign
  sends you confirm in Phase 8); silent background capture is a v2+ concern.
- **Sentiment analysis** (`interactions.sentiment`) — the column stays null;
  AI-scored sentiment belongs with the enrichment/AI roadmap, not the write
  path.
- **Score decay cron** (`decayRelationshipScores`) — the recency factor is
  recomputed from `now` on every write, so scores self-correct at the next
  interaction; a daily decay job needs a scheduler (Inngest/BullMQ/cron),
  which the deployment story doesn't have yet.
- **Reminder *notifications*** (email/push for due follow-ups) — needs the
  delivery infrastructure deliberately kept out of NetPro; due follow-ups
  surface on `/contacts`, `/dashboard`, and `netpro track list --due-today`.
- **Multi-user RLS partitioning** — still single-owner (Phase 5 boundary).

## Key decisions

| Area | Decision | Rationale |
|---|---|---|
| Relationship-score scale | Store 0–1 (blueprint's 0–100 ÷ 100) | Every existing consumer — search `minScore` filter, analytics `avgRelationshipScore`, dashboard, dormant-ties ordering — already treats the column as 0–1, and seed data/tests use that scale. The blueprint's formula is computed verbatim, then normalized once at the write boundary. |
| Score recomputation | Recompute from full history on every `logInteraction` (one indexed SELECT + pure JS) | The formula needs recency/frequency/depth/richness over all interactions anyway; incremental updates would drift. At single-owner volume (10²–10⁴ interactions) a per-write recompute is microseconds on the new index — the same "portable + honest at v1 scale" pragmatism as Phases 2–3. |
| Type/channel/direction vocabularies | Whitelisted, from the Deep Dive comments (`meeting`, `call`, `note`, `email_sent`, `email_received`, `linkedin_message`, `intro_made`; `inbound`/`outbound`; `email`/`linkedin`/`in_person`/`phone`/`other`) | Free-text types would silently fragment analytics and scoring (richness counts *distinct types*). Whitelist + actionable error matches the house validation style. |
| Backdated interactions | Allowed (`occurredAt` in the past, capped at 10 years; future capped at +1 day for timezone slack) | "Log yesterday's coffee" is the core CRM use case. Stats recompute from the *max* occurredAt so a backdated log never rewinds `lastInteraction`. |
| Follow-up completion vs. interaction logging | Independent actions | Completing a follow-up means "I handled it"; logging is a separate truth. `track add --follow-up` creates both in one command because that's the blueprint's workflow, but the web UI keeps them separate buttons. Auto-completing follow-ups on any interaction would erase the "promised to follow up" signal. |
| Recurrence | `recurrenceRule` stores a simple duration (`7d`, `30d`); completing a recurring follow-up inserts the next occurrence (`dueAt + interval`) | The column exists; a full RRULE engine is unjustified for "ping Jane every month". Duration-only covers the real use cases and stays portable. |
| Activity log | Written inside the same call as the mutation, best-effort semantics (never fails the operation) | Auditability was in the scaffold schema with no producer; keeping it in the core module means CLI and web both populate it with zero extra route code. |
| Web data flow | Server components read the core module directly (like `/search`, `/dashboard`); mutations go through JSON API routes called by small client panels | Matches the established pattern: reads are server-rendered and cache-free, writes are validated once in core and reused by both surfaces. No new state library. |

## Data & security notes

- All new reads exclude soft-deleted contacts (`deletedAt IS NULL`); logging
  against a deleted/unknown contact is a 404-class error, never a dangling row
  (FKs already cascade).
- API routes enforce the same caps as the CLI: `subject` ≤ 200,
  `content`/`note` ≤ 5000, `reason` ≤ 500 chars; enums whitelisted; ids are
  server-generated UUIDs. No secrets, no new env vars, no new dependencies.
- The proxy already denies every `/api/*` route without an owner session —
  the new routes inherit that boundary and add body/size validation only.

## Testing strategy

- Core: migrated in-memory SQLite fixture (`createTestSqliteConn` — exercises
  the committed migrations, including the new indexes). Deterministic injected
  `now`. Score formula tested against hand-computed vectors (recency decay,
  frequency cap, direction balance, richness cap); backdating, recurrence
  re-arm, snooze/complete/cancel transitions, activity-log writes.
- CLI: pure `executeTrack*` functions over a test conn (house pattern —
  render/execute split), covering selector ambiguity, duration parsing
  (`7d`/`24h`/`2w`), `--json`, and each list view.
- Web: route tests with mocked `@/lib/db` (in-memory SQLite) covering happy
  paths, validation rejections, 404s, and the owner boundary behavior; page
  render tests for `/contacts/[id]` panel behavior.
- Postgres: schema/index types compile; the existing live-Postgres CI suite
  runs the new migration. Queries stay ANSI-portable by construction (no
  dialect-specific SQL beyond the standard narrowing boilerplate).
