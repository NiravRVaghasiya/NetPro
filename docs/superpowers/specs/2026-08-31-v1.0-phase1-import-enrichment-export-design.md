# NetPro v1.0 Phase 1 — Import, Enrichment & Export — Design

> Status: Approved
> Source blueprints: `NetPro — Blueprint.md`, `NetPro — DB & Pipeline Deep Dive.md`, `NetPro — Security & Auth Architecture.md`
> Builds on: `docs/superpowers/specs/2026-08-30-v0.1-alpha-scaffold-design.md` (the completed v0.1-alpha scaffold)

## Purpose

The blueprint's v1.0 milestone ("The Essentials") bundles together several independent subsystems: import, enrichment, network analytics, federated search, AI outreach, a public profile card, and Vercel deploy. Building all of it in one pass would repeat the mistake the v0.1-alpha scaffold's own design explicitly avoided — this spec covers only the first, foundational phase.

**Phase sequence for v1.0** (agreed before this spec was written):

1. **Import & Data Portability** *(this spec)*
2. People Search
3. Network Analytics
4. AI Outreach
5. Profile Card
6. Vercel One-Click Deploy

Nothing else is usable without contacts existing in the database, so this phase has to come first regardless of feature value — every later phase depends on it.

## Scope

**In scope:**
- LinkedIn CSV import (the one source every user needs first)
- Enrichment via three providers: Hunter.io, People Data Labs, Clearbit
- CSV export
- Both CLI (`netpro import`, `netpro enrich`, `netpro export`) and web (`/import`, `/contacts`, corresponding API routes)

**Explicitly out of scope for this phase** (candidates for later phases or follow-ups, not forgotten):
- GitHub import, manual contact entry, vCard/Google Contacts import
- JSON and vCard export formats
- Full contacts search/filter/facets UI — that's Phase 2 (People Search)
- Per-user API key storage / the full `KeyVault` encryption system from the Security blueprint (rotation, audit logging, blind-index search) — deferred in the v0.1-alpha scaffold, still deferred here
- Background job infrastructure (Inngest/BullMQ) — enrichment runs as an in-process rate-limited async loop, not a durable queue
- Live verification of enrichment providers against real APIs — no API keys are available during this phase's implementation (see Testing Strategy)

## Key Decisions

| Area | Decision | Rationale |
|---|---|---|
| Import sources | LinkedIn CSV only | The core "replace LinkedIn Premium" action; GitHub import can be a fast-follow once this works end-to-end |
| Enrichment providers | All three (Hunter.io, PDL, Clearbit) | User's explicit choice — build the full provider set now against mocked HTTP, since none can be live-tested regardless of how many are implemented |
| Enrichment provider testing | Mocked HTTP responses in unit tests; no live verification | No API keys available. The implementation plan will say this explicitly per task rather than implying false certainty — this is the same "disclose testing gaps honestly" pattern the scaffold plan used for CLI keychain crypto and Docker builds before those were actually verifiable |
| Export formats | CSV only | Simplest, most universally useful, re-importable |
| Surfaces | Both CLI and web | The scaffold already has matching command/route stubs on both; the shared `packages/core` logic is written once and wired into both, keeping them from drifting apart |
| Enrichment API keys — CLI | Read from the CLI's existing `Keychain` (`netpro config set enrichment.hunter <key>`) | Infrastructure already built in the scaffold (Task 8), just unused until now |
| Enrichment API keys — web | Server-side environment variables, host-configured, not per-user | The full per-user `KeyVault` settings system was deferred in the scaffold; building a real (even minimal) encrypted key-storage table is its own scope. Per-user web key entry becomes a later task once `/settings` is built for real |
| Import pipeline shape | Plain async function returning a summary object (`{ imported, merged, errors }`), not an `EventEmitter`-based pipeline | The blueprint's `ImportPipeline extends EventEmitter` pattern exists for live progress reporting during long-running imports; a LinkedIn CSV parses in milliseconds to low seconds, so live progress events are unneeded complexity for this phase |
| Enrichment orchestration | In-process rate-limited async loop (token-bucket limiter, sequential per-provider) | No durable job queue (Inngest/BullMQ) needed yet — BYO-key free-tier rate limits (e.g. Hunter's 25/day) mean enrichment is inherently slow-drip regardless of queue sophistication; a queue is premature until there's real multi-user scale |
| CLI command structure | `enrich` becomes an 8th top-level CLI command (`netpro enrich --source <hunter\|pdl\|clearbit\|all> [--force]`) | The blueprint's own CLI reference treats `import` and `enrich` as separate commands, not flags on one command. This is a disclosed addition beyond the v0.1-alpha scaffold's fixed 7-command set |
| Web contacts view | `/contacts` upgraded from placeholder to a minimal paginated list (no search/filter) | Users need to see what got imported; full search/filter is explicitly Phase 2's job, not duplicated here |

## Architecture

### `packages/core/import`

```
src/import/
├── linkedin-csv.ts     # LinkedInCSVParser: raw CSV → RawContact[]
├── normalize.ts         # name/company/title normalization, seniority extraction,
│                        # fingerprint generation, mergeContacts()
├── pipeline.ts           # runImport(csv, existingContacts) → ImportSummary
└── index.ts
```

`RawContact` and `NormalizedContact` shapes, the fingerprint algorithm (`email:<lowercased>` priority, falling back to `name:<slug>|company:<slug>`), and the merge strategy (prefer non-null incoming values, always take newer full name) follow the blueprint's `DB & Pipeline Deep Dive` doc directly — that logic is already fully specified there and doesn't need re-design.

`runImport()` is a plain async function: parse → normalize → check fingerprints against existing DB rows → batch insert new / update merged → return `{ imported: number, merged: number, errors: ImportError[] }`. No event emitter, no streaming — the whole operation completes and returns.

### `packages/core/enrichment`

```
src/enrichment/
├── types.ts              # EnrichmentProvider interface, EnrichmentResult
├── providers/
│   ├── hunter.ts          # HunterProvider (email-finder + domain-search)
│   ├── pdl.ts              # PDLProvider (person/enrich)
│   └── clearbit.ts         # ClearbitProvider (company enrichment)
├── cache.ts                # EnrichmentCache — reads/writes the `enrichments` table,
│                           # honors each provider's cacheTTL
├── rate-limiter.ts          # LocalRateLimiter — in-memory token bucket, one per provider
├── pipeline.ts               # EnrichmentPipeline.enrichContact() / enrichBatch()
└── index.ts
```

`EnrichmentProvider` interface (from the blueprint, adopted as-is): `id`, `name`, `rateLimit`, `priority`, `cacheTTL`, `canEnrich(contact)`, `enrich(contact)`. Each provider implementation wraps one real HTTP API:

- **Hunter.io**: `email-finder` (needs domain + first/last name) and `domain-search` (company → domain) endpoints. Confidence = Hunter's own `score / 100`.
- **PDL**: `person/enrich` endpoint (accepts LinkedIn URL, email, or name+company). Broadest field coverage: email, role, seniority, location, social URLs, skills, experience history.
- **Clearbit**: company-level enrichment (domain → company name, industry, size). Enriches `contacts.company`/`companyDomain`/`industry`, not person-level fields.

`EnrichmentPipeline.enrichContact(contact)` iterates providers in priority order; for each, checks cache freshness, rate limit budget, and `canEnrich()` before calling out. Results are merged into the contact by per-field confidence (blueprint's existing `mergeResults()` algorithm, adopted as-is). A provider throwing (network error, invalid key, 4xx/5xx) is caught and skipped — one provider failing never aborts the others or the batch.

`canEnrich()` also acts as the API-key gate: if a provider's key isn't configured (CLI Keychain empty, or web env var unset), `canEnrich()` returns `false` and the provider is skipped silently — not an error, since BYO-key means "no key" is an expected, normal state, not a failure.

### `packages/core/export`

```
src/export/
├── csv.ts        # exportContactsCSV(contacts): string
└── index.ts
```

Straightforward field-to-CSV-row mapping over the `contacts` table shape. No filtering logic in this phase (exports everything) — filtered export arrives with Phase 2's search/facets.

### CLI (`apps/cli`)

- `commands/import.ts` — replaces the stub. `netpro import --linkedin <path>` reads the file, calls `runImport()`, prints the summary.
- `commands/enrich.ts` — **new file**, new command. `netpro enrich --source <hunter|pdl|clearbit|all> [--force]` loads contacts missing key fields (or all, with `--force` bypassing cache), runs `EnrichmentPipeline`, prints a per-provider summary (enriched count, skipped count, errors).
- `commands/export.ts` — replaces the stub. `netpro export --format csv` (only `csv` accepted this phase; other format flags print a clear "not yet supported" message rather than silently accepting them) writes to stdout or a `--output <path>` file.
- `config/keychain.ts` — unchanged; enrichment commands call `Keychain.get('enrichment.hunter')` etc., already built.
- `cli.ts` — modified to register the new `enrich` command alongside the existing seven.

### Web (`apps/web`)

- `app/(app)/import/page.tsx` — replaces the placeholder. Client component: file input (drag-and-drop), calls `POST /api/import`, renders the returned summary.
- `app/api/import/route.ts` — **new route**. Accepts a multipart CSV upload, calls the same `runImport()` from `packages/core`, returns the summary as JSON.
- `app/(app)/contacts/page.tsx` — replaces the placeholder. Server component: paginated table (name, company, role, source, relationship score), an "Export CSV" button linking to the export route. No search box, no filters — Phase 2 adds those to this same page.
- `app/api/export/route.ts` — **new route**. `GET /api/export?format=csv` streams `exportContactsCSV()`'s output with a `Content-Disposition: attachment` header.
- `app/api/enrich/route.ts` — **new route**. `POST /api/enrich` with a contact ID or `{ all: true }` in the body, runs `EnrichmentPipeline`, returns a summary. Reads provider keys from `process.env.HUNTER_API_KEY` / `PDL_API_KEY` / `CLEARBIT_API_KEY` (server-side only, never sent to the client).

## Data Flow

```
Import:  CSV upload/file → LinkedInCSVParser → normalize (name/company/title,
         fingerprint) → dedupe against existing contacts (by fingerprint) →
         batch insert (new) / update (merged) → ImportSummary

Enrich:  contact(s) missing key fields → for each provider (priority order):
         cache fresh? → skip. rate-limited? → skip. no key? → skip (not an error).
         else: call API → parse response → cache result (enrichments table) →
         merge into contact by confidence → EnrichSummary

Export:  query all contacts → exportContactsCSV() → CSV string/stream
```

## Error Handling

- **Malformed CSV rows**: skipped individually, collected into `ImportSummary.errors` with the row number and reason — a few bad rows never fail the whole import.
- **Enrichment provider errors** (network failure, invalid key, rate-limit response, malformed API response): caught per-provider-per-contact, logged into the summary, pipeline continues to the next provider/contact. No provider failure aborts a batch.
- **Missing API key**: not an error — `canEnrich()` returns `false`, provider is silently skipped, reflected in the summary as "skipped: no key configured" so the user understands why nothing happened rather than seeing silent no-op.
- **CSV export with zero contacts**: returns a valid empty-but-well-formed CSV (header row only), not an error.

## Testing Strategy

- **Import**: unit tests on `linkedin-csv.ts` (fixture CSV → expected `RawContact[]`), `normalize.ts` (name/company/title/fingerprint edge cases — the blueprint's own test examples for `normalizeTitle`/`generateFingerprint`/`mergeContacts` are directly reusable), and `pipeline.ts` (dedup behavior against a seeded test DB). Fully live-testable — no external dependencies.
- **Enrichment**: unit tests per provider against mocked HTTP responses (request shape assertions, response parsing, error handling), plus pipeline-level tests for cache/rate-limit/confidence-merge logic using a fake provider. **Cannot be verified against real Hunter.io/PDL/Clearbit APIs in this phase** — no keys exist. Each implementation task in the eventual plan will state this limitation explicitly, the same way the scaffold plan disclosed when something couldn't be live-verified (e.g. Auth.js's `next-auth@beta` install, Docker builds before Task 13 actually ran one).
- **Export**: unit test on CSV formatting (field escaping, empty-contacts case, full-field case).
- **CLI end-to-end**: `netpro import`/`enrich`/`export` are testable live (import/export have no external deps; enrich's live path only exercises the "no key configured, skip" branch without real keys — which is itself a legitimate, testable behavior).
- **Web end-to-end**: `/import` and `/contacts` pages, and the three new API routes, are buildable and testable via `next build` + manual verification, same as the scaffold's routes.

## Technical Notes

- **HTTP client**: native `fetch` (Node 20+ built-in) for all three enrichment providers — no new HTTP library dependency, matching the blueprint's own `SecureHTTPClient` pattern.
- **HTTP mocking in tests**: `vi.spyOn(global, 'fetch')` per test, returning a fixture `Response` object — no new mocking library (e.g. `msw`) needed for three providers' worth of request/response shapes.
- **CSV parsing (import)**: a lightweight, well-tested library (`papaparse` or `csv-parse` — pick one at implementation time, don't hand-roll a parser) to correctly handle quoted fields containing commas/newlines, which LinkedIn's export can contain in company names and headlines.
- **CSV formatting (export)**: same library's stringify/unparse function, for symmetric quoting behavior.

## Success Criteria

- `netpro import --linkedin <file>` imports a real LinkedIn export CSV, correctly deduplicates on re-import, and prints an accurate summary
- `netpro enrich --source all` runs against contacts with no configured keys and reports "skipped: no key" for every provider, without crashing
- `netpro export --format csv` produces a valid CSV re-importable by common spreadsheet tools
- `/import` in the web app accepts a CSV upload and shows the same summary shape as the CLI
- `/contacts` lists imported contacts with correct data, and its Export button downloads a working CSV
- All enrichment provider unit tests pass against mocked responses; the plan clearly documents that live provider verification is deferred until real API keys exist
- `npm run lint && npm run typecheck && npm run test && npm run build` all pass repo-wide, same bar as the v0.1-alpha scaffold
