# NetPro v1.0 Phase 4 — AI-Powered Outreach (Drafting) — Design

> Status: Implemented
> Builds on: Phase 1 (Import, Enrichment & Export), Phase 2 (People Search),
> Phase 3 (Network Analytics)
> Source blueprints: `NetPro — Blueprint.md` (MVP "AI Outreach" row, CLI
> reference `netpro outreach`, `/outreach` page detail, milestone "AI-composed
> outreach with BYO API key"), `NetPro — Security & Auth Architecture.md`
> (§2.4 BYO-Key flow, §4.3 anti-spam content guidance, §5.1 outreach input
> validation, rate-limit table for `/api/outreach`)

## Purpose

Phases 1–3 filled the database, made contacts searchable, and made the network
legible. Phase 4 turns that data into *action*: given a contact (looked up from
the database) plus optional extra context, NetPro composes a ready-to-send
outreach message — a subject line plus a short, personalizable body — via a
user-provided LLM API key. This replaces the three outreach stubs: the
`packages/core/src/ai` placeholder module, the CLI `netpro outreach`
"not yet implemented" action, and the web `/outreach` "Coming soon" page. It
also adds the first real **POST** mutation-style API route (`/api/outreach`)
alongside the read-only routes from earlier phases.

The v1 boundary is deliberate and documented: NetPro **drafts**; the user
sends. Nothing in this phase sends email, writes campaign state, or stores
secrets server-side.

## Scope

**In scope:**

- **AI provider abstraction** in `packages/core/src/ai/`:
  - `AiProvider` interface — `id`, `label`, `complete(messages, opts)` →
    text, and a cheap `verifyCredential()` probe.
  - OpenAI-compatible Chat Completions (`POST /v1/chat/completions`) — works
    with OpenAI and any OpenAI-compatible endpoint.
  - Anthropic Messages (`POST /v1/messages`).
  - Both use global `fetch` (no SDK, no new dependencies — same constraint as
    the enrichment providers) and call models that return plain JSON/text;
    default model IDs are overridable via env/config (`ai.openai.model`,
    `ai.anthropic.model`, `ai.openai.baseUrl`).
  - Factory `createAiProvider(providerId, config)` plus
    `resolveAiProvider(creds)` mirroring the enrichment provider factories.
- **Prompt construction** — `buildOutreachPrompt(input)` pure function: turns
  a recipient profile (name, role, company, headline, location, industry,
  LinkedIn/GitHub URLs, existing notes) + sender name + tone + purpose/context
  + optional length into a system + user message pair. Contains the
  house rules: short, specific, no invented facts, no made-up shared history,
  clear low-friction ask, sign off as the sender. Deterministic and fully
  unit-tested without network access.
- **Drafting engine** — `composeOutreachMessage(input, deps)`:
  validates input, builds the prompt, calls the provider, parses the
  `subject` / `body` from the model response (JSON-first with a tolerant
  plain-text fallback that extracts a leading `Subject:` line), and returns a
  structured `OutreachDraft` (`subject`, `body`, `provider`, `model`,
  `tone`, `generatedAt`). Network access is injected (`fetch`/provider
  factory) so tests never hit the real APIs.
- **Credential resolution (BYO-key):**
  - CLI: `Keychain.get('ai.openai.key')` / `Keychain.get('ai.anthropic.key')`
    and `Keychain.get('ai.provider')`, with `AI_PROVIDER` /
    `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `OPENAI_BASE_URL` env fallbacks
    — exactly the established CLI pattern (enrichment keys live the same way).
  - Web: server-side env vars only (`AI_PROVIDER`, `OPENAI_API_KEY`,
    `ANTHROPIC_API_KEY`, `OPENAI_BASE_URL`, optional model overrides) —
    identical in spirit to the Phase 1 web enrichment keys (`HUNTER_API_KEY`
    et al., "server-side, host-configured — no per-user key storage in this
    phase").
- **CLI `netpro outreach`** (replaces the stub):
  - Recipient selectors: `--to <email-or-id-or-name>` resolves a contact from
    the database (by email, id, or case-insensitive full-name match — name
    matches must be unique or the command errors listing candidates), OR
    ad-hoc `--email/--name/--company/--role` flags for drafting to someone
    not in the network.
  - `--context <text>` ("met at React Conf, spoke about WASM"),
    `--tone <warm|professional|casual|friendly>` (default `professional`),
    `--purpose <ask>` (what the sender wants), `--sender <name>`
    (default: `netpro config get user.name` → git `user.name`),
    `--provider <openai|anthropic>`, `--model <id>`, `--json`.
  - Renders subject + body; clear setup error when no key is configured
    ("set one with `netpro config set ai.openai.key sk-...`").
- **Web `POST /api/outreach`** (new route; added to middleware `API_ROUTES`):
  - JSON body: `{ contactId? }` or `{ recipient: {name,email,company,role} }`,
    plus `context?`, `tone?`, `purpose?`, `sender?`, `provider?`, `model?`.
  - 200 → `OutreachDraft` JSON; 400 on invalid input / unresolvable contact /
    duplicate name; 503-style **500 with `code: 'ai_not_configured'`** when no
    server key is present (the UI uses this to render setup guidance); 502
    when the provider call fails; generic 500 otherwise. Auth-gated 401 like
    the other API routes.
  - Tone/context/length validated server-side (length caps per Security doc
    §5.1: subject ≤200 chars-equivalent, context ≤2000, purpose ≤500).
- **Web `/outreach` page** (replaces stub): a client composer — contact
  picker (server component feeds a search/lookup via existing
  `GET /api/search?q=`), tone selector, context/purpose textareas, "Generate
  draft" button, result card with subject + body and copy buttons, and an
  explicit "NetPro drafts — you send" note. Shows a setup banner (pointing at
  `/settings`) when the API reports no AI key configured.
- **`/settings` page**: real (minimal) status panel listing integration
  configuration state (GitHub OAuth, enrichment providers, AI provider) from
  server env presence — booleans only, never secrets. Replaces the
  "Coming soon" stub.

**Explicitly deferred** (documented, not forgotten):

- **Sending email / SMTP / Gmail** — actual delivery, reply tracking, opens,
  bounces. Requires mail infra and deliverability/compliance work; the
  blueprint's SpamGuard (Security doc §4.3) and `campaigns`/`campaignRecipients`
  tables exist for it. v1.5 batch-campaign phase.
- **Batch campaigns & drip sequences** — `/outreach/campaigns`, the
  `--batch ./targets.csv` flag, template merge variables, per-recipient
  personalization loops, daily limits. The campaigns page stays a stub with a
  note. Depends on sending.
- **`--draft` `$EDITOR` review loop** — interactive terminal editing; CLI v1
  prints the draft (and `--json` enables scripted review).
- **Per-user encrypted web key vault** — the Security doc's AES-256-GCM
  `KeyVault` + `user_api_keys` table (§2.3) is the hosted multi-tenant design.
  It ships when web user accounts are a first-class product concern; the
  self-hosted single-owner deployment that v1.0 targets configures keys via
  env, consistent with Phase 1 enrichment. The provider/credential seam is
  built so a vault-backed `getAiCredentials()` can replace the env reader with
  no engine changes.
- **Streaming responses, regenerate/alternate drafts, temperature knobs** —
  engine returns one complete draft; the interface leaves room.
- **Logging drafts to the `interactions` table** — a *generated* draft is not
  an interaction (it was never sent); logging it would corrupt Phase 3's
  dormancy/activity signals. Interaction logging arrives with real sends (the
  CRM/campaign phase), which is also what feeds per-contact relationship
  scoring.
- **OpenAI key-format dry-run verification on save** — keys are read from
  env/keychain, not submitted through NetPro, so there is no save path; a bad
  key surfaces as a provider auth error on first generation with an
  actionable message.

## Key decisions

| Area | Decision | Rationale |
|---|---|---|
| v1 boundary | Draft only; never send | Sending drags in SMTP/OAuth-mail, deliverability, anti-spam enforcement, bounce handling, and campaign state — a v1.5-sized surface. Drafting alone delivers the blueprint's core value ("AI-composed outreach, BYO key") and keeps the phase shippable. Drafts deliberately do **not** write `interactions` (nothing was sent), preserving analytics truthfulness. |
| Providers | OpenAI-compatible Chat Completions + Anthropic Messages, raw `fetch` | Matches the enrichment-provider house style (factory + injected `fetch`, zero SDK deps). The OpenAI-compatible endpoint also covers OpenRouter, local Ollama/LLaMA servers, etc. via `baseUrl`. No new npm dependencies. |
| Provider seam | `AiProvider` interface + `createAiProvider(id, { apiKey, baseUrl?, model? })`; engine takes an injected provider/fetcher | Identical testability strategy to enrichment: unit tests inject a fake provider; no network in tests. Credential source (keychain/env vs future vault) is invisible to the engine. |
| Output contract | Prompt requests strict JSON `{"subject","body"}`; parser tolerates a fenced/raw JSON or a leading `Subject:` line; body trims trailing/leading whitespace | Cheap models (and compatible endpoints) occasionally wrap JSON in prose or markdown fences. JSON-first keeps structure; the fallback means a well-behaved plain-text completion still works. Failures produce a clear error, never garbage. |
| Prompt rules | System prompt forbids inventing facts/shared history, caps length, requires one clear ask, and instructs use of only provided facts; unknown fields are simply omitted from context | Prevents hallucinated rapport ("Loved your talk at KubeCon!") — the single biggest trust risk in AI outreach. Mirrors Security doc §4.3 content guidance (no spammy trigger phrasing, personalization). |
| Credentials (web) | Server env only; no key storage UI in this phase | Consistent with the committed Phase 1 decision (enrichment keys read from env in the web app). Keeps NetPro out of the key-storage business until multi-tenant hosting warrants the §2.3 vault. Settings page shows config *status*, never values. |
| Credentials (CLI) | Existing encrypted `Keychain` (`ai.openai.key`, `ai.anthropic.key`, `ai.provider`, `user.name`) + env overrides | Reuses the audited AES-256-GCM local store; `netpro config set` already teaches users this flow. |
| Contact resolution | Email → id → unique full-name match; ambiguous names error with candidates; ad-hoc flags bypass the DB | Search-by-email is exact and safe; name search is convenient but must be unambiguous to email the wrong person. Ad-hoc flags cover drafting to people outside the network. |
| API shape | `POST /api/outreach` with JSON body; 400 validation, 401 unauth, 500 `ai_not_configured`, 502 upstream failure | First write-shaped route; status codes follow the Security doc's API conventions. `ai_not_configured` is a distinct, UI-actionable condition rather than a generic 500. |
| Input limits | Tone enum whitelist; context ≤2000 chars; purpose ≤500; ad-hoc name ≤200; no newlines in subject-adjacent fields | Bounds prompt size/cost and follows §5.1's validation philosophy (header-injection hygiene matters once sending exists later). |
| Determinism | Pure prompt builder; injected clock (`generatedAt`) and injected provider in tests | Same `now?` injection discipline as Phase 3. |

## CLI

```
netpro outreach
  --to <email|id|name>          # recipient from your contacts (exact email/id,
                                # or unique full-name match)
  [--email <addr>] [--name <n>] [--company <c>] [--role <r>]   # ad-hoc recipient
  [--context <text>]            # e.g. "met at React Conf after your WASM talk"
  [--purpose <text>]            # the ask, e.g. "15 min to chat about OSS collab"
  [--tone <warm|professional|casual|friendly>]   # default: professional
  [--sender <name>]             # default: config user.name → git user.name
  [--provider <openai|anthropic>]                # default: config ai.provider
  [--model <model-id>]          # override the provider default
  [--json]                      # emit the draft as JSON
```

- Errors (exit 1): no AI key configured (with the exact `netpro config set`
  hint), unknown provider, contact not found, ambiguous name (lists
  candidates), provider/API failure (status + message), invalid tone.
- Success: prints `Subject: …` then the body; `--json` prints the
  `OutreachDraft`.

## Web

- `POST /api/outreach` — body `{ contactId? | recipient?: {name,email,
  company,role}, context?, purpose?, tone?, sender?, provider?, model? }` →
  `OutreachDraft`; gated by middleware (401 JSON).
- `/outreach` — client composer: pick a contact (lookup through
  `GET /api/search`) or fill ad-hoc fields, choose tone, add context/purpose,
  generate, copy subject/body. Setup banner when AI isn't configured.
- `/settings` — read-only integration status panel (env presence): GitHub
  OAuth, Hunter/PDL/Clearbit enrichment, AI provider/model; brief "how to
  configure" env-var hints.
- Middleware: add `/api/outreach` to `API_ROUTES` (it is already listed in
  the Security doc's API_ROUTES and rate-limit table).

## Testing

- Core (`packages/core/src/ai/*.test.ts`):
  - prompt builder — includes sender/recipient facts, omits unknown fields,
    injects tone/purpose/context, includes the no-hallucination rules;
  - parser — strict JSON, fenced JSON, `Subject:` plain-text fallback,
    malformed → thrown error;
  - `composeOutreachMessage` with a fake injected provider — request shape
    (messages array, model), tone passed through, error propagation,
    `generatedAt` injection, missing-key path via `resolveAiProvider`;
  - provider factories — OpenAI request body/headers/URL parse + error
    statuses; Anthropic request shape + content extraction; baseUrl override;
    all against an injected fake `fetch`.
- CLI (`apps/cli/src/commands/outreach.test.ts`): flag→input mapping and
  validation (`toOutreachOptions`), tone whitelist, contact resolution
  (email/id/name/ambiguous/missing) against in-memory SQLite, no-key error
  message, render vs `--json`.
- Web:
  - `app/api/outreach/route.test.ts` — 400 on invalid body, 400 on
    unresolvable/ambiguous contact, 200 draft shape with a mocked core
    engine, `ai_not_configured` (core throws the configured error), 502 on
    upstream failure; seeded in-memory SQLite following the analytics route
    test pattern.
  - settings page renders env-based status without leaking values.
- End-to-end: real CLI `import` → `outreach --to <email>` against migrated
  SQLite with a stubbed `OPENAI_API_KEY` + intercepted fetch (recorded
  request shape); live `next dev` confirms `POST /api/outreach` 401 when
  signed out and the `/outreach` gate.

## Success criteria

- `netpro outreach --to <contact>` produces a subject + body using the
  contact's real data; ad-hoc recipients, tones, context, and `--json` work;
  missing keys and ambiguous targets error clearly.
- `/outreach` generates and displays the same draft through
  `POST /api/outreach`, auth-gated, with a setup banner when unconfigured.
- No secret is ever logged or rendered; web reads keys only from env; CLI
  uses the existing encrypted keychain.
- No new runtime dependencies; behavior identical on SQLite and Postgres
  (the engine touches no database — resolution reuses the portable search
  helpers).
- `npm run lint && npm run typecheck && npm run test && npm run build` all
  pass repo-wide.
