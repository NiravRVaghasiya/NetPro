# NetPro v1.0 Phase 5 — Profile Card

Date: 2026-09-06

## Repository assessment

At `c3f433e` (merged PR #12), Phases 1–4 deliver import/enrichment/export,
portable people search, attribute-based analytics, and BYO-key AI drafting.
The baseline passes lint, typecheck, all 234 tests, and a production build.
Next.js still reports the existing middleware deprecation and instrumentation
Edge-runtime warnings. The native SQLite dependency installs in this sandbox
using its preinstalled Node headers (`npm_config_nodedir=/usr/local npm ci`);
no dependency changes are needed.

The next product milestone in the blueprint is **Profile Card**, followed by
one-click deployment/release readiness. CRM (`track`), campaigns, contact-detail
pages, and the `init` wizard remain stubs; the roadmap puts CRM/campaigns in
v1.5. Federated/vector search, graph-native analytics, real email delivery,
and viewer analytics remain explicitly deferred, not requirements silently
claimed as complete.

Two prerequisites surfaced at the auth boundary: `lib/auth.ts` exports Auth.js
handlers but no `/api/auth/[...nextauth]` route mounts them; and any GitHub user
would be accepted despite the database being a single shared, unpartitioned
network. A publicly shared instance must not expose its private network to
arbitrary GitHub sign-ins. This phase wires the route and enforces an explicit
single-owner GitHub account ID. It does **not** introduce multi-tenancy.

## Scope

- One networking card per self-hosted instance, authored independently of
  imported contacts and OAuth identity data.
- Authenticated `/settings/card`: edit, preview, save a private draft, explicitly
  publish the current form, unpublish immediately, copy the public link, and
  download profile JSON for the CLI.
- Public `/card`: server-rendered published snapshot, useful social metadata,
  contact/link actions, and `/card/vcard` download. No published snapshot means
  not found, even for an authenticated owner; preview lives in the editor.
- `netpro card --generate --input profile.json [--output card.html]`, with
  `--format vcard` as an alternative. Portable, offline generation only: this
  does not publish or mutate the server database.
- Core validation, persistence, standalone HTML, and vCard generation reused
  by CLI/web. No new npm dependencies.

## Data and publication contract

`profile_cards` is a new table in **both** Drizzle dialects with a singleton
`id = 'default'`, `draft` (JSON text), `published` (nullable JSON text),
`published_at` (nullable ISO timestamp), and `updated_at` (ISO timestamp).
JSON is deliberately plain text in both dialects, avoiding the existing
SQLite-auto-decode/Postgres-raw-text asymmetry. Committed, additive migrations
run via the existing CLI/web startup migrators.

The profile has a required `fullName` and optional `headline`, `bio`, `company`,
`role`, `location`, `email`, `phone`, and up to six `{label, url}` links. Optional
strings normalize to empty strings. There are no contact IDs, private notes,
relationship metrics, credentials, or implicit OAuth fields in this contract.
Unknown fields are rejected rather than accidentally published.

Saving changes **only** the draft. Publishing atomically saves a normalized
draft and a separate published snapshot. Unpublishing clears only the snapshot
and publication timestamp, preserving the draft. Public loaders select only
the published column; no private snapshot is serialized to public HTML,
metadata, RSC payloads, or downloads. No cross-request cache is used: subsequent
requests must stop serving a card as soon as it is unpublished. Already shared
copies/screenshots/downloads cannot be recalled, which the UI/docs explain.

## Validation and output safety

- Shared limits: 120-character name/company/role, 160-character headline/location,
  2,000-character bio, 254-character email, 40-character phone/link label,
  2,048-character link URL, six links; JSON input at most 32 KiB.
- Required field/type checks, control-character rejection (bio permits newlines),
  bounded email/phone shapes, and absolute HTTP(S) links without credentials.
  No raw HTML, arbitrary URL schemes, uploaded images, or remote avatar fetches.
- React escapes text; standalone HTML escapes all text and attributes and has
  no scripts or remote assets. Mailto values are URI-encoded. External links
  use `noopener noreferrer nofollow`; the card sets a no-referrer policy.
- vCard 3.0 escapes delimiters/backslashes/newlines, uses CRLF, and folds lines
  by UTF-8 octets without splitting Unicode code points.
- Public cards are `noindex, nofollow` by default; this is an indexing request,
  **not** access control. Published details are public to anyone with the URL.
- No `profile_views` writes, cookies for tracking, IP storage, enrichment,
  telemetry code, or viewer identification. Viewer analytics belongs to v2.5.

## Auth and HTTP boundary

`NETPRO_OWNER_GITHUB_ID` is the owner's numeric GitHub account ID (stable across
username changes). Missing/invalid configuration denies sign-in. The provider
account ID is verified at sign-in and on every JWT read; old sessions without
an owner identity and sessions for a replaced owner are invalidated. Only the
configured owner can access the existing private application or card editor.
Both environment examples and Docker Compose pass this setting through.

- `GET /api/card`: owner-only draft/publication state.
- `PUT /api/card`: save JSON profile as a draft.
- `POST /api/card`: explicitly publish JSON profile.
- `DELETE /api/card`: unpublish, retain draft.

The route itself checks `auth()`, independent of middleware. Mutations require
same-origin requests (accounting for trusted reverse-proxy forwarded host and
protocol); PUT/POST require JSON with a streaming size bound. Responses are
non-cacheable. Expected statuses: 400 validation, 401 unauthenticated, 403 origin
mismatch, 413 oversized body, 415 wrong content type, 500 generic storage error
without leaking SQL/configuration. Middleware matches path segments, not loose
prefixes, and treats `/api/card` as private while `/card` stays public. Public
routes bypass middleware session processing, so anonymous card visitors do
not receive unnecessary Auth.js cookies.

## Explicit non-goals and next phase

No public slug registry, multi-user publishing, themes/templates marketplace,
QR dependency, image uploads, viewer analytics, or deployment automation in
this phase. The CLI exports files, it does not host them or auto-publish a
contact. No real OAuth provider round trip can be claimed without operator
credentials. PostgreSQL compatibility must be distinguished from live
PostgreSQL verification.

**Phase 6 — Deployment and release readiness** should cover Vercel with managed
Postgres (never ephemeral SQLite), migration packaging/execution under
serverless concurrency, production environment documentation, Docker provider
configuration and database exposure, the existing Next.js warnings, and an
end-to-end release smoke suite. A passing local build alone is not a v1.0
production-readiness claim.

## Acceptance criteria

1. Draft → publish → edit draft → unpublish is tested against real migrations;
   private edits never change the public card before publication.
2. Public page, metadata, and vCard expose only explicit published fields;
   unpublished/missing cards return 404 and cannot be cached as public snapshots.
3. Signed-out, non-owner, legacy-session, bad-origin, invalid-body, unsafe-URL,
   and output-injection paths fail safely in tests.
4. CLI HTML and vCard generation works offline from documented sample JSON,
   including Unicode; invalid input reports a useful nonzero-exit error.
5. Repo-wide lint, typecheck, tests, and production build pass; live smoke
   checks cover public/private routes and the publication lifecycle without
   adding an authentication bypass or real personal data to the repository.
