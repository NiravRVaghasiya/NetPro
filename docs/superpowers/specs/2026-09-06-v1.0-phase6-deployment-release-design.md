# NetPro v1.0 Phase 6 — Deployment & release readiness (design)

Phases 1–5 built the product. This phase makes it deployable, and it starts
from an uncomfortable finding: **the release candidate could not have been
deployed successfully**, in two independent ways that a passing local build
could never have revealed.

Phase 5's own verification record was honest about the gap it was leaving:

> Postgres schema/query types compile and its additive migration is committed,
> but **no live PostgreSQL integration run** was performed.

That is exactly where both bugs were hiding.

## What was actually broken

### 1. Concurrent migrations failed 5 of 6 cold starts

Every entry point called drizzle's `migrate()` directly at startup. That is
fine for one long-lived process. On Vercel, a deployment cold-starts many
serverless instances simultaneously, and each one races to apply the same DDL.

Measured against a real PostgreSQL 18 server, empty database, six concurrent
migrators — the shape of a fresh deploy taking traffic:

```
workers=6 ok=1 failed=5
  -> Failed query: CREATE TABLE "account" (...)
  -> Failed query: CREATE SCHEMA IF NOT EXISTS "drizzle"
```

Drizzle wraps statements in a transaction, so the *database* stayed consistent
— but five of six requests threw, which on Vercel is five failed cold starts
(HTTP 500) on every deploy carrying a migration. The
`CREATE SCHEMA IF NOT EXISTS` failure is the tell that this is a real race and
not merely duplicated work: `IF NOT EXISTS` races with itself in Postgres,
because the existence check and the create are not atomic.

**Fix.** One shared runner in `packages/db/src/migrate.ts`, used by the CLI, the
web startup hook, and the deploy command. Postgres migrators serialize on a
session-level advisory lock held by a dedicated pool client and released in a
`finally`; if a process dies, Postgres frees the lock when the connection
drops, so it cannot wedge. `lock_timeout` bounds the wait so a stuck peer fails
loudly instead of hanging an invocation. A per-process promise cache stops a
warm instance from re-migrating per request. SQLite keeps the direct path
(single writer, one local process) behind the same entry point.

The regression test was mutation-verified: removing the lock makes it fail with
the original errors.

### 2. Production authentication was entirely broken

Running a real production build with NetPro's own documented configuration:

```
[auth][error] UntrustedHost: Host must be trusted.
URL was: http://localhost:3000/api/auth/session
```

Every authenticated request returned 401, and `/api/auth/providers` returned
"There was a problem with the server configuration."

Auth.js v5 derives host trust like this (`@auth/core/lib/utils/env.js`):

```js
config.trustHost ??= !!(AUTH_URL ?? AUTH_TRUST_HOST ?? VERCEL ?? CF_PAGES
                        ?? NODE_ENV !== "production")
```

`NEXTAUTH_URL` is **absent**. next-auth reads it for the base path and callback
origin, so it looks fully supported — but it does not confer trust. NetPro's
README, `docs/getting-started.md`, both `.env.example` files, and
`docker-compose.yml` all told operators to set `NEXTAUTH_URL`. A self-hosted
deploy following the documentation exactly would have had authentication fail
outright.

Two properties made this invisible until now: the `NODE_ENV !== "production"`
clause masks it in development, and the `VERCEL` clause masks it on Vercel. Only
a **production build on a non-Vercel host** — never previously exercised —
exposes it.

**Fix.** `apps/web/lib/trust-host.ts` treats an operator-configured
`NEXTAUTH_URL` as the same explicit statement of trust `AUTH_TRUST_HOST` asks
for, while still honouring an explicit opt-out and deferring to Auth.js's own
default when nothing is configured (so trust is never silently widened on an
unconfigured instance). `docker-compose.yml` also passes `AUTH_URL` explicitly,
and CI greps container logs for `UntrustedHost`.

## Scope

- **Serverless-safe data layer** — advisory-locked migrations, runtime-aware
  pool sizing (1 connection per serverless instance vs 10 on a long-lived
  server), explicit `sslmode` mapping for managed providers, an idle-client
  error handler so a provider failover cannot kill the process, and a startup
  guard rejecting ephemeral SQLite on Vercel.
- **Explicit deploy step** — `netpro migrate` (and `--status`), used identically
  by the Vercel build, the Compose migration job, and operators by hand, so the
  deploy path cannot drift from the documented one. `NETPRO_AUTO_MIGRATE=false`
  keeps DDL off request paths entirely.
- **Vercel target** — `vercel.json`, a `vercel-build` script that migrates then
  builds (tolerating a first deploy with no database yet), and a one-click
  deploy button with the required environment variables.
- **Production hardening** — CSP, HSTS (production only, since it would strand a
  plain-HTTP local instance), frame/content-type/referrer/permissions headers,
  `no-store` on `/api/*`, and `poweredByHeader: false`. Postgres is no longer
  published to the host in Compose.
- **Readiness, not just liveness** — `/api/health` distinguishes reachable
  (`healthy`), reachable-but-unmigrated (`degraded`, 503), and unreachable
  (`unhealthy`, 503), so a rollout gate stops instead of serving a broken app.
  Diagnostic detail is owner-only; anonymous callers never see driver errors
  containing hostnames or database names.
- **Next.js 16 conventions** — `middleware.ts` → `proxy.ts` (deprecated, slated
  for removal), and the instrumentation hook slimmed so the Edge bundle no
  longer pulls `node:fs`/`node:path`/`node:module`. The build now emits **zero**
  warnings, down from six.
- **CI that could have caught all of this** — a Node 20/22 matrix, a live
  PostgreSQL service running the integration suite and the migration CLI twice
  (idempotence), and a Docker job that builds the image, migrates, boots it
  against Postgres, and asserts health, auth boundaries, and clean logs.

## Deliberate decisions

**Advisory lock over "just run migrations once".** Even with an explicit deploy
step, a self-hosted operator can start two containers, and `NETPRO_AUTO_MIGRATE`
defaults to on for local and Docker use. The lock makes the *default* safe
rather than relying on operators reading documentation.

**Trust inferred from `NEXTAUTH_URL`, not forced on.** Returning `true`
unconditionally would trust arbitrary `Host` headers on an unconfigured
instance — strictly worse than Auth.js's default. Configuration is the signal.

**Fail closed on ephemeral SQLite.** Vercel + SQLite "works" in a smoke test and
silently discards the user's imported network on the next redeploy. A startup
error naming the fix is better than a deploy that looks fine.
`NETPRO_ALLOW_EPHEMERAL_SQLITE` exists for throwaway previews.

**HSTS only in production.** A browser that sees HSTS once refuses plain HTTP to
that origin for two years — actively harmful for `localhost` and self-hosted
HTTP instances.

**No new runtime dependencies.** No Sentry, no `@vercel/postgres`, no logging
framework. `package-lock.json` is unchanged; `pg` and `better-sqlite3` were
already present.

## Explicitly out of scope

Sentry/OpenTelemetry, structured logging, cron jobs (`/api/cron/*` in the
blueprint belongs to v1.5 campaigns, which do not exist yet), npm/Homebrew CLI
publishing, changesets, staging environments, load testing, and backup
automation. Blueprint items requiring absent features are not stubbed.

A **real GitHub OAuth round trip** still cannot be claimed: it needs operator
credentials and a public callback URL. Owner authorization was verified with
synthetic JWTs signed by the server's own ephemeral secret — the normal Auth.js
path with a test identity, not a bypass.

## Acceptance criteria

1. Concurrent cold-start migrations against real PostgreSQL succeed for all
   workers and apply exactly once; the test fails if the lock is removed. ✅
2. A production build with only `NEXTAUTH_URL` set authenticates the owner,
   rejects non-owner and legacy JWTs, and logs no `UntrustedHost`. ✅
3. The full card lifecycle (draft → private → publish → public → unpublish →
   404) works against real PostgreSQL, with bad-origin writes rejected. ✅
4. `/api/health` reports `degraded` 503 on an unmigrated database and leaks no
   driver detail to anonymous callers. ✅
5. `netpro migrate` is idempotent against a real database and turns the common
   misconfigurations into actionable messages with a non-zero exit. ✅
6. Repo-wide lint, typecheck, tests, and build pass with **zero** build
   warnings. ✅
