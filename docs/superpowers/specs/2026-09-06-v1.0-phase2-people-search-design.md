# NetPro v1.0 Phase 2 — People Search — Design

> Status: Implemented
> Builds on: Phase 1 (Import, Enrichment & Export)
> Source blueprints: `NetPro — Blueprint.md` (Search & Discovery, CLI reference),
> `NetPro — DB & Pipeline Deep Dive.md` (§1.4 search_index schema, §1.5 query patterns,
> §2.5 Stage 4 Search & Indexing)

## Purpose

Phase 1 puts contacts in the database; Phase 2 makes them findable. This phase
ships a **portable, faceted keyword search** over the `contacts` table,
exposed on both surfaces (CLI + web) through a single shared core function.

## Scope

**In scope:**
- Free-text query across name, email, headline, company, role, location
  (case-insensitive substring; AND across whitespace-split terms, OR across
  columns per term).
- Faceted filters: `company`, `role`, `location`, `industry` (substring),
  `seniority` (exact, normalized vocabulary), `hasEmail`, `minScore`
  (relationship score 0–1), `lastActiveWithinDays`.
- Sorting: `relevance` (default — name > email > company > role/headline/
  location match rank, then relationship score), `score`, `recent`
  (`lastInteraction`, NULLS LAST), `name`.
- Pagination via `limit` (default 25, max 100) / `offset`; a `total` count.
- Facet aggregates (top-10 value counts for company/role/location/seniority/
  industry) for filter UI.
- CLI `netpro search` (replaces the stub) and web `/search` page +
  `GET /api/search` (replaces the stubs).
- Soft-deleted contacts (`deletedAt IS NOT NULL`) are always excluded.

**Explicitly deferred** (documented, not forgotten):
- **Hybrid search** from the blueprint — SQLite **FTS5** virtual table,
  Postgres **pgvector**, 384-dim embeddings (`all-MiniLM-L6-v2`), and RRF
  re-ranking. These need dialect-specific storage and an embedding model; they
  build on the same `searchContacts` entry point and the existing
  `search_index` table in a later phase.
- Populating the `search_index` denormalized table (this phase queries
  `contacts` directly; `search_index` stays for the future FTS/vector stage).
- Blueprint CLI flags `--skills` / `--open-to-connect` — no skills column or
  open-to-connect signal exists yet.
- Federated/external search (GitHub, PDL person-search) — enrichment covers
  PDL/Hunter/Clearbit already; federated *search* providers are future work.
- Autocomplete/suggest endpoint (`SearchEngine.suggest`).

## Key decisions

| Area | Decision | Rationale |
|---|---|---|
| Query engine | ANSI SQL substring matching + facets, not FTS5/pgvector | Runs identically on SQLite and Postgres — no dialect-specific virtual tables or extensions. Mirrors Phase 1's pragmatism (migrations built only when needed). |
| Filter/order construction | Shared `conditions.ts` using Drizzle `sql` + `AnyColumn` | A raw-SQL fragment is identical across dialects, so ONE module builds WHERE/ORDER BY for both — avoiding the `if dialect` duplication the import/enrichment pipelines have for typed query-builder calls. Only the thin executor branches on dialect. |
| Table queried | `contacts` directly (not `search_index`) | Always consistent with import/enrichment writes; no sync bug. `search_index` is reserved for FTS/vector later. |
| Free-text semantics | AND across terms, OR across columns, `lower() LIKE %term%` | Predictable, portable, no FTS query syntax. `lower()` gives case-insensitivity on both SQLite and Postgres. |
| Facets | Aggregated over the active filter set via `GROUP BY lower(col)` | Counts reflect what the user is currently looking at; top-10 per field. |
| API shape | `searchContacts(conn, opts): Promise<SearchContactsResponse>` returning `{ contacts, total, limit, offset, facets }` | One function consumed by both CLI and web; same `conn` pattern as Phase 1. |
| Web surface | Server component reading URL search params + `GET /api/search` | No client JS state; shareable/back-button-friendly URLs; consistent with the existing minimal pages. |
| Auth | `/api/search` added to middleware `API_ROUTES` (401 JSON); `/search` already protected by the `(app)` layout + middleware | Matches the Security blueprint's API route protection pattern applied in Phase 1. |

## CLI

```
netpro search [query terms...]
  [--company <substr>] [--role <substr>] [--location <substr>] [--industry <substr>]
  [--seniority <level>] [--has-email] [--min-score 0..1] [--active-within <days>]
  [--sort relevance|score|recent|name] [--limit <n>] [--offset <n>] [--json]
```

Invalid `--sort` / out-of-range `--min-score` / non-numeric options fail with a
clear message and exit code 1. Commander delivers hyphenated flags as camelCase
(`--min-score` → `minScore`, `--active-within` → `activeWithin`).

## Web

- `GET /api/search?q=&company=&role=&location=&industry=&seniority=&hasEmail=&minScore=&activeWithin=&sort=&limit=&offset=` → `SearchContactsResponse` JSON; invalid `sort` → 400.
- `/search` — search box, a filter form (company/role/location/industry/
  seniority/has-email), facet sidebar links, sort links, results table, and
  prev/next pagination — all driven by URL query params.

## Success criteria

- `netpro search <terms>` and the flag filters return correct, ranked,
  paginated contacts from a real imported database; invalid flags error clearly.
- `/search` and `GET /api/search` accept the same queries/filters and return
  results + facets; both are auth-gated.
- Behavior is identical on SQLite and Postgres (ANSI SQL via shared condition
  builder).
- `npm run lint && npm run typecheck && npm run test && npm run build` all pass
  repo-wide.
