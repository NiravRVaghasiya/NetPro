# NetPro v1.5 Phase 8 — Batch Campaigns (Draft-Only) — Design

> Status: Implemented
> Builds on: Phase 4 (AI Outreach — draft-only boundary), Phase 7 (CRM —
> interaction logging, contact resolution), Phase 2 (Search — recipient
> selection)
> Source blueprints: `NetPro — Blueprint.md` (roadmap v1.5 "Batch campaigns",
> `/outreach/campaigns` page detail), `NetPro — DB & Pipeline Deep Dive.md`
> (§ campaigns / campaign_recipients schema), Phase 4 design spec (deferred
> "Batch campaigns & drip sequences" item)

## Purpose

Phase 4 draws one message for one person. Real outreach is a list: the same
well-crafted note, personalized per recipient, sent over days without
torchering anyone's inbox. Phase 8 completes v1.5 with batch campaigns —
**draft-only**, honoring the boundary NetPro has kept since Phase 4: *NetPro
drafts — you review and send; nothing is emailed automatically.*

A campaign is a saved template (plus optional drip steps) attached to a
snapshot of recipients (picked by id or by search). NetPro renders every
personalized draft, tracks which ones you actually sent, logs those sends as
interactions (feeding Phase 7 scoring and Phase 3 analytics), and enforces a
daily limit so a manual mailing stays humane.

## Scope

**In scope:**

- **Core `campaigns` module** (`packages/core/src/campaigns`):
  - `createCampaign` — name, description, template `{subject, body}`, optional
    ordered drip `steps[{delayDays, subject, body}]`, `dailyLimit`,
    `sendFrom`; recipients from explicit contact ids **or** a saved search
    selection (runs `searchContacts` once and snapshots the ids). Status
    starts `draft`. Duplicate recipients are merged, soft-deleted contacts
    rejected.
  - Merge-variable rendering — `{{firstName}} {{lastName}} {{fullName}}
    {{company}} {{role}} {{email}} {{headline}} {{location}} {{industry}}`,
    resolved per recipient from the contact row, overridable via
    `personalizedVars`; unknown variables are a validation error at save time
    (listed in the message), never a silent blank in someone's inbox.
  - Lifecycle — `draft → active → paused → completed`, `archived` from any
    state; transitions validated, denormalized stats (`sent`, `replied`,
    `totalRecipients`) recomputed from `campaign_recipients` on every change.
  - `renderCampaign` — recipients joined to contacts with every step's draft
    rendered; the daily-limit meter (`sentToday`, `dailyLimitRemaining`).
  - `markRecipientSent` — the pivotal mutation: blocks when the campaign's
    daily limit is already reached (actionable error, `--force` override for
    the CLI), sets `sentAt`/status, writes the `email_sent` outbound
    interaction **through Phase 7's `logInteraction`** (so scoring, stats, and
    the activity log all stay true), and schedules the next drip step
    (`scheduledAt = sentAt + delayDays`) when the sequence continues.
  - `markRecipientReplied` (logs an `email_received` inbound interaction,
    cancels the remaining drip for that recipient — replying ends a follow-up
    sequence, that's the point of `condition: no_reply`) and
  - `markRecipientSkipped` (manual opt-out of one person; nothing sent,
    nothing logged).
- **Web** (replaces the `/outreach/campaigns` stub):
  - `GET/POST /api/campaigns`, `GET/PATCH /api/campaigns/[id]` (lifecycle +
    edits while `draft`), `POST /api/campaigns/[id]/recipients/[recipientId]`
    (`sent` / `replied` / `skipped` actions). Owner-only via the existing
    proxy boundary; strict validation, shared limits with core.
  - `/outreach/campaigns` — list with status/stat badges and a creation form
    (template, drip steps, daily limit, recipients by search query or pasted
    ids).
  - `/outreach/campaigns/[id]` — campaign detail: rendered drafts per
    recipient with copy buttons, mark-sent / replied / skip actions, the
    daily-limit meter, sequence timeline, and the "NetPro drafts — you send"
    note.
- **CLI `netpro campaign`**: `list [--json]`, `create --name --subject --body
  [--step 3d --step-subject … ] [--to id,id | --from-search "company:Stripe"]
  [--daily-limit n]`, `show <id>`, `render <id> [--contact <sel>] [--json]`
  (prints personalized drafts for review/copy), `mark-sent <id> <contact>
  [--force]`. Same `resolveContactRef` selector as `track`/`outreach`.
- **Indexes** — `campaign_recipients(campaign_id, status)` and
  `campaign_recipients(scheduled_at)` join the Phase 7 migration if it hasn't
  shipped, else ride its own additive migration.

**Explicitly deferred** (documented, not forgotten):

- **Actual delivery** — SMTP/Resend/Gmail transports, open/click tracking
  pixels, bounce webhooks, unsubscribe links/list headers, and the Security
  doc's SpamGuard rate/deliverability suite. The `opened`/`bounced` counters
  and `sendVia` column stay at zero/null until a delivery phase owns them;
  `markRecipientSent` is the human-in-the-loop stand-in, and every downstream
  consumer (interactions, scoring, analytics) already treats it as truth.
- **AI-composed campaign templates** — Phase 4 drafts one message with a live
  provider call; wiring `composeOutreachMessage` into campaign creation (draft
  the template, then batch-render) is a small follow-up once users ask for it.
- **Scheduled background sends** (`scheduledAt` is written but no worker
  consumes it) — needs the scheduler deferred since Phase 3; in draft-only
  mode the schedule is *advice* ("send step 2 on Thursday"), rendered in the
  UI, enforced by nobody.
- **A/B testing, reply detection, campaign-level analytics dashboards** —
  volume features for a delivery phase.

## Key decisions

| Area | Decision | Rationale |
|---|---|---|
| Draft-only boundary | Campaigns never send; `markRecipientSent` records a human-confirmed send | Consistent with Phase 4's load-bearing decision and the repo's privacy posture. It also keeps the entire deliverability/anti-spam surface (Security doc §4.3) out of v1.5 while making the data model send-ready: a future transport replaces the manual mark with a real one, and every consumer of `interactions` keeps working unchanged. |
| Recipient snapshot | Search selection resolves to concrete contact ids at creation | A campaign is a commitment to a *list*, not a live query — re-resolving on every render would silently add/remove people and make "sent to 40 of 52" meaningless. Re-running the search to top up is an explicit action. |
| Interaction logging on send | `markRecipientSent` → `crm.logInteraction(type: email_sent, direction: outbound, channel: email, campaignId)` | The Phase 4 spec deferred interaction logging to "the phase with real sends"; a confirmed manual send *is* a real send. This is what finally feeds relationship scoring, activity/dormancy, and campaign stats from one source of truth. |
| Reply ends the sequence | `markRecipientReplied` cancels remaining drip steps for that recipient | The blueprint's step condition is `no_reply`; continuing to nag someone who answered is the exact anti-pattern SpamGuard exists to prevent. |
| Daily limit enforcement | Counted per UTC day from `campaign_recipients.sentAt`; hard error at the limit, `--force`/`force: true` override | The limit is the user's own anti-spam guardrail; the override exists because the person who set it is the person allowed to change their mind — but the default path makes the frictionless thing the safe thing. |
| Merge variables | Whitelisted `{{var}}` set, save-time validation, per-recipient overrides | Free-form templating engines (Handlebars et al.) are a new dependency and an injection surface; nine whitelisted fields + JSON overrides cover personalization needs with pure string replacement and testable errors. |
| Stats | Denormalized counters recomputed from recipients after every mutation | The schema ships `sent/opened/replied/bounced` columns for cheap list rendering; recomputing (instead of incrementing) makes them self-healing and trivially consistent in tests. |

## Testing strategy

- Core: migrated in-memory SQLite fixture; deterministic `now`. Template
  rendering (all variables, overrides, unknown-variable rejection), search
  snapshotting, dedupe, lifecycle transition matrix, daily-limit blocking +
  force + UTC-day boundary, drip scheduling math, replied-cancels-sequence,
  interaction/scoring side effects asserted through the contacts row.
- CLI: `executeCampaign*` purity over a test conn — list/show/render output,
  `--step` parsing, `--from-search` wiring, mark-sent limit error.
- Web: route tests with mocked `@/lib/db` for create/validate/404/lifecycle
  and the recipient-action endpoint; detail-page render test for draft cards
  and actions.
- Postgres: portable ANSI SQL throughout (standard dialect narrowing only);
  live-Postgres CI suite runs the migrations.
