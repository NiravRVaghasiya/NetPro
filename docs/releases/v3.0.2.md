# NetPro v3.0.2 — the serve banner stops calling the API the Web UI

**A one-line patch where it matters: `netpro serve` no longer prints the same address twice.** v3.0.1 made the bundle actually run; v3.0.2 makes the banner tell the truth about what is running.

Before — every `netpro serve` looked like two services on one port:

```text
NetPro server started

Local:    http://127.0.0.1:3777

Database: C:\Users\niravnetpro\netpro.db

Identity: ins_b68f5cda762a8bc342d7e81e

Auth:     local — loopback trusted; access token set for remote callers

Web UI:   http://127.0.0.1:3777
```

`Local:` and `Web UI:` printed the same loopback address. Opening the second one showed only the API's built-in console page — live health, database, identity — while the full Web UI (Observatory, Network, People, Search, Pathfinder, …) is the separate Next.js app in `apps/web` that talks to that API over HTTP. Two lines, one URL, the wrong name.

After — the port says what it is, and the Web UI is only claimed when one exists:

```text
NetPro server started

Local:    http://127.0.0.1:3777  (API + built-in console)
Database: ~/.netpro/netpro.db
Identity: ins_7a4546a7d03292e3ea3f4d4a
Auth:     local — loopback trusted; access token set for remote callers

Web UI:   not running — start it with `npm run dev -w apps/web`
          (set NETPRO_WEB_URL or [server] web_url once it has a fixed address)
```

With a Web UI running, point the banner at it:

```bash
NETPRO_WEB_URL=http://localhost:3000 netpro serve
# or in ~/.netpro/config.toml:
# [server]
# web_url = "http://localhost:3000"
```

```text
Local:    http://127.0.0.1:3777  (API + built-in console)
Web UI:   http://localhost:3000  (separate app, points at this server)
```

An unusable value (not an `http(s)` URL) is treated as not set — better to say "not running" than to print a broken link.

Nothing else changes in this release. The feature set, the database schema (15 migrations per dialect, no new ones), the `~/.netpro` layout and the HTTP API are identical to v3.0.1, so there is nothing to migrate and nothing to re-import.

## Install

**Prerequisites:** Node.js ≥ 20. Nothing else — no Docker, no database server, no account.

```bash
npm install -g https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.2/netpro-3.0.2.tgz

netpro --version  # 3.0.2
netpro init       # creates ~/.netpro: config.toml, SQLite db, logs, keys
netpro serve      # API + built-in console at http://127.0.0.1:3777 (foreground; Ctrl+C stops it)
netpro status     # install · database · identity · server health · providers
```

Upgrading from v3.0.1, from the withdrawn v3.0.0 bundle, from a source checkout, or from nothing at all is the same three commands. `~/.netpro` is untouched: your database, identity, config and access token carry over.

```bash
npm uninstall -g netpro        # drop whatever is there (including a stale link)
cd ~                           # not the checkout: `npm install -g` with no name installs the cwd project
npm install -g https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.2/netpro-3.0.2.tgz
netpro status
```

### Verify the download

```bash
curl -LO https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.2/SHA256SUMS
shasum -a 256 -c SHA256SUMS
```

## What was wrong

The banner in `packages/server/src/serve.ts` printed the bound server URL on both the `Local:` and `Web UI:` lines. That read as two services when only one was running — and named the API port as the UI.

Three things made it stick:

- The **standalone console page** (`GET /` — `packages/server/src/routes/home.ts`) is genuinely useful — it renders live health from `GET /api/health` — so pointing the Web UI line at it did not look broken at a glance.
- The **full Web UI** (`apps/web`) is a separate process: `npm run dev -w apps/web` on `http://localhost:3000` (or any address you give it). It is a pure client of the standalone server and serves no API of its own. Nothing in `netpro serve` started it, and nothing in `netpro serve` knew where it was.
- Every smoke passed because it asserted the banner *once*, not that the two lines differed. The `local-stack` smoke started servers and hit `/api/health`, but never failed a build for advertising the API as the UI.

## What changed

All in the already-merged [`fix(serve)`](https://github.com/NiravRVaghasiya/NetPro/pull/72) — this tag just ships it:

- **`packages/server/src/serve.ts` + `packages/server/src/routes/home.ts`** — `Local:` now reads `http://127.0.0.1:3777  (API + built-in console)` and says what actually answers on that port. `Web UI:` prints the configured address with `(separate app, points at this server)` when one is set, and otherwise `not running — start it with npm run dev -w apps/web` plus the `NETPRO_WEB_URL` / `[server] web_url` hint. Raw values that are not usable `http(s)` URLs are ignored.
- **`packages/server/src/config.ts` + `packages/db/src/local.ts`** — a single display-only setting: `NETPRO_WEB_URL` env wins over `[server] web_url` in `~/.netpro/config.toml`, defaults to `null`, validated as a non-empty string and then filtered to `http(s)` only so the banner never prints a broken link. Unknown `[server]` keys still fail loudly — `web_url` joins the allow-list alongside `host`, `port`, `allowed_origins`.
- **`packages/server/src/config.test.ts`, `packages/server/src/serve.test.ts`, `packages/db/src/local.test.ts`** — pin the three states the banner must handle: no address → "not running", a good `http(s)` address → announced and never equal to the bound port, an unusable value → ignored. The `serve` suite also asserts `Local:` carries the `(API + built-in console)` disambiguator.
- **`scripts/smoke/local-stack.sh`** — the server smoke now asserts the banner it runs: `Local:` must end with `(API + built-in console)`, `Web UI:   not running` with no `NETPRO_WEB_URL` and must not allocate the UI's port, and `Web UI:   http://localhost:3000` when one is configured via the standalone `netpro-server` bin (which must still bind its own port unchanged).
- **Docs (`README.md`, `docs/getting-started.md`, `docs/local-first.md`, `docs/deployment.md`, `.env.example`, `apps/web/.env.example`)** — every place that said `http://127.0.0.1:3777` was the Web UI now says it is the API + console, and the Web UI is `http://localhost:3000` on its own port. `.env.example` documents `NETPRO_WEB_URL` as the display-only knob it is: the server never serves the UI.
- **Version bump to 3.0.2** — `package.json` (root + `apps/*` + `packages/*`), `apps/cli/src/cli.ts` (commander's `.version()`) and `packages/server/src/version.ts` (`SERVER_VERSION`). Both literals are pinned to the root manifest by `apps/cli/src/cli.test.ts` and `packages/server/src/version.test.ts`, so a hand-edit that misses one fails in CI.

No migrations, no schema change, no new dependencies, no API change.

## What the release gate verifies

`npm ci` → lint → typecheck → the full test suite → build → `scripts/smoke/cli.sh` → `npm pack` → the tarball's contents asserted statically (name, version, publishable, `bin.netpro`, bundled CLI, both migration sets, `better-sqlite3` and `pg` still runtime dependencies) → `scripts/smoke/installed-package.sh` against that tarball from a neutral working directory (`--version`, `init`, `migrate --status`, `status`).

On the same commit, CI runs the deep gates the release relies on: PostgreSQL integration (including the performance pass and migration idempotency), the server smoke on SQLite *and* PostgreSQL (now with the banner assertions above), the standalone Web UI smoke, and the Docker image end-to-end (migrations via the shipped CLI, then server + web against Postgres, including the token-mode auth boundary).
