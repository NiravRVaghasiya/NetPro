# NetPro v3.0.1 — the bundle installs and runs

**A patch release with one job: make the download work.** v3.0.0 was the first
tagged release of NetPro, and the tarball attached to it could not run once
installed:

```text
✗ netpro init failed: Could not locate @netpro/db migrations for "sqlite"
  — tried: <pkg>/apps/cli, <pkg>, <cwd>/node_modules/@netpro/db,
  <cwd>/packages/db, /packages/db
```

`npm install -g <tarball>` succeeded. `netpro init` did not — on a freshly
installed package, in any directory that did not happen to contain NetPro's own
`packages/db`.

Nothing else changes in this release. The feature set, the database schema
(15 migrations per dialect, no new ones) and the `~/.netpro` layout are identical
to v3.0.0, so there is nothing to migrate and nothing to re-import.

---

## Install

**Prerequisites:** Node.js ≥ 20. Nothing else — no Docker, no database server, no
account.

```bash
npm install -g https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.1/netpro-3.0.1.tgz

netpro --version  # 3.0.1
netpro init       # creates ~/.netpro: config.toml, SQLite db, logs, keys
netpro serve      # http://127.0.0.1:3777 (foreground; Ctrl+C stops it)
netpro status     # install · database · identity · server health · providers
```

Upgrading from the withdrawn v3.0.0 bundle, from a source checkout, or from
nothing at all is the same three commands. `~/.netpro` is untouched: your
database, identity, config and access token carry over.

```bash
npm uninstall -g netpro        # drop whatever is there (including a stale link)
cd ~                           # not the checkout: `npm install -g` with no name installs the cwd project
npm install -g https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.1/netpro-3.0.1.tgz
netpro status
```

### Verify the download

```bash
curl -LO https://github.com/NiravRVaghasiya/NetPro/releases/download/v3.0.1/SHA256SUMS
shasum -a 256 -c SHA256SUMS
```

## What went wrong in v3.0.0

The release gate proved the artifact *built*; nothing proved it *ran* from where
a user runs it. The bundled CLI resolves its migrations by walking a list of
candidate directories, and the published layout was not on that list: the package
unpacks its bundle to `<pkg>/apps/cli/dist/index.js` and the migrations to
`<pkg>/packages/db/migrations`, while the resolver looked at `<pkg>` — where no
`migrations/` folder exists.

Three things kept it invisible in the repository:

- from a checkout, `@netpro/db` resolves through `node_modules`, so the migration
  folder is found by a path an installed package never has;
- the tarball genuinely contained all 15 migrations per dialect, so every
  file-presence check passed;
- the smoke scripts ran the CLI from the repository, where `packages/db` is in
  the working directory.

The tag was cut at 12:56, the release published at 13:09, and the fix committed
at 13:21 — after the asset existed. It recorded two downloads before the asset
was withdrawn, which is why this is a patch release rather than a re-cut of
v3.0.0: a published tag is a promise, and the number on the box should change
when the contents do.

## What changed

- **`packages/db/src/migrate.ts`** — `migrationCandidates()` now states every
  layout NetPro ships, including the published root package, where
  `apps/cli/dist/index.js` sits next to `packages/db`. Candidates derived from
  `import.meta.url` are skipped when it is not a file URL, as before.
- **`packages/db/src/package-layout.test.ts`** — pins the published layout, the
  workspace layout, and the no-`import.meta.url` case against a temporary
  directory that reproduces exactly what `npm install -g` unpacks.
- **`scripts/smoke/installed-package.sh`** — packs, installs the tarball into a
  scratch global prefix, and runs the shipped CLI from a *neutral* working
  directory (`--version`, `init`, `migrate --status`, `status`). The neutral
  directory is the point: run from the checkout and the repository's own
  `packages/db` satisfies the lookup, which is how v3.0.0 shipped. It runs on
  every push to `master` and, in the release workflow, against the exact tarball
  that is about to be published.
- **The version is verified, not hoped for.** `apps/cli/src/cli.ts` and the
  server's `packages/server/src/version.ts` carry the version as literals (a
  bundled CLI has no manifest next to it to read), and unit tests now pin both
  to the root `package.json`. `npm run release:bump -- <version>` moves the
  manifests and both literals in one command, so "bump the version" cannot mean
  "bump most of it".
- **`docs/getting-started.md`** — what a `netpro` that is "not recognized" after
  a successful install actually means (npm's global prefix is not on `PATH`), and
  the two npm behaviours that look like NetPro uninstalling itself.

## What the release gate verifies

`npm ci` → lint → typecheck → the full test suite → build → `scripts/smoke/cli.sh`
→ `npm pack` → the tarball's contents asserted statically (name, version,
publishable, `bin.netpro`, bundled CLI, both migration sets, `better-sqlite3` and
`pg` still runtime dependencies) → `scripts/smoke/installed-package.sh` against
that tarball, which is the check that fails where a user would have.

On the same commit, CI runs the deep gates the release relies on: PostgreSQL
integration (including the performance pass and migration idempotency), the
server smoke on SQLite *and* PostgreSQL, the standalone Web UI smoke, and the
Docker image end-to-end.
